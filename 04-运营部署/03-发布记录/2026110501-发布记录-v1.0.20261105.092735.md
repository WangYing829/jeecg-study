## 本轮挖出的真缺陷（留痕）

> 这一节是本记录最有价值的部分。**发布演练的价值不在于「跑通了」，而在于「跑出真问题」**。

### E-51 上一版发布候选的前端产物是**残缺的**，而构建全程报成功

- **现象**：本轮重建的 `dist/` 是 **4806** 个文件；上一版 `versions/20261105.085009` 与 `versions/20261105.083954` 只有 **3417** 个 —— **少 1389 个**，且旧文件集是新版文件集的**严格子集**（0 个冲突、0 个被移除）。
- **差在哪**：全部在 `dist/js/`（rollup 的 chunk 输出目录）—— 2861 → 4250。`assets/`、`chat/`、`resource/` 数量一致。
- **为什么危险**：缺的是**按需加载的路由 chunk**。`index.html` 引用的入口资源**全都在**（实测 0 缺失）⇒ **首屏正常**，但点菜单/切路由时才报 chunk 加载失败。**任何只看首页的检查都发现不了它。**
- **为什么构建没报错**：两次构建都打印了 `✓ 9761 modules transformed` 与 `build successfully!`，退出码 **0**。**从日志到退出码，没有任何一个判据能发现产物被截断。**
- **根因（已定位到机制层）**：`vite build` 返回后源 `dist` 的文件数**仍在继续增长**（chunk 写出未被全部 await），同步脚本按「当下的快照」拷贝 ⇒ 拷走一部分。
- **处置（已落成可执行判据）**：`build-and-sync.ps1` 新增三道 ——
  ① **等源 dist 写入稳定**（连续两次采样文件数不变才继续）；
  ② **同步后文件数必须与源完全相等**，不等即 `throw`「拷贝被截断，禁止发布」；
  ③ **`index.html` 引用的每个资源都必须真实存在**；
  另：**`-SkipFrontend` 分支也要核对** `latest` 与源的 dist 文件数（此前正是它让残缺产物被当成发布候选快照下来）。
- **验收**：本轮产物 `latest` 与 `versions/20261105.092735` 均 = 4806 文件、`index.html` 引用缺失 0 ⇒ **本版才是第一个完整可发布的前端产物**。

### E-52 发布产物的 WebSocket 指向**构建期默认地址** ⇒ 每页一条连接被拒、通知功能不可用

- **怎么发现的**：本轮**第一次对着发布候选产物取证**（`vite preview` 托管 `builds/latest/frontend/dist`），
  结果 **95 / 102 个页面**带 `WebSocket connection ... ERR_CONNECTION_REFUSED` 控制台错误。
  **对着 dev server 取证永远看不到** —— dev 走 `.env.development`（`http://localhost:8590/jeecg-boot`），产物走 `.env.production`。
- **根因**：`dist/_app.config.js` 里的 `VITE_GLOB_DOMAIN_URL` 是**构建期**写死的
  `http://127.0.0.1:8080/jeecg-boot`；前端消息通知的 WebSocket 地址由它派生
  （`notify/index.vue`：`glob.domainUrl` 把 `http://` 换成 `ws://` 再拼 `/websocket/<userId>`）
  ⇒ 部署到 8590 时它去连 **8080** ⇒ 连不上。
- **为什么上游不算 bug**：`build/script/buildConf.ts` 的注释原文是
  「**生成外部配置文件，用于生产发布后配置，无需重新打包**」⇒ `_app.config.js` 本来就是**运行期覆盖文件**，
  **部署时改**是设计内的动作。**漏的是我们自己的发布流程**：《部署方案》§5.3 原来没有这一步。
- **处置（已落成可执行判据）**：
  ① `build-and-sync.ps1` 新增 `-RuntimeDomainUrl` 参数：改写**源 dist** 的 `_app.config.js` →
  同步到 `latest` → **断言** `latest` 里的值确实生效（没生效就 `throw`，禁止发布）；
  ② 不传该参数时**打印醒目警告**（不默默带着默认值上线）；
  ③ `manifest.json` 增记 `runtimeDomainUrl` 与 `frontendFiles`；
  ④ 《部署方案》§5.3 新增「步骤 4：前端运行期配置」，§7.1 新增**第 11 条冒烟**；
  ⑤ 本版产物已改写为 `http://127.0.0.1:8590/jeecg-boot`（源 dist / `latest` / 版本目录三份一致）。
  ⑥ **补记（本记录定稿后核对发现）**：本版本目录的 `manifest.json` 生成于 **09:32:33**，
     **早于** ③ 的脚本改动 ⇒ 原件只有 4 个键（`sqlFiles` / `backendJar` / `version` / `builtAt`），
     与本节描述的 6 键 schema 不一致。已按当前脚本 schema **补写** `runtimeDomainUrl` 与 `frontendFiles`
     （值全部实测：`frontendFiles = 4806`＝版本目录 `dist` 实际文件数；`runtimeDomainUrl` 直接取自该目录
     `dist/_app.config.js` 的实际内容，非手写）。
     ⇒ **本版 `dist` 的运行期改写发生在构建之后**，manifest 是事后补齐的记录，不是构建时快照。
- **验收**：改写后**重跑发布候选取证**（`vite preview` 托管同一份产物，34 页 × 3 视口 = 102 张），
  **控制台错误从 95 / 102 归零到 0 / 102**，其余指标同样全零：
  落到登录页 0、采集异常 0、失败响应 0、R-04 命中 0、错误文案 0、横向溢出 0。
  ⇒ **E-52 修复前后对比实测，不是推断。**
