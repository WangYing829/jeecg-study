02

备份与恢复

最重要

备份与恢复

2.1 备份策略

对象 周期 保留 方式
业务库 jeecg-study 每日 23:00 30 天 mysqldump + gzip
平台库 jeecg-boot 每周一次 8 份 mysqldump + gzip
错题图片目录 每日 23:00 30 天 增量复制（robocopy）
前端 dist 每次发布时 5 个版本 已在 builds/ 保留
数据库结构与迁移脚本 每次变更时 永久 已在 git

错题图片是唯一不在数据库里的业务数据，必须单独备份。丢了图片不影响学情统计，但原始错题就没了。

2.2 备份脚本

# 02-代码开发/05-源码/04-建库迁移/backup.ps1
param([string]$Env = 'prod')
$ErrorActionPreference = 'Stop'

$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
$backupDir = 'D:\DevProject\2-JavaPrj\20261030-jeecg-study\04-运营部署\03-发布记录\backup'
New-Item -ItemType Directory -Path $backupDir -Force | Out-Null

$dbs = @{ prod = @('jeecg-study-prod','jeecg-boot'); dev = @('jeecg-study') }
$env:MYSQL_PWD = $env:MYSQL_PWD

foreach ($db in $dbs[$Env]) {
  $out = Join-Path $backupDir "$db-$stamp.sql.gz"
  # 注意：mysqldump 单行输出，经 gzip 压缩
  & mysqldump --single-transaction --routines --triggers --default-character-set=utf8mb4 `
    -u root $db 2>$null | & gzip -9 > $out
  if ($LASTEXITCODE -ne 0) { throw "备份失败：$db" }
  Write-Output ("{0}  {1:N2} MB" -f (Split-Path $out -Leaf), ((Get-Item $out).Length/1MB))
}

# 图片目录
$imgSrc = 'D:\DevProject\2-JavaPrj\20261030-jeecg-study\02-代码开发\05-源码\data\upload\study'
if (Test-Path $imgSrc) {
  & robocopy $imgSrc (Join-Path $backupDir "upload-$stamp") /E /NFL /NDL /NJH /NJS /NP | Out-Null
  Write-Output '图片备份完成'
}

# 保留策略：只留最近 30 天
Get-ChildItem $backupDir -Filter *.sql.gz | Where-Object { $_.LastWriteTime -lt (Get-Date).AddDays(-30) } | Remove-Item -Force

Windows 上 mysqldump 不一定自带 gzip。若无 gzip，用 mysqldump --result-file= 生成 .sql 再用 .NET 的 GZipStream 压缩，或直接保留未压缩的 .sql（体积更大但零依赖）。

2.3 恢复

# 恢复业务库
param()
$ErrorActionPreference = 'Stop'
$file = 'D:\...\backup\jeecg-study-prod-20261030-230000.sql.gz'

# 1) 先备份当前状态（覆盖前的救命备份）
# 2) 停服务
Stop-Service study-backend

# 3) 还原
& mysql -u root -e "DROP DATABASE IF EXISTS jeecg-study-prod; CREATE DATABASE jeecg-study-prod DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_unicode_ci;"
& gzip -dc $file | & mysql -u root jeecg-study-prod
if ($LASTEXITCODE -ne 0) { throw '恢复失败' }

# 4) 起服务并验证
Start-Service study-backend
Invoke-WebRequest 'http://127.0.0.1:8093' -UseBasicParsing -TimeoutSec 10

2.4 恢复演练（每月一次）

步骤 动作 通过标准
1 取最近一份备份 文件存在且可解压
2 恢复到临时库 jeecg-study-restore-test 无报错
3 抽查数据 错题池条数、单词条数、上下文条数与备份当天一致
4 抽查业务查询 跑一次复习队列查询，返回正常
5 删除临时库 清理干净

备份不做恢复演练等于没有备份。这是本手册唯一一条不允许例外的规则。

监控与告警

指标 正常 告警阈值 采集方式

5.2 简易监控脚本

# 每 10 分钟执行一次（Windows 计划任务）
$ErrorActionPreference = 'Continue'
$svc = Get-Service study-backend -ErrorAction SilentlyContinue
if (-not $svc -or $svc.Status -ne 'Running') {
  Write-Output "ALERT 服务异常：$($svc.Status)"
  # 尝试自愈
  Start-Service study-backend -ErrorAction SilentlyContinue
  Start-Sleep -Seconds 10
  if ((Get-Service study-backend).Status -eq 'Running') { Write-Output 'RECOVERED 自动重启成功' }
  else { Write-Output 'CRITICAL 自动重启失败，需人工介入' }
  exit 1
}

5.3 日志位置

日志 路径

后端 stderr 同上 stderr.log
应用日志 .../logs/jeecg-boot.log
前端访问日志 nginx/logs/access.log

04

常见故障处置

照着做

常见故障处置

编号 现象 可能原因 处置步骤
T-01 后端服务停止 OOM / 端口占用 / 未捕获异常 1. Get-Service study-backend
2. 看 stderr.log 尾部
3. 内存不足→调 -Xmx；端口占用→netstat -ano \| findstr :8093 查杀
4. 手动 Start-Service 并观察是否再次退出
T-02 服务反复重启 未捕获异常循环 看 stdout.log 中最后一段异常栈；临时加 --spring.profiles.active=prod 复现；不要直接改代码上线
T-03 前端 404（刷新子页） nginx 缺 try_files 在 server 块加 try_files $uri $uri/ /index.html;；nginx -s reload
T-04 前端白屏 构建产物不完整 / JS 报错 1. 浏览器 Console 看报错
2. 比对 dist/assets 与构建日志
3. 重新构建并同步
T-05 接口 500 且提示连接池耗尽 MySQL 连接数被占满 SHOW PROCESSLIST; 查慢查询；确认 jeecg-study 单库连接配置是否正确；重启后端释放连接
T-06 数据库连不上 口令变更 / 服务未启动 mysql -u root -p -e "SELECT 1;" 验证；核对 application-*.yml 与环境变量优先级
T-07 迁移脚本报「已存在」 脚本非幂等 检查 study_schema_migration；不要改已执行脚本，追加补偿脚本
T-08 复习队列为空但有错题 next_review_at 为空或排期未生成 查 study_error_pool.next_review_at 是否为 NULL；重新触发队列物化
T-09 错题丢了 事务未提交 / 手动删了数据 1. 查 study_error_pool 是否真缺
2. 查 study_practice_record_* 是否有记录
3. 从备份恢复
T-10 护眼提醒不触发 阈值配置 / 心跳中断 1. 查 study_context.eye_interval_min
2. 查 study_eye_usage.heartbeat_count 是否增长
3. 心跳断了→查前端 useEyeGuard 与网络
T-11 端口被占 上次进程未退出 netstat -ano \| findstr :8093 → taskkill /PID <pid> /F；先确认不是别的服务
T-12 页面数据为空但库里有 Redis 缓存脏数据 1. 查 study:kp:tree:* 缓存键
2. 删除相关键
3. 重进页面重新加载

6.1 排障通用顺序

1. 先确认范围：单个页面 / 单个模块 / 整体
2. 查服务状态与日志尾部（stdout + stderr）
3. 查接口：直接 curl 该接口，看响应体
4. 查数据：连库看目标表与迁移记录
5. 查缓存：Redis 相关键
6. 定位后再动手，不要先重启再猜

先看日志再动手。重启会丢现场。

数据维护

动数据

数据维护

7.1 错题池健康度检查

-- 1) 无排期的错题（异常）
SELECT COUNT(*) FROM study_error_pool
WHERE review_status = 1 AND next_review_at IS NULL;

-- 2) 长期积压（超过 30 天未复习）
SELECT COUNT(*) FROM study_error_pool
WHERE review_status = 1 AND next_review_at < DATE_SUB(CURDATE(), INTERVAL 30 DAY);

-- 3) 错因分布（用于评估五维是否够用）
SELECT error_cause, COUNT(*) AS cnt
FROM study_error_pool GROUP BY error_cause ORDER BY cnt DESC;

-- 4) 空知识点归属（应为 0）
SELECT COUNT(*) FROM study_error_pool WHERE knowledge_point_code IS NULL;

第 3 条是「错因维度由真实错题反推」的证据来源。某维度长期为 0 或某维度占比 > 60%，说明五维划分需要调整——这是 V1 复评的输入。

7.2 复习队列积压

SELECT schedule_date, COUNT(*) AS cnt
FROM study_review_schedule
WHERE status = 1
GROUP BY schedule_date
ORDER BY schedule_date DESC
LIMIT 14;
现象 处置
单日 > 50 正常：超过单日上限的部分自动顺延
连续 3 天 > 50 异常：孩子可能已经放弃；检查是任务过重还是排期算法有问题
队列为空但错题很多 查 next_review_at 是否为 NULL

7.3 坐标树版本巡检

-- 现行节点数 vs 历史节点数
SELECT version, status, COUNT(*) FROM study_knowledge_point
GROUP BY version, status ORDER BY version;

-- 失效但仍在被错题引用的节点（正常，但要确认不重复）
SELECT kp.point_code, COUNT(e.id) AS err_count
FROM study_knowledge_point kp
JOIN study_error_pool e ON e.knowledge_point_code = kp.point_code
WHERE kp.status = 0
GROUP BY kp.point_code LIMIT 20;

7.4 分表维护

-- 查看现有分表
SHOW TABLES LIKE 'study_practice_record_%';

-- 确认当月表已建
SELECT COUNT(*) FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'jeecg-study' AND TABLE_NAME = CONCAT('study_practice_record_', DATE_FORMAT(NOW(), '%Y%m'));

若为 0，说明月度建表任务未执行，手动执行 05-init-month-table.sql。

08

应急处置流程

出事了

应急处置流程

8.1 服务不可用

1. 确认范围：前端 / 后端 / 数据库 / 全部
2. 看日志定位（T-01 ~ T-12）
3. 能自愈就自愈（重启服务、清缓存）
4. 不能自愈 → 从 builds/ 回滚到上一版本
5. 数据损坏 → 从备份恢复（先做覆盖前备份）
6. 恢复后跑冒烟检查 + 红线冒烟
7. 写事件记录：时间线、原因、处置、影响

8.2 数据异常

情况 处置
错题大量丢失 立即停止服务 → 备份当前状态 → 从最近备份恢复 → 比对条数
排期错乱 查 study_review_schedule；必要时重建队列（删除未完成排期后重新物化）
坐标树损坏 从备份恢复 study_knowledge_point；注意保留失效版本
统计数字对不上 先核对 study_error_pool 与 study_practice_record_* 的条数，再查聚合逻辑

8.3 红线被破（最严重）

1. 立即停用对应功能（置 feature 开关为 false，或临时下线该路由）
2. 评估影响范围：是否有孩子已经看到答案？数据是否需要追溯？
3. 修复 + 补自动化断言（写进 check-redline.ps1）
4. 回归全部 24 条红线断言
5. 事件记录 + 复盘：这条例外为什么没被测试拦住？

红线被破不追求「快速上线」，只追求「确认没被绕过」。 宁可停一天。
