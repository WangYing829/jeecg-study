# 架构决策记录（ADR）

> **决策一旦定下，就带上「复审触发条件」**——没有触发条件的决策，AI 会在某个会话里顺手推翻它，造成大面积返工。
> 权威全文在 `00-项目说明.md` 与各设计说明书；本文件把散落的决策**收拢成可检索的一处**，并补上复审条件。

## 格式约定

| 字段 | 含义 |
|---|---|
| 状态 | 已采纳 / 待确认 / 已废弃 / 被 ADR-XXX 取代 |
| 背景 | 为什么需要做这个决策（不是「我们决定…」而是「面对什么问题」） |
| 决策 | 一句话说清做了什么 |
| 理由 | 为什么选它而不是备选 |
| 影响 | 会带来什么好处 / 代价 |
| 复审触发条件 | **什么情况下这个决策应该被重新评估**（关键字段，不能空） |

## ADR-001 双数据源：平台表留 `jeecg-boot`，业务表进 `jeecg-study`

- **状态**：⛔ **已被 ADR-015 取代**
- **背景**：JeecgBoot 的用户、权限、菜单、字典深度耦合 `jeecg-boot` 库。若把平台表也搬进新库，底座的大量 SQL 会失效。
- **决策**：平台表留在 `jeecg-boot` 库，业务表进 `jeecg-study` 库，用 `@DS("study")` 切换。
- **理由**：改动面最小，且与 monitorV2 现状一致。
- **影响**：✅ 底座零改动；⚠️ 跨库事务需要处理，⚠️ `@DS` 在本仓库**无先例**（见 ADR-014 关联项与知识库 §3.3）。
- **复审触发条件**：① 出现真实的跨库事务需求且 `@DS` + `@Transactional` 组合验证失败；② 底座开始支持多租户。
- **→ 后续**：V1.1 引入**独立基座**后不再共享 `jeecg-boot` 库，双数据源的前提消失，被 ADR-015 取代。

## ADR-002 独立 Maven 模块 `jeecg-module-study` + `jeecg-module-study-api`

- **状态**：⚠️ **已调整**（ADR-016）：改为**单模块** `jeecg-module-study`
- **背景**：业务代码要么并入 `jeecg-module-system`，要么独立成模块。
- **决策**：独立模块，边界清晰可整体摘除。
- **理由**：与 monitorV2 的 `jeecg-module-monitor` 做法一致，工程形态已被验证。
- **影响**：✅ 边界清晰；⚠️ 需要在父 pom 的 `<modules>` 注册、在 `jeecg-system-start` 的 pom 依赖。
- **复审触发条件**：出现第二个业务模块，或模块数量增长到难以维护。
- **→ 后续**：不再拆 api 子模块——上游 `jeecg-module-system` 拆 api/biz 是因为它被跨模块引用，本模块无此需求（ADR-016）。

## ADR-003 本期形态按 Web 双视图落地

- **状态**：已采纳（**待形态验证**）
- **背景**：竞品分析倾向小程序，但未最终确定。
- **决策**：学习端 + 家长端两个 Web 视图；接口保持无状态化。
- **理由**：先落地可跑形态，同时为小程序 / APP 预留。
- **影响**：✅ 立刻能跑；⚠️ 小程序形态下护眼与全屏交互体验会打折。
- **复审触发条件**：形态验证结论出来，或用户明确要小程序 / APP。

## ADR-004 学习端用独立全屏布局 `layouts/study`

- **状态**：已采纳
- **背景**：孩子端要沉浸与聚焦，管理端是信息密度型界面。
- **决策**：学习端不加载管理端顶栏与侧栏，独立布局。
- **理由**：使用场景根本不同。
- **影响**：✅ 专注；⚠️ 学习端不能用管理端的列表页方案，要单独实现。
- **复审触发条件**：学习端需要复用管理端导航。

## ADR-005 护眼四项进 V0，不延后

- **状态**：已采纳
- **背景**：近视率 52.7%，护眼是产品指标而非营销词。
- **决策**：用眼统计 / 蓝光过滤 / 休息提醒 / 间隔可配，四项全部进 V0。
- **理由**：晚做等于不做——护眼是使用前提，不是功能。
- **影响**：✅ 护眼成为底座能力；⚠️ V0 工作量增加。
- **复审触发条件**：用户明确同意延后。

## ADR-006 错因五维首版固定，但记录每个错因标签的使用频次

- **状态**：已采纳（**V1 后复评**）
- **背景**：竞品证据（A+ 错题本自定义错因）要求错因由真实错题反推，与固定五维冲突。
- **决策**：首版固定五维（概念不清 / 审题偏差 / 计算失误 / 方法不会 / 时间不够），同时记录每个标签的使用频次。
- **理由**：工程化妥协——先保证错因必填可统计，再让数据决定是否扩展。
- **影响**：✅ 首版实现简单；⚠️ 维度可能不够用。
- **复审触发条件**：使用频次数据显示某类错误长期无法归入五维。

## ADR-007 变式生成为结构化模板变换，模型只做自然语言润色

- **状态**：已采纳
- **背景**：让模型直接生成变式，答案无法验算，判分就必然依赖模型 → 违反 R-02。
- **决策**：变式由**规则**做结构变换（答案恒可验算），模型只润色表述。
- **理由**：R-02 的根本保障在结构，不在提示词。
- **影响**：✅ 答案恒可验算；⚠️ 变式多样性受模板库限制。
- **复审触发条件**：模板库覆盖不了实际需要的变式类型。

## ADR-008 `judge_source` 只允许 `rule` / `rule+model`

- **状态**：已采纳
- **背景**：千问批改误判的证据说明模型判定不可靠。
- **决策**：在**类型层面**排除 `model` 单独取值。
- **理由**：把红线 R-02 落到数据层，比落到代码规范更难被绕过。
- **影响**：✅ 红线有数据层保险；⚠️ 需要 CHECK 约束 + 应用层双保险。
- **复审触发条件**：出现经过验证的模型判定方案，且有可复现的准确率数据。

## ADR-009 练习页答案区不渲染到 DOM

- **状态**：已采纳
- **背景**：反搜题是本产品最核心的风险。
- **决策**：初始态**不渲染**答案区（不是 `display:none`）。
- **理由**：让 R-01 可以用 DOM 查询直接验收，而不是靠肉眼。
- **影响**：✅ 红线可自动化验证；⚠️ 需要额外的取解析接口与状态管理。
- **复审触发条件**：无。

## ADR-011 统一 HTML 报告壳子 + Markdown 源稿 + 生成器

- **状态**：已采纳
- **背景**：10 份交付物如果各写各的，风格漂移且无法批量重建。
- **决策**：源稿 Markdown → 生成器 → 自包含 HTML；静态校验 + 浏览器校验台双层把关。
- **理由**：产物风格一致、可 diff、可批量重建。
- **影响**：✅ 一致性有保障；⚠️ 内容改动必须回到源稿。
- **复审触发条件**：产物形态需要脱离 HTML（如要生成 Word / PDF）。

## ADR-012 浏览器验证用内置 Browser + iframe 校验台

## ADR-014 分包方式：建议改为「业务域 → 技术层」

- **状态**：✅ **已采纳（关闭）** —— 口径已定：**域优先**
- **背景**：《系统设计说明书》§4.1 画的是**技术层优先**（根下并列 `controller/ service/ entity/ mapper/`），而 monitorV2 实际工程是**域优先**（`monitor/alarm/controller`、`monitor/alarm/service`…）。
- **决策**：jeecg-study 采用**域优先**（`study/family/controller`、`study/family/service`…），层在域内。
- **理由**：① JeecgBoot 官方 `CLAUDE.md` 明确约定 `org.jeecg.modules.<module>.{controller,entity,mapper,service,vo}`，**域优先是上游官方规范**；② 与 monitorV2 实际工程一致；③ 一个业务域的代码物理聚合，**AI 更不容易漏建目录**。
- **影响**：已同步修订《系统设计说明书》§4.1、§2.1、§4.2。
- **复审触发条件**：域内文件数超过约 15 个、或同一实体需要被多个域以不同视角复用。

## ADR-015 单库：平台表与业务表全部进 `jeecg-study`（V1.1 新增）

- **状态**：✅ **已采纳**（取代 ADR-001）
- **背景**：ADR-001 假定平台表留在 `jeecg-boot` 库、业务表进 `jeecg-study`，双数据源切换。V1.1 引入**独立基座**——jeecg-study 使用自己拉取的 JeecgBoot v3.9.2，与 monitorV2 完全隔离。同时多用户要求家长与孩子都是 `sys_user`，平台表变成业务刚需。
- **决策**：平台表（133 张）与业务表（17 张）**同在 `jeecg-study` 库**；数据源只保留默认 `master`；**`@DS("study")` 取消**。
- **理由**：① 独立基座若与 monitorV2 共享 `jeecg-boot` 库就谈不上独立；② 平台表是业务刚需（用户体系），同库关联查询与事务边界最简单；③ 少一套数据源，少一类跨库事务 bug。
- **影响**：✅ 不再有跨库事务与 `@DS` 切换的复杂度；✅ 本地「一个库看全貌」；⚠️ 与 monitorV2 的 `jeecg-boot` 库彻底分离，不能互相看到对方的表。
- **复审触发条件**：① 需要把 jeecg-study 的平台表迁回共享库；② 平台表与业务表的备份周期/权限要求出现冲突。

## ADR-016 业务模块形态：单模块 `jeecg-module-study` + 域内分层（V1.1 新增）

- **状态**：✅ **已采纳**（调整 ADR-002）
- **背景**：ADR-002 原计划 `jeecg-module-study` + `jeecg-module-study-api` 两个模块。上游 `jeecg-module-system` 拆 api/biz 是因为它被其他模块引用；上游 `jeecg-module-demo`、monitorV2 的 `jeecg-module-monitor` 都是单模块。
- **决策**：**单模块** `jeecg-module-study`，域内再分 `controller/ entity/ mapper/ service/ service/impl/ vo/ dto/`。
- **理由**：本模块无跨模块引用需求，多一个模块只增加构建复杂度与依赖管理成本；与上游 demo 模块、monitorV2 一致。
- **影响**：✅ 构建更简单；✅ 与上游包结构约定一致；⚠️ 若将来要把 study 能力开放给别的模块，需再拆 api 模块。
- **复审触发条件**：出现第二个模块引用 study 的 service 接口。

## ADR-017 多用户身份模型：孩子复用 `sys_user` + PIN 登录（V1.1 新增）

- **状态**：✅ **已采纳**
- **背景**：需要支持多个孩子、多个家长，家长↔孩子多对多。孩子端要给低龄孩子用，若复用管理端的用户名密码，记忆负担过重且暴露管理端登录方式。
- **决策**：**孩子也是一个 `sys_user`**（角色 `study_kid`），只把登录方式换成 **PIN**；家长走底座原生 `POST /sys/login`。孩子端是**独立两步登录页**：家庭码 → 选孩子 → 输 PIN。
- **理由**：① **复用底座现成的 Shiro/JWT/Redis 会话/`@RequiresPermissions` 全套能力，不新增第二套认证栈**——这是「多用户但不做通用权限体系」的关键；② 孩子端不出现「用户名/密码」；③ 家庭码作为第一道，避免公开列出所有孩子。
- **影响**：✅ 认证栈零新增；✅ 权限体系天然复用；⚠️ 需要新增 `study_family` / `study_child` 等 4 张表；⚠️ PIN 强度低（4–6 位数字），靠失败 5 次锁 10 分钟兜底。
- **复审触发条件**：① 孩子年龄段提升到能记密码；② 需要支持孩子端人脸/图案解锁；③ 出现 PIN 暴力破解的实测风险。

## ADR-018 数据范围隔离：以 `child_id` 为唯一维度（V1.1 新增）

- **状态**：✅ **已采纳**
- **背景**：多家长多孩子后，「谁能看什么」成为核心安全命题。若在每个接口里散写过滤条件，漏一处就是数据泄露。
- **决策**：**内容/知识库全局共享**（教材版本、考点树、题库、母题、词库、语法点），**学习行为/数据按 `child_id` 隔离**（上下文、错题池、排期、变式、作文、作答记录、用眼统计，共 7 张表）。过滤只允许发生在 `family/scope/ChildScopeHelper`，家长侧的 child 集合必须**实时查关系表**并与前端参数**求交集**；越权统一返回 **4010**（不是 404，避免资源探测）。
- **理由**：内容供给成本高，家庭内共享合理；学习数据必须隔离。集中式 scope 组件比散落过滤条件更不容易漏。
- **影响**：✅ 越权可自动断言；✅ 家长只见关联孩子；⚠️ 7 张表要加 `child_id` 并回填存量数据。
- **复审触发条件**：① 出现跨家庭共享内容的需求（如亲戚共用题库）；② 孩子数量增长到需要分区/分库隔离。

## ADR-019 主色沿用上游默认 `#1890ff`，不自定义品牌色（V1.1 新增）

- **状态**：✅ **已采纳**
- **背景**：设计规范旧版基于 monitorV2 取样，配色与上游 JeecgBoot 基座不完全一致。基座已就位后，「jeecg-study 用什么主色」成为必须一次定死的问题——它牵动 10 级色阶、antd 运行时 token、antd 组件内部色板、暗色变量组与全部既有页面。
- **决策**：**主色沿用上游 JeecgBoot v3.9.2 默认 `#1890ff`**（`src/settings/designSetting.ts:10` → `build/generate/generateModifyVars.ts:38` → `src/App.vue:71,76`），不引入 jeecg-study 专属品牌色。设计规范 §3.1 明确「主色不改」：需要主色变体时用 `primary-1`~`primary-10` 色阶，不用 `lighten()`/`darken()` 现算。
- **理由**：① 上游 `SIDEBAR` 默认值已是 `#1890ff`，**改主色等于与上游长期对抗**，每次升级都要重做一遍色板；② 项目已有 5 份文档锁定 `#1890ff`，改动成本不对称；③ 主色换品牌是**架构级变更**，收益（品牌辨识度）不匹配成本（色板 + 暗色 + token 全链重做）。
- **影响**：✅ 与上游零摩擦，升级不返工；⚠️ 失去品牌辨识度，需要品牌时用 logo / 封面 / 顶栏 Logo 渐变区承载，不动主色令牌；⚠️ 想换色必须先补 ADR 并重跑设计规范。
- **复审触发条件**：① 公司层面确定 VI 规范并要求落地到主色；② 上游 JeecgBoot 官方变更默认主色（需重新评估是跟随还是锁定）。

## ADR-020 设计规范以基座 `file:line` 为真源，并显式区分「基座锁定」与「本项目自定」（V1.1 新增）

- **状态**：✅ **已采纳**
- **背景**：旧版设计规范取样自 monitorV2，与本项目实际基座（上游 JeecgBoot 3.9.2）**不一致**，导致 3 条实际错误的规则：表单布局（`vertical` vs 上游默认 `horizontal`）、移动端阈值（768px vs 实际 992px）、表格分页（自研 vs 上游 `BasicTable` 内置）。根因不是笔误，而是**规范没有指定「真源从哪来」**。
- **决策**：《产品设计规范》**以基座源码 `file:line` 为唯一真源**，每条数值标注来源文件与行号；规范内**明确区分两类条目**——「基座锁定（可回溯）」与「本项目自定（基座没有，规范说了算）」，后者在 §1.4 集中列出 13 项。**基座未定义、且 antd 自身默认值在仓内不可取证的，不臆造 `file:line`**，标注「antd 默认（仓内不可引用）」。
- **理由**：① 规范的价值在于「可核对」，不能核对的值等于没写；② 把「基座如此」和「我们如此」混在一起，后续 agent 会把自定项误当成上游约定照抄；③ 明确「不可取证」比硬凑一个行号诚实——`node_modules` 未安装时 antd 默认值在仓内根本没有来源。
- **影响**：✅ 规范条目可逐条核对，改基座时能定位受影响的条目；✅ 后续 agent 能区分「照抄上游」与「按规范自定」；⚠️ 每条都要维护行号，上游升版需复核；⚠️ 需要精确引用 antd 默认值时必须先 `pnpm install`。
- **复审触发条件**：① 基座升级到新 tag（必须全量复核行号）；② `node_modules` 纳入仓库或改为可离线核对的产物（可把「antd 默认」换成精确引用）。

## ADR-021 凭据存储：PIN 用 PBKDF2，家庭码用 HMAC+pepper（V0 开发新增）

- **状态**：✅ **已采纳**（**偏离《多用户改造契约》§5 正文**，契约已同步）
- **背景**：契约 §5 写「`PasswordUtil.encrypt(childCode, pin, pinSalt)` 同款哈希」。查基座 `jeecg-boot-base-core/src/main/java/org/jeecg/common/util/PasswordUtil.java`：`ALGORITHM = "PBEWithMD5AndDES"`，且**同时提供 `decrypt`** —— 那是**可逆的对称加密**，不是哈希。孩子 PIN 只有 4–6 位数字（熵 10^4–10^6），存可逆密文等于把凭据放在明文旁边；拿到库 + salt 就能还原全部孩子的 PIN。
- **决策**：两类凭据**分开策略**，理由是**检索方式不同**：
  - **孩子 PIN** → **PBKDF2-HMAC-SHA256**，每行独立盐（`study_child.pin_salt`），**10 万次迭代**；按 `child_id` 取行后校验。熵低，必须慢 KDF。
  - **家庭码** → **HMAC-SHA256(服务端 pepper, code)**，存 `study_family.family_code`；pepper 由配置注入（`jeecg.study.family-code-pepper`），**不入库、不进版本库**。HMAC 是**确定性**的，才能走唯一索引 O(1) 定位家庭。
- **理由**：① 一套算法套两类凭据，会在「检索效率」与「抗离线爆破」之间二选一；拆开后各自最优；② pepper 不入库，拿到数据库也反推不出家庭码；③ 常量时间比较（`MessageDigest.isEqual`）避免计时侧信道。
- **影响**：✅ 孩子 PIN 与家庭码都不以可逆形式落库；✅ 家庭码仍可 O(1) 检索；⚠️ `study_family.family_code_salt` 列当前**不参与校验**（HMAC 确定性方案不需要每行盐），保留作 pepper 轮换迁移的预留位；⚠️ pepper 丢失会导致所有家庭码无法验证，必须有轮换预案。
- **复审触发条件**：① 家庭码数量增长到需要按 pepper 版本并存；② 需要支持家庭码自主重置以外的批量迁移。

## ADR-022 孩子的 `childId` 由服务端实时反查，不放进 JWT claim（V0 开发新增）

- **状态**：✅ **已采纳**（**偏离《多用户改造契约》§5 正文**，契约已同步）
- **背景**：契约 §5 写「孩子 token 附加 claim `childId`、`childCode`、`role=study_kid`」。但底座 `JwtUtil.sign(username, secret, clientType)` 的载荷只带 `username` / `clientType` —— 要塞 `childId` 就得**自己签 token**，那就不再复用底座的 Shiro/JWT 链路了，与「孩子也是 `sys_user`、token 与家长完全同构」的设计相冲突。
- **决策**：**不放 claim**。服务端按 `study_child.user_id` 实时反查当前登录用户的 `childId`（`ChildScopeService.ownChildId()`）。
- **理由**：① 效果等价，token 与家长完全同构，底座鉴权链路一行不改；② 更贴合契约 §3.2「Controller 不接受前端传来的 `childId` 作为唯一依据」—— claim 是**客户端可读**的，反查则完全在服务端闭环；③ 停用孩子后权限**立即**失效，不必等 token 过期。
- **影响**：✅ 身份判定只有一条路径，不存在「claim 与库不一致」的分叉；✅ 停用 / 解除关联即时生效；⚠️ 每个孩子请求多一次索引查询（`study_child.user_id` 有唯一索引，成本可忽略）。
- **复审触发条件**：① 底座 `JwtUtil` 支持自定义 claim 且提供官方扩展点。

## ADR-024 跨域只读查询约定（V0 开发新增）

- **状态**：✅ **已采纳**
- **背景**：错题池 `study_error_pool` 由 `error` 域**独占**维护（F-WRG-04 / G-01），但背单词、语法、写作三个域都要展示「我的错题 / 我的错句」。若每个域各建一张错题表，就违反「统一错题池」这条根本约束。
- **决策**：允许跨域**只读**查询 `study_error_pool`，但**写入一律走 `StudyErrorPoolService` 接口**。跨域只读 Mapper 必须在类注释里写明「只读」与所属域，不新增列、不改写入路径。
- **理由**：① 「统一错题池」是数据层硬约束，破坏它的代价远大于多写一个只读 Mapper；② 只读查询不产生写冲突，域之间的耦合被限制在 SELECT 上；③ 写入路径收敛在一个 Service 里，幂等、复习排期、错因校验这些规则只需要维护一份。
- **落地**：`grammar/mapper/StudyGrammarErrorQueryMapper`（读错句收藏馆）、`word` 域写 `study_error_pool.upgrade_flag` 一列（跨域写，需在交付报告登记）。
- **影响**：✅ 各域不重复造错题表；⚠️ 错题池表结构变更时，所有跨域只读 Mapper 都要跟着改。
- **复审触发条件**：错题池拆表，或引入只读视图 / 物化视图作为跨域契约。

## ADR-025 写作域数据落位与家长反馈归属（V4 开发新增）

- **状态**：✅ **已采纳**
- **背景**：`study_writing` 既有六层拆解内容，又有学生作品与家长反馈的需求，但表里 `layer` 的原始注释只列了 `HOOK / OPEN / MATERIAL / STRUCT / HAND / END` 六个拆解层；家长反馈属于「家长端资源域」还是「写作域资源域」也未定。
- **决策**：
  1. `study_writing.layer` 扩展三个非拆解层：`OUTLINE`（学生提纲）、`DRAFT`（学生初稿）、`FEEDBACK`（家长一句话反馈）。
  2. **六层拆解是全局内容**：`child_id = NULL`；学生提纲 / 初稿、家长反馈：`child_id = 孩子的 id`。查孩子自己的行必须带 `child_id` 条件。
  3. **家长反馈归写作域**，端点落在 `/api/v1/study/writing/feedback`（权限码 `study:parent:writing:feedback`），不放在家长端资源域，避免与家长端只读边界打架。
  4. 提纲是否通过**不单独存状态列**，服务端读提纲内容用同一条规则重算（幂等、不会出现状态与内容不一致）。
  5. 写作病句按错因标签进统一错题池（`source_module = WRITING`、`content_type = PARAGRAPH`、`judge_source = rule`）。
- **理由**：① 不改表结构、不新增脚本（数据库是本轮既定的交付物，改表会连带改 DDL 真源与追溯矩阵）；② 「重算而不是存状态」天然幂等，且杜绝「状态说过了、内容其实没过」的不一致；③ 反馈放写作域后，家长端只读边界（只给报告不给辅导建议）仍然成立。
- **影响**：✅ 写作域自包含；⚠️ `layer` 的取值集合比 DB 文档多三个，查询必须显式列出要哪几层，不能「不按 layer 过滤全取」。
- **复审触发条件**：① 引入独立的作品 / 反馈表；② 家长端资源域统一收编反馈与提醒偏好。

## ADR-026 语法域零 AI 依赖：变形走语料库、检测走规则表（V3 开发新增）

- **状态**：✅ **已采纳**
- **背景**：F-GRM-01 要求给一个中文意思输出五种英文表达，F-GRM-02 要求标出错处并给出三件套讲解。接口文档原本允许「语料库未命中时由模型生成」。但 R-02 明确「AI 只做解释层」，且本轮**没有接入任何 AI 客户端**。
- **决策**：
  1. **句子变形器只检索语料库**（`study_grammar_point.transform_variants`）；未命中就返回空列表 + 提示文案，`source = unavailable`，**不猜不编**。
  2. **错误检测是确定性规则表**（正则 + 固定最小讲解 / 例句 / 反例 + 修正器），`source` 恒为 `rule`。
  3. 语料条目缺某种形态时，用语法点的例句 / 反例兜底，保证输出**恒定五态**（TC-05-01）。
  4. 修正器契约是「整段匹配文本 → 整段修正文本」，这样 `am wanting` 才能被整体改成 `want`，而不是只改其中一个词。
  5. 错句按 `source_module = GRAMMAR` 进统一错题池，`content_id = 语法点业务ID + "#" + 句子短摘要`——同一句话幂等，同一语法点下的不同错句各占一条。
- **理由**：① 规则可复现、可单测，符合「AI 只做解释层」；② 修正器按整段改，避免改出「I wanting to go」这种半截句子；③ 幂等键带句子摘要，收藏馆才能筛出全部错句。
- **影响**：✅ 语法域零 AI 依赖、离线可跑；⚠️ 语料未覆盖的中文意思暂时返回空结果，需要运营补语料。
- **复审触发条件**：接入 AI 客户端后重新评估「未命中降级」策略。

## ADR-027 类简单名全模块唯一（Spring 启动阻断的根治约定）

- **状态**：✅ **已采纳**
- **背景**：MyBatis-Spring 2.0.7 用「类名去首字母小写」作为 Mapper 的 bean 名。开发过程中出现过 `error` 域与 `practice` 域**各有一个 `StudyContextMapper` / `StudyQuestionMapper`**（不同包、同名），直接抛 `ConflictingBeanDefinitionException`，**整个 Spring 上下文起不来**——本轮已实测复现并留证。Spring 对普通 `@Service` / `@Controller` 也有同样的默认 bean 名规则。
- **决策**：study 模块内**所有** Mapper / Service / Controller 的**简单名必须全模块唯一**；跨域同名一律重命名（用域前缀区分，如 `StudyErrorContextMapper` / `StudyPracticeContextMapper`）。上游基座 `@MapperScan("org.jeecg.**.mapper*")` 不动。
- **理由**：① 改上游 `@MapperScan` 加 `nameGenerator` 会影响全基座，且违反「不改上游」约定；② 重命名只动本模块自己的类，代价最小、影响可控；③ 命名带上域前缀后，冲突在编码期就能靠肉眼与脚本发现。
- **影响**：✅ 启动期冲突彻底消除；⚠️ 新增类时要自查重复名（`Get-ChildItem -Recurse -Filter *.java | Group-Object BaseName`）。
- **复审触发条件**：① 升级 MyBatis-Spring 并改用 `nameGenerator`；② study 模块拆分为多个 jar。

## ADR-028 红线断言的扫描范围 = 本项目管辖的前端目录（V0–V4 合流新增）

- **状态**：✅ **已采纳**
- **背景**：`RedLineScanner.scanFrontendCopy` / `scanHiddenAnswerImplementation` 原先用**绝对路径**判断「这个文件是不是学习端 / 家长端」，判据是路径里含 `study` / `parent` / `kid`。但**仓库路径本身就叫 `20261030-jeecg-study`** → 上游 JeecgBoot 基座的几百个 demo / 仪表盘页面全部被当成学习端扫。实测误报：`src/views/report/chartdemo/index.vue`（「销售额排行」）、`src/views/dashboard/Analysis/...`（文件名含 analysis）、`src/components/Form/src/.../JUpload.vue`（同时含隐藏指令与答案标识）。同时 `JAVA_STRING` / `VUE_TEXT` 正则存在灾难性回溯，扫上游 825KB 的 `canvas-editor.js` 直接 `StackOverflowError`。
- **决策**：
  1. **前端红线只扫本项目管辖的三个目录**：`src/views/study/**`、`src/layouts/study/**`、`src/components/study/**`。上游基座页面不属于本产品，按「上游基座零改动」约定不得纳入红线范围。
  2. 范围判断一律用**相对 `frontendRoot()` 的路径**，禁止用绝对路径做子串匹配。
  3. 扫描用正则必须**线性复杂度**：`JAVA_STRING` 用占有量词（`++` / `*+`），`VUE_TEXT` 用懒惰量词（`*?`）；禁止会指数回溯的「贪婪 + 交替」写法。
- **理由**：① 红线约束的是本产品交付给用户的界面，拿上游 demo 页当判据等于逼我们改上游；② 路径含子串判定在「仓库名带 study」的场景下必然误判，这类缺陷在扫描器里出现过两次（D-02 空通过、D-08 范围泄漏），必须用结构化路径解决；③ 正则爆栈会让整个红线套件不可用，属于「一条断言打挂全量」的严重放大故障。
- **影响**：✅ 红线只对本产品代码负责，判定可复现；⚠️ 未来若新增前端目录（如 `layouts/parent`），必须同步加进 `PROJECT_FRONTEND_DIRS`，否则新目录**不受红线约束**。
- **复审触发条件**：① 前端目录结构变更；② 引入 AI 生成代码做前端批量改造。

## ADR-029 一个类实现多个 Service 契约时，测试必须 mock 具体实现类（V0–V4 合流新增）

- **状态**：✅ **已采纳**
- **决策**：当同一个实现类同时实现多个 Service 契约（例：`StudyErrorPoolServiceImpl` 同时实现 `StudyErrorPoolService` 与 `StudyErrorManageService`）时，测试里的 `@MockBean` **必须指向具体实现类**，不得指向其中任一接口。
- **背景**：Spring 的 `@MockBean` 按**类型**替换 Bean。`StudyErrorPoolServiceImpl` 是这两个契约**唯一**的 Bean，一旦 mock 了 `StudyErrorPoolService` 接口，这个 Bean 就被整体换成「只实现该接口」的替身 → `StudyErrorManageService` 无人实现 → `StudyErrorPoolController` 构造器注入断链 → **整个 Spring 上下文起不来**，连累同一 JVM 里所有测试类（实测 210 条里 82 条失败）。mock 具体类时替身是具体类的子类，天然同时实现两个接口，契约不破。
- **理由**：① 根因是「一个类两个契约」，这是设计现实，测试要适应它而不是让测试去改架构；② 治本方案（拆成两个独立 Bean + 互相委托）在本项目走不通——委托方若依赖被 mock 的接口会拿到 mock 替身，若依赖具体类则会在 mock 替换时被摘掉，注入直接失败；③ mock 具体实现类的语义也更准确：这些用例要替换的就是「错题池服务」这个整体。
- **影响**：✅ 上下文不再被单个测试类的 mock 拖垮；⚠️ 新增「多契约单实现」的服务时，测试必须照此约定写，并在类的 javadoc 里说明。
- **复审触发条件**：上游改用 `@MockitoBean` 或引入按接口隔离的 Bean 代理。

## ADR-030 家长反馈端点与权限码对齐（ADR-025 细化）

- **状态**：✅ **已采纳**
- **背景**：ADR-025 §3 定「家长反馈归写作域，端点落在 `/api/v1/study/writing/feedback`，权限码 `study:parent:writing:feedback`」。但合流时出现**三处不一致**：前端打 `POST /api/v1/study/parent/feedback`（家长端资源域**没有**这个端点，页面功能实际不通）、写作域实现落在 `POST /api/v1/study/writing/parent/feedback`、权限码写成了 `study:parent:feedback`。同时需求 F-PAR-02 / F-FAM-08 / A-21 要求「家长可对**某篇作文 / 某次练习**留一句话」且反馈**绑定具体 child**——前端的「泛化一句话」页面与这条口径也不吻合。
- **决策**：
  1. **以写作域端点为准**：反馈端点为 `POST /api/v1/study/writing/parent/feedback`，列表为 `GET /api/v1/study/writing/parent/feedbacks`；家长端资源域**不新增**反馈端点（保持「家长端资源域只读」的边界，F-PAR-01）。
  2. **权限码对齐 ADR-025**：写入 `study:parent:writing:feedback`，读取 `study:parent:writing:query`。
  3. **反馈必须绑定具体作品**：`WritingFeedbackRequest` 保持 `targetType` / `targetCode` / `content` 三字段，`targetCode` 为初稿业务ID；家长端补 `GET /api/v1/study/writing/parent/drafts` 只读列出可见孩子的最近初稿（**不含正文**），供家长选反馈对象。
  4. 前端家长反馈页改为「选一篇最近的作文 → 留一句话」。
- **理由**：① 「反馈归写作域」是 ADR-025 已定的归属，前端改调写作域比在家长端资源域另开一个端点更符合「家长端资源域只读」；② 绑定具体作品是 F-PAR-02 的明文要求，泛化反馈无法定位到「哪次练习」；③ 初稿摘要不含正文，守住家长端只读边界。
- **影响**：✅ 家长反馈端到端打通，且与需求口径一致；⚠️ ADR-025 §3 里写的路径 `/api/v1/study/writing/feedback` 以本 ADR 为准。
- **复审触发条件**：家长端资源域收编反馈（ADR-025 的复审触发条件之一）。

## ADR-031 SQL 排序确定性规范（并列排序必须可判定）

- **状态**：✅ **已采纳**
- **背景**：首轮 `mvn test` 复跑（验证测试清理修复）时，`StudyWordServiceTest.unitMapsToTextbookOneToOne` **偶发**失败（`expected: "UTU1" but was: "UTU2"`）——上一轮是绿的。根因不在测试：`StudyWordMapper.selectUnitStats` 的 `ORDER BY MIN(unit_order)` **没有唯一兜底键**，测试数据里 UTU1 与 UTU2 的 `MIN(unit_order)` 并列（同为 1），两行谁在前随执行计划漂移。TC-03-01 明文要求「顺序一致」，所以这是**生产侧**的确定性缺陷。顺着这条线索全量排查，又查出 **26 处**同类写法（另 1 处 Java 层排序），其中 3 处是**对外可见的真实缺陷**：
  - 家长端日序列聚合（`listDailyEyeUsage` / `listDailyErrorCount` / `listDailyWritingCount`）**完全没有 ORDER BY** —— 家长端趋势图的横轴顺序会随执行计划漂移；
  - 薄弱考点 TOP-N（`weakPoints`）`ORDER BY cnt DESC LIMIT n` —— 并列时**截断哪几条不确定**；
  - 「相关题目」`selectRelatedQuestionCodes` 无序 `LIMIT 5` —— 等于随机丢数据。
  其余为「最近一条」类查询（`LIMIT 1`）缺主键兜底，以及若干聚合查询缺 `ORDER BY`。
- **决策**：
  1. **对外可见顺序的查询必须显式 `ORDER BY`**，且排序键**末位必须是唯一列**（落在该表唯一索引上，或主键 `id`）。业务唯一但库上无唯一索引的键，也要有确定性兜底。
  2. **「最近一条」（`LIMIT 1`）必须以主键 `id` 兜底**：`ORDER BY create_time DESC, id DESC`。仅按时间排时，同一秒的多行不可判定。
  3. 落成**可执行断言** `StudySqlOrderDeterminismTest`（包 `org.jeecg.modules.study.sql`），三条规则都是必要条件、零误报：
     - **SQL-A**：含 `GROUP BY` 的 SQL 必须带 `ORDER BY`；
     - **SQL-B**：含 `LIMIT n`（n > 1 或参数化）的 SQL 必须带 `ORDER BY`；
     - **SQL-C**：`LIMIT 1` 的 SQL，其 `ORDER BY` 末位键必须落在该表唯一索引上（或为主键 `id`）。
     另配两条**防假绿**用例：扫描有效性（必须真的扫到 SQL、覆盖多个 Mapper）、唯一索引清单有效性（组合唯一索引必须以列集合登记）。
  4. **唯一性判定以真实库结构为准**：断言内置的唯一索引清单由 `information_schema.STATISTICS` 于 2026-10-31 从真实库 `jeecg-study` 实测导出（含组合唯一索引 `uk_family_user(family_id,user_id)`、`uk_word_spelling_line(spelling,line_type)`，以及分区表 `study_practice_record_yyyyMM` 的前缀匹配），**不靠印象罗列**。
  5. **本轮不改表**：三处业务幂等键（`child_id+content_type+content_id`、`subject_code+knowledge_point_code+title`、`child_id+layer+reference_code+title`）**目前没有数据库唯一索引**，靠 `ORDER BY id` 兜底保证确定性；若后续要加唯一索引，走 `02-代码开发/02-数据库/03-脚本/` 的**增量脚本**，不改历史脚本。
- **理由**：① 「顺序一致」是测试用例的明文要求，flaky 用例会持续污染闸门信号，必须在生产侧消除而不是改测试迁就；② 家长端趋势图与 TOP-N 的顺序是**用户可见**的，不是内部实现细节；③ 断言基于真实库实测导出，能同时挡住「新增 SQL 又忘了兜底键」的回归，而不是只修当前这几处。
- **影响**：✅ 消除一类**偶发**失败（对 CI 稳定性价值最大）；✅ 家长端趋势图与薄弱考点顺序确定；⚠️ 断言对**新增表**不自动生效——新表上线时必须同步补进唯一索引清单（清单与库结构不同步会被 `uniqueIndexCatalogMustBeAlive` 用例显式标注）。
- **复审触发条件**：① 业务表新增/改唯一索引（需同步清单）；② 若后续引入 `@SelectProvider` 或 MyBatis XML 写 SQL（本轮断言只覆盖注解式 `@Select`，XML 需扩展扫描器）。

## ADR-032 前端跨组件状态传递改用「模块级共享单例」，禁用 provide/inject 与 defineExpose 传状态

- **状态**：✅ **已采纳**
- **背景**：P2 浏览器取证阶段发现**护眼页拿不到护眼会话状态**（取证缺陷 5/6）——页面显示不出「提醒间隔」，护眼遮罩判定也随之失真。排查出的是**三重**根因，每一重单独看都像「代码写对了」：
  1. **`provide/inject` 方向反了**：`layouts/study/index.vue` 里 `provide()` 的是**布局组件**，而页面模板里写的是 `<StudyLayout>` —— 布局是页面的**子**组件。Vue 的 `provide/inject` 是「父 provide → 子 inject」，页面作为父级根本 inject 不到子级提供的值。
  2. **`defineExpose` + 模板 ref 不可靠**：模板 ref 拿到的是**深层 reactive 代理**，Vue 会把代理对象里的嵌套 ref **自动解包**。`eye.eyeIntervalMin` 拿到的是**数字**而不是 `Ref`，再写 `.value` 永远是 `undefined`（且 `undefined?.value` 静默通过，页面表现为「数据为空」而不是报错）。
  3. **生命周期钩子绑错组件**：护眼会话的 `start()` 若写在状态工厂里，`onMounted` 会**绑定到第一个调用它的组件**。布局挂载顺序一变（路由切页），会话就静默停摆，且没有任何报错。
- **决策**：
  1. 护眼状态**模块级共享单例**：`components/study/StudyEyeState.ts` 拆成两个导出——
     - `useStudyEyeState()`：**纯工厂**，只创建状态，**不得注册任何 `onMounted` / `onBeforeUnmount`**；
     - `useSharedEyeState()`：模块级 `let sharedEyeState: StudyEyeState | null = null` 的**单例入口**，首次调用创建，之后一律复用同一个实例。
  2. **会话生命周期归学习端布局**：`layouts/study/index.vue` 持有 `onMounted(() => eye.start())` / `onBeforeUnmount(() => eye.stop())`；护眼页 `views/study/eye/index.vue` 只**读**状态，不碰生命周期。
  3. **删除** `STUDY_EYE_STATE_KEY` 常量与全部 `provide()` / `inject()` / `defineExpose` 相关写法。
  4. 提醒间隔取值口径：`eye.eyeIntervalMin.value ?? contextIntervalMin.value`——护眼会话下发优先，家长端上下文兜底。
- **理由**：① 这三条都不是「写法偏好」，是 Vue 3 响应式与组件树方向的**硬语义**，靠 code review 很难稳定拦住，必须用**架构约束**（单例 + 工厂无钩子）把错误写不出来；② 模块级单例的生命周期边界恰好等于「整个学习端会话」，而护眼会话的语义（连续用眼时长）本身就是**跨路由**的，provide/inject 的「子树可见性」与需求语义不匹配；③ 「工厂不得注册钩子」把「谁负责 start/stop」从隐式约定变成显式归属，避免路由切换后静默停摆。
- **影响**：✅ 护眼页与布局读到**同一份**状态；✅ 路由切换不再丢会话；⚠️ 单例意味着状态**不随组件卸载自动重置**——测试或多实例场景需显式调用清理（当前布局的 `onBeforeUnmount` 承担 stop 职责）。
- **固化**：`org.jeecg.modules.study.ui.StudyEyeSharedStateTest`（4 条）——① 扫描有效性（必须真的扫到文件）；② 护眼状态**必须全局唯一**（解析模块级单例缓存变量 + 导出共享入口，布局与护眼页必须调用同一入口）；③ 护眼状态模块**不得注册生命周期钩子**（先剥注释再判定）且布局必须同时持有 `start` / `stop`；④ 护眼页**不得**使用 `inject` / `defineExpose` / `STUDY_EYE_STATE_KEY`。
- **复审触发条件**：① 护眼状态需要**按孩子**多实例并存（多孩子同屏）；② 引入 Pinia 或其他全局状态方案；③ 学习端改为多标签页并存且需要跨标签同步。

## ADR-033 家长端页面外壳改「全屏固定层」，不新建 `layouts/parent`

- **状态**：✅ **已采纳**
- **背景**：P2 浏览器取证在 390px / 768px 视口下发现**家长端 3 页被整个盖住**（取证缺陷 7，P0 级）：家长端页面在种子脚本 `07-seed-role-menu.sql` 里就挂在**管理端布局** `layouts/default`（这是上游「所有 DB 菜单都挂默认布局」的实现决定的），而上游 `layouts/default/sider/index.vue:2-12` 在 `<992px` 时把侧栏渲染成**常开的抽屉 + 遮罩**（`:open="!getCollapsed"`）——210px 抽屉压住内容、遮罩压灰整页，家长端在窄屏下**直接不可用**。这违反《产品设计规范》§9.5 / §9.6 与自检 #26 / #27（「家长端无管理端顶栏与侧栏」）。
- **备选与取舍**：
  - **备选 A：新建 `layouts/parent` 目录**。问题是上游 `transformObjToRoute`（`src/router/helper/routeHelper.ts:139-162`）对 DB 菜单**一律挂 `LAYOUT`（管理端布局）**——动态菜单**永远无法用自定义布局**；改这条链路要动上游路由内核，且要处理「静态路由与 DB 菜单同路径冲突」，改动面大、回归风险高。
  - **备选 B：改上游 `layouts/default` 的断点行为**。违反「上游基座零改动」约定。
  - **采纳 C：`StudyParentShell` 改全屏固定层**。
- **决策**：
  1. `components/study/StudyParentShell.vue` 改为 `position: fixed; inset: 0; z-index: 1100` 的**全屏固定层**，盖住管理端抽屉 / 遮罩 / 顶栏 / 侧栏；家长端 3 页（`/study-parent/report`、`/study-parent/error`、`/study-parent/feedback`）**全部**走该外壳。
  2. 因为盖住管理端顶栏后家长端**再无导航与退出路径**，外壳**自带**：3 项页面导航（学习报告 / 错题分析 / 作文反馈，`router-link` + 当前页高亮）+ **登出按钮**（`useUserStore().confirmLoginOut()`）。
  3. 窄屏（`≤992px`）顶部条换**两行**：第一行孩子名 + 切换 + 家庭 + 退出，第二行页面导航。
  4. 窄屏导航**不用横向滚动**（`overflow-x: auto`），改 `flex-wrap: wrap` 换行——横向滚动违反 F-16（窄屏不得出现横向滚动）。
- **理由**：① 「家长端不是管理端」的**产品要求**与「DB 菜单一律挂默认布局」的**上游实现**冲突时，正确的做法是**在本产品管辖目录内解决**（`components/study/**`），而不是去改上游路由内核或基座布局；② 全屏固定层把「家长端页面」与「管理端外壳」彻底解耦——即使将来菜单挂载方式变化，家长端的呈现不受影响；③ 自带导航与登出是**盖住管理端外壳后的必要补偿**，不是额外功能。
- **影响**：✅ 家长端 390 / 768 / 1440 三视口均完整可用、无遮罩、无裁切；✅ 未改动任何上游文件；⚠️ 家长端外壳是 `fixed` 层，**z-index 需高于管理端抽屉**（实测 1100 足够）；⚠️ 若未来家长端页面数量增加，导航项需同步维护（当前 3 项与 3 个路由一一对应）。
- **固化**：`org.jeecg.modules.study.ui.StudyParentShellTest`（5 条）——① 扫描有效性；② 外壳必须 `position: fixed` + `inset: 0` + z-index ≥ 1000（**先剥注释再判定**）；③ 外壳必须自带 3 个页面路由导航 + `router-link`；④ 必须提供 `confirmLoginOut` 登出入口；⑤ 家长端 3 页**都必须**走 `StudyParentShell`。
- **复审触发条件**：① 上游支持「DB 菜单指定自定义布局」（则改回真正的 `layouts/parent`）；② 家长端页面数超过 3 页（导航项需扩展）；③ 家长端需要与管理端**并存**而非替换（则全屏固定层方案不再适用）。

## ADR-034 菜单图标走「离线图标集 + 数据库菜单图标白名单」

- **状态**：✅ **已采纳**
- **背景**：用户 2026-11-02 截图标注「**所有菜单都没有图标**」。第一直觉是数据库 `sys_permission.icon` 缺值，但实测**92 个图标值全有**。真因在三段：
  1. `.env.development` / `.env.docker` / `.env.dockercloud` 的 `VITE_GLOB_ICONIFY_USE_TYPE=online` → `Icon.vue` 走 `Iconify.renderSVG()` **在线**从 `api.iconify.design` 拉图标；本机外网不通（实测 iconify API 与 npm registry 均超时）→ 返回 null → 组件退化成占位符 `<span class="iconify">`（样式 `border-radius:100%`）→ 就是那个**空心圆点**。
  2. 改成 `local` 后，图标数据来自 `vite-plugin-purge-icons` 生成的离线图标集，而该插件**只扫源码文本**（`content` 配置列的 html/pug/vue/js/ts）→ **只存在于数据库、源码里从没出现过的图标名不会被收集**，离线模式下照样是空圆点（实测 3 个）。
  3. 上游基座 `db/jeecg-study-mysql.sql:8241` 的「关于」菜单图标写的是 `simple-icons:about-dot-me`，而 iconify `simple-icons` 集合里现名是 `aboutdotme`（simple-icons v10 起去掉连字符）→ **online / local 两种模式都取不到**。
- **决策**：
  1. 四个环境文件（`.env.development` / `.env.production` / `.env.docker` / `.env.dockercloud`）统一 `VITE_GLOB_ICONIFY_USE_TYPE=local`（`.env.production` 本来就是 local）。
  2. 新增 **`src/components/Icon/data/menu-icons.ts`**：**数据库菜单图标白名单**，纯数据清单，**不被任何模块 import**（purge 插件按文本提取，数组元素本身就是收集点）。新增 / 修改 `sys_permission.icon` 后必须同步登记。
  3. 失效图标名 `simple-icons:about-dot-me` → `aboutdotme`，**数据库与上游源码两边同时改**：DB 走增量脚本 `20-fix-menu-icon-name.sql`；上游 `src/router/routes/modules/about.ts` 改两处（留 `update-begin/update-end` 痕迹）——只改一边都不行（只改 DB → 离线集收不到；只改源码 → 菜单仍取不到）。
  4. 断言 `StudyMenuIconOfflineTest` 把这条链路的四段全盯住：环境变量必须是 local、`Icon.vue` 必须保留 local 分支、**DB 每一个菜单图标都必须能被离线集收集到**、白名单不许积灰。
- **理由**：① 离线可用是**产品硬指标**（内网 / 无外网环境是常态），图标不能依赖在线 CDN；② 「数据库里有 ≠ 渲染得出来」是这条链路最反直觉的地方，必须用**白名单 + 断言**把「DB 图标 ⊆ 可收集集合」变成可执行契约，而不是靠人肉同步；③ 上游失效名属于**上游数据缺陷**，两边同时改是唯一能让「菜单配置」与「图标集」自洽的做法。
- **影响**：✅ 92/92 菜单图标在运行时离线图标集里可取（实测 54 集合 / 1013 图标，缺失 0）；✅ 各环境不再依赖外网；⚠️ **新增菜单图标必须同步登记白名单**，否则断言直接红（这是有意的「吵」）；⚠️ 白名单是**纯数据清单**，不要 import 它进运行时代码。
- **固化**：`org.jeecg.modules.study.ui.StudyMenuIconOfflineTest`（6 条）——① 扫描有效性（环境文件 / 图标组件 / 白名单 / DB 图标 / 白名单图标 / 源码记号都必须非空）；② 四环境 `VITE_GLOB_ICONIFY_USE_TYPE` 必须是 `local`；③ `Icon.vue` 必须保留 local 分支且引用 `@purge-icons/generated`；④ **DB 每个菜单图标必须能被离线集收集到（白名单 ∪ 源码，且源码扫描必须先剥注释）**；⑤ 白名单不许留没人用的图标名；⑥ **白名单文件里不许出现「只在注释里」的图标记号**（否则第 ④ 条会假绿）。
- **复审触发条件**：① 上游支持自定义图标集合上传（则白名单可下沉到后端）；② 菜单图标改为由**后端下发 SVG** 而非 iconify 记号（则整条链路重做）；③ 图标量级超过数千（则白名单改成分片按需加载）。

## ADR-035 admin 角色必须拿到全部 study 菜单权限（授权在数据侧，隔离语义不动）

- **状态**：✅ **已采纳**
- **背景**：用户 2026-11-02 反馈「**侧边栏找不到学习助手 / 家长端菜单**」。逐条排除后定位到**数据侧**：
  - `SysPermissionServiceImpl.queryByUser(userId)` **纯按** `sys_user_role → sys_role_permission → sys_permission` 取菜单，**admin 角色没有「兜底全量」**（不是「admin 自动可见一切」）；
  - `07-seed-role-menu.sql` 只把 study 菜单绑给 `study_kid`(8) 与 `study_parent`(4)，**admin 一条 study 权限都没有**；
  - `parent_id` / `component` / `menu_type` / `hidden` / `status` / 前端 `transformObjToRoute` 均已逐条核对，无问题。
- **决策**：
  1. 新增增量脚本 **`19-seed-admin-study-menu.sql`**：admin 授权**全部** study 菜单(12) + 按钮(41)，`INSERT … SELECT … WHERE NOT EXISTS`，主键 `CONCAT('st_rpa_', LEFT(MD5(...),16))` → **幂等**（实测重跑仍是 53 条）。
  2. admin 同时挂进**演示家庭 A**（`study_family_member` PARENT + `study_parent_child_rel` `is_primary=0`），使管理端点开家长端三页能看到**真实数据**而不是空态。
  3. **不改** `ChildScopeServiceImpl`：不给管理员加任何旁路。家庭 B 仍然隔离；家长 A 访问孩子 B 仍返 **4010**；学习端 kid 页对 admin 返 4010 属**设计内行为**（学习端只认孩子身份）。
  4. 边界写进脚本注释：脚本只解决「**看得见菜单**」与「**演示家庭数据可见**」，不解决「**管理员可代看任意孩子**」——后者是另一个需求。
- **理由**：① 「admin 看不到某个菜单」在 JeecgBoot 里**不是 bug**，是「菜单 = 角色授权」的模型；解法在数据侧（授权），不该在代码侧给 admin 开后门；② 隔离语义（ADR-018）与「菜单可见性」是**两件事**——把 admin 加进演示家庭是数据归属，**不等于**放开跨孩子访问；③ 脚本必须幂等，否则重跑就把 `sys_role_permission` 撑爆。
- **影响**：✅ admin 登录后侧边栏出现「学习助手」「家长端」两项及其下级菜单；✅ 幂等（重跑 53 条不变）；✅ 隔离语义零改动（家庭 B 仍隔离、越权仍 4010）；⚠️ **新增 study 菜单后要重跑脚本 19**。
- **固化**：接口层复验（admin 登录 → `GET /sys/permission/getUserPermissionByToken`）返回的菜单树前两项为「学习助手」「家长端」，子菜单 title / icon 正确；`StudyMenuRenderRuleTest` 另断言 study 一级菜单的 `always_show` 口径。
- **复审触发条件**：① 管理员需要**跨家庭**查看孩子数据（则要另设计「管理员只读视图」，而不是改隔离语义）；② study 菜单数量增长到脚本维护困难（则脚本改为按 `sys_permission` 域前缀动态授权）。

## ADR-036 有可见下级菜单的节点一律 `always_show=0`

- **状态**：✅ **已采纳**
- **背景**：用户 2026-11-02 反馈「**学习助手和家长端的下级菜单没有展示出来**」——两个一级菜单看得见，7 个 / 3 个下级菜单**一个都不渲染**。
- **根因（数据侧触发 + 前端规则）**：
  - 前端 `src/components/Menu/src/components/BasicSubMenuItem.vue:41-48` 的 `menuHasChildren()` 末项是 `&& checkChildrenHidden(menuTreeItem)`；
  - `src/utils/common/compUtils.ts:389-399` 的 `checkChildrenHidden()` **第一句**就是 `if (alwaysShow) { return false; }`；
  - ⇒ **`alwaysShow` 为真时 `menuHasChildren` 恒为 false**，节点被当成叶子节点渲染，children 一个都不渲染；
  - `alwaysShow` 来自 `sys_permission.always_show`，而 `07-seed-role-menu.sql` 给两个 study 一级菜单写了 `always_show=1`。
  - **铁证**：上游 12 个一级菜单（主页 / AI应用平台 / 低代码开发 / 数据可视化 / 系统管理 / 我的租户 / 系统监控 / 消息中心 / 统计报表 / 组件示例 / 导航示例 / 关于）的 `always_show` **全部是 0**，所有子菜单也都是 0；**全库只有我们这两个是 1**。
- **决策**：
  1. 新增增量脚本 **`21-fix-study-menu-always-show.sql`**：`UPDATE sys_permission SET always_show=0 WHERE id IN ('st_menu_study','st_menu_parent') AND always_show<>0`（幂等）。
  2. **口径固化**：**有可见下级菜单的节点一律 `always_show=0`**。`always_show` 在 Vue3 菜单渲染里与「children 展开」**互斥**，它表达的是「没有子菜单时也别塌成一个入口」，不是「强制显示子菜单」。
  3. 断言 `StudyMenuRenderRuleTest` 把口径落成可执行断言：DB 里 `menu_type IN (0,1)` 且**有可见子节点**的节点，`always_show` 必须为 0；同时断言上游 12 个一级菜单的基线口径一致。
- **理由**：① 这是**上游框架的硬语义**，不是本项目的选择——靠「约定大家别这么填」一定会再犯，必须用断言钉死；② 口径与上游 12 个一级菜单**完全一致**，本项目的两个菜单没有理由特殊；③ 修**数据侧**（一条 UPDATE）而不是改上游渲染逻辑——改上游会让所有菜单的行为都变，风险远大于收益。
- **影响**：✅ 修后 `getUserPermissionByToken` 返回的 JSON 里**不再出现 `alwaysShow` 字段**，字段形状与上游「主页」「AI应用平台」完全一致；✅ 7 个 / 3 个下级菜单按上游同款逻辑渲染；⚠️ **以后新增带子菜单的一级菜单必须写 `always_show=0`**（断言会红）。
- **固化**：`org.jeecg.modules.study.sql.StudyMenuRenderRuleTest`（5 条）；**故障注入已做「绿 → 注入 `always_show=1` → 红 → 还原 → 绿」闭环**。
- **复审触发条件**：① 上游把 `alwaysShow` 与 `children` 的互斥关系改掉（则本 ADR 失效）；② 本项目要改用自定义菜单组件（则改为在组件层实现「强制展开」）。

## ADR-037 基座以 diff-only 方式入库，用 `stage` 绕开嵌套仓库拦截

- **状态**：✅ **已采纳**
- **背景**：用户 2026-11-02 要求「把项目上传到 GitHub，基座代码部分**只上传相对于基座修改、新增或删除的文件**」。
  本仓库既有约定（`02-代码开发/05-源码/README.md` §4）就是「只跟踪相对上游 v3.9.2 的改动，上游历史留在基座自己的 `.git` 里」。
- **关键约束**：基座目录 `02-代码开发/05-源码/01-JeecgBoot基座/` **自带一个完整 `.git`**，
  在父仓库眼里就是**嵌套仓库**。实测两个独立的拦截点：

  | 拦截点 | 命令 | 实测现象 |
  |---|---|---|
  | 嵌套 `.git` | `git add -f -- <基座内文件>` | **exit 0 但索引没变**（静默跳过）；`git add <整个基座目录>` → `fatal: 'sub/' does not have a commit checked out` |
  | `.gitignore` | `git update-index --add --index-info`（批量形式） | 被 ignore 规则命中而**静默跳过**（exit 0 但条目没落地） |
  | — | `git update-index --add --cacheinfo`（单条形式） | ✅ **可绕过 ignore**，条目正常进索引，`git status` 不误报，commit + clone 均正常 |

- **决策**：
  1. 新增 **`2026103019-基座同步.py stage`** 子命令：读 overlay 清单 → `git hash-object -w --no-filters` 取 blob →
     `git update-index --add --cacheinfo`（**分批 80 条**，规避 Windows 命令行 32KB 上限）写入父仓库索引。
  2. **必须回读校验**：`git ls-files --cached` 确认条目真在索引里，否则「报成功但没入库」会被当成成功。
  3. **不动基座的 `.git`**：上游历史原地保留，「只跟踪相对上游改动」这条约定不变；
     备选方案（把 `.git` 改名）会让所有基座 git 命令需要显式 `--git-dir`，收益不抵风险。
  4. 父仓库 `core.autocrlf=false` **+ 根目录 `.gitattributes`（`* -text`）** ⇒ blob 与工作区**逐字节一致**，
     且**任何人 clone 检出都是同一批字节**（`-text` 关掉全部换行符转换）。
     只设 `core.autocrlf=false` 不够——那是**本机**配置，别人 clone 时不生效。
  5. `restore` 克隆上游加 `-c core.longpaths=true`：上游代码模板目录路径超 260 字符，
     不开这个开关会「clone 成功但 checkout 失败（Filename too long）」。
  5. 顺带修两处既有缺陷：① 所有 git 调用加 `-c core.quotepath=false`（默认会把中文路径转义成八进制，写进清单就是坏路径）；
     ② `export` 排除清单产物自身（否则下一轮会**自我引用**）。
- **理由**：① 嵌套仓库是 git 的硬边界，绕开工作区扫描是唯一不破坏上游历史的干净解；
  ② 批量形式与单条形式在 ignore 规则上的差异是**实测**出来的，不靠猜；
  ③ 回读校验是防止「报成功但没落地」的通用防线（同 E-15「扫描集合为空 ⇒ 假绿」）。
- **影响**：✅ 父仓库索引 = 394 个基座条目（392 overlay + 2 份清单）+ 97 个仓库自身文件 = **491**；
  ✅ `node_modules` / `target/` / `.git/` / `package-lock` 入库数**全为 0**；✅ clone 后 `restore` 可还原完整基座。
- **固化**：`2026103019-基座同步.py stage`（含回读校验）；`2026103023-凭据扫描.py` 扫**会入库**的文件集合
  （基座目录按 overlay 清单扫，不是按工作区扫）。
- **复审触发条件**：① 改用 git submodule 承载基座（则 stage 退役，改用 submodule 指针）；② 上游改目录结构导致 overlay 清单口径变化。

## ADR-039 孩子端登录页走静态路由（动态菜单机制的唯一例外）

- **状态**：✅ 已采纳
- **背景**：
  本项目的前端路由**全部**由 `sys_permission` 驱动（`url` + `component` + `component_name`），
  前端**没有静态路由**；页面文件在但库里没有菜单 ⇒ 用户在界面上永远找不到入口。
  但 2026-11-02 落地 §11.2「孩子端登录页」时撞上了一个**结构性的死结**：
  孩子**没有账号密码**，只有家庭码 + PIN，登录页必须在**无登录态**下可达；
  而动态菜单（`SysPermissionServiceImpl.queryByUser`）**要先有 token 才下发**——
  挂在菜单里的登录页，孩子根本进不去（他连菜单都看不到，因为没登录）。
  上游底座自己的 `/login` 也是静态路由（`basicRoutes` + `meta.ignoreAuth`），
  说明「免认证页走静态路由」本来就是底座的既定做法。
- **决策**：
  孩子端登录页 `/study/kid/login` 登记为**静态路由**
  （`jeecgboot-vue3/src/router/routes/index.ts` 的 `StudyKidLoginRoute`，`meta.ignoreAuth = true`，进 `basicRoutes`），
  **不**在 `sys_permission` 里建行；其余 12 个页面仍全部走 DB 动态菜单。
- **理由**：
  ① 同一个 path 注册两次（静态 + 动态）会让 vue-router 行为不可预期——**不能两边都建**；
  ② `sys_permission.id` / `url` 都是菜单语义，插一条 `hidden=1` 的免认证菜单并不能让它在无 token 时下发；
  ③ 上游 `/login` 已是同一模式，不算破例，而是**沿用底座惯例**。
- **影响**：
  ✅ 孩子可凭家庭码 + PIN 免登录进入；✅ 其余 12 页仍受「菜单即入口」纪律约束；
  ⚠️ 本项目从此有**一个**静态路由，文档与断言都要显式说明（否则下一个人会「补一条菜单」把它补坏）。
  落地：`22-seed-study-interface-pages-menu.sql` 头部注释 + 断言
  `StudyInterfacePageTest#kidLoginMustBeStaticRoute`（**两头都守**：有静态路由 + 不在 DB 里）。
- **复审触发条件**：
  ① 底座提供「免认证页也能进菜单树」的官方机制 ⇒ 改回动态菜单并撤掉静态路由；
  ② 出现第二个免认证页面 ⇒ 一并评估（仍走 `basicRoutes`，不新建目录）。

## ADR-040 管理端内容维护页只读全局共享内容；「题目维护」不读错题池

- **状态**：✅ 已采纳
- **背景**：
  《前端页面清单》规划态里管理端 9 个页面的接口栏写着「题目维护 → `GET /error-pool` 等复用」，
  落地时逐条核对后端才发现**这个复用是错的**：
  ① `study_error_pool` 是**按孩子隔离的行为表**（`child_id` 非空），
  `GET /error-pool` 强制带 `childCode`，返回的是「**这个孩子**错了哪些题」；
  ② 管理端内容维护页的定位是维护**全局共享内容**（内容表不带 `child_id`），
  把单个孩子的行为数据列在内容维护台里，等于在管理端开了一个看单个孩子学习行为的口子（R-04）；
  ③ 同类问题还有两处：`MotherListItemVO` 混着 `attemptCount / errorCount / mastery / passed`，
  `WordListItemVO` 混着 `feedbackCount / memoryStrength / lastFeedback`——
  这些都是后端 VO 里**本来就有的**行为字段，前端可以选择不展示。
- **决策**：
  ① 管理端 9 个页面**只读全局内容接口**；接口返回体里混带的行为字段**一律不展示**；
  ② 「题目维护」改读**坐标树的内容统计**（`GET /knowledge-points/tree` + `/knowledge-points/search`），
  展示每个考点挂了多少题/词/母题/语法点/拆解，**不再读错题池**；
  ③ 「词表维护」只展示内容字段（业务 id / 释义 / 音标 / 词性 / 单元），
  **拼写不展示**——拼写就是拼写题的答案，词表接口按 R-01 本就不下发它；
  ④ 能改的只有 2 页（上下文配置、考点维护），其余 7 页**只给浏览**，
  没有对应写接口就不给修改按钮（宁可少给一个按钮，也不要给一个点了会失败或改坏数据的按钮）。
- **理由**：
  ① 「接口已就绪」这句话必须由**接口的真实语义**证明，不能由规划态表格的一行字继承——
  规划态写「等复用」时，读者默认那是个内容接口，实际是行为接口；
  ② 红线 R-04 的落地不靠文档靠**列选择**：同一份响应里，内容字段和行为字段是分得开的，
  页面展示哪些列就是红线落点；
  ③ 「少给一个按钮」优于「给一个坏按钮」——写接口没到位时，提供浏览比提供假编辑更诚实。
- **影响**：
  ✅ 管理端不再有任何读单个孩子行为数据的路径；
  ✅ 管理端页面全部走一个通用内核 `ManageContentPage.vue`（tree/form/list 三模式），9 页只提供配置；
  ⚠️ 管理端「维护」能力目前只覆盖 2 页，其余 7 页是内容浏览（已在用户手册 §11.2 写明）；
  ⚠️ 「新增孩子档案」仍只有接口与后台入口，家长端没有「新建孩子」按钮（同样原因）。
  落地：断言 `StudyInterfacePageTest#managePagesMustNotExposeChildBehavior`
  （12 个行为字段 + `/error-pool` 全禁，**先剥注释**）与
  `#wordPageMustNotTouchSpelling`；已做故障注入验证（注入 3 处 → 红 3/3 → 还原 → 绿）。
- **复审触发条件**：

  不能顺手把行为数据塞进内容维护台；

## ADR-041 补齐 `StudyActionColumn` / `StudyEnumTag`；管理端列表走 BasicTable、家长端列表走 StudyDataList

  ✅ 管理端不再有手写 `<a-table>`；操作列统一走 `StudyActionColumn`；
  ✅ 家长端关系标签颜色合法且同名同色；窄屏不再横向滚动；

## ADR-042 设计规范断言按「端」分离作用域，而不是一套口径管四端

- **状态**：✅ 已采纳
- **背景**：
  `StudyUiSpecAssertionTest` 是把《产品设计规范》§13 禁止项（F-01…F-25）与 §14 自检清单
  逐条落成源码级断言的套件。它原先把「学习端 / 家长端 / 管理端」当成**同一批文件**扫，
  于是 §11.2 新增管理端页面后，一次性炸出 16 条失败——但逐条核对后，
  里面大部分是**断言作用域错了**，不是代码错了：
  ① 「学习端不使用表格」「学习端不套管理端表单骨架」「学习端一屏一任务」是**学习端专项**，
     管理端恰恰**必须**用 `BasicTable`、**必须**用管理端表单骨架（§1.3 管理端适用第 3–9 章全部）；
  ② 「表格首列 ≤12 字」「不用 antd 栅格」等口径把 §6.2 明确允许的
     `a-row :gutter="16"` + `a-col :span="12|24"` 也一起禁了——§6.2 真正禁的是
     antd 响应式断点属性（`.ant-col` 被锁成 `width:100%`，断点自动分列根本不成立）；
  ③ 「家长端列表必须走 `StudyDataList`」与「家长端不许用 `BasicTable`」互相打架，
     而项目里**已上线的 3 个家长端页面**本来就走 `StudyDataList`——口径应当向既有实现看齐；
  ④ 「每个页面都要自己 import `net.ts`」在「薄配置页 + 共享内核」的管理端结构下不成立：
     发请求的是内核，断网提示与重试入口也渲染在内核里。
- **决策**：
  ① **断言按端分作用域**：`learningFiles()` / `learningPageFiles()` 显式排除
     `views/study/parent/`（家长端）与 `views/study/manage/`（管理端）；
     管理端单列，走它自己的口径（必须 `BasicTable`、表单必须 `horizontal`）。
  ② **每条断言改成「更精确」而不是「更宽松」**：
     - `f07` 拆成三段（家长端与学习端禁管理端骨架 / 学习端连 `BasicTable` 都禁 / 管理端必须 `BasicTable`）；
     - `f10` 只管学习端，另加「管理端表单不得写 `vertical`」；
     - `checklist09` 从「禁 `a-row`/`a-col`」改成「`gutter` 必须 16、列宽只能 12/24、禁 antd 断点属性」；
     - `checklist16` 从「只看字面量」改成「字面量必须在预设名集合内 + 动态色只允许出现在 `StudyEnumTag` +
       该组件的候选色板必须在集合内」；
     - `f14` 从「不得出现操作列字样」改成「出现操作列字样的文件必须引用 `StudyActionColumn`」。
  ③ **字面量扫描类断言先剥注释**（本仓既有纪律，`StudyInterfacePageTest` 已是这个口径）：
     `checklist19` 与 `copyHits` 统一剥注释再扫——注释里为了说明「这些字样不能出现」
     而引用的字样，不是用户看得见的文案。
  ④ **「逐页」判定范围扩到「页面 + 它直接 import 的本项目组件」**（`StudyOfflinePolicyTest`）：
     薄配置页把加载委托给共享内核时，断网提示与重试入口就在内核里，
     只扫页面文件会把「委托」误判成「没处理」。
  ⑤ **静态路由页面不进 `sys_permission` 菜单种子检查**（`StudyMaintainabilityTest#n09`）：
     判据是「该页面是否被 `src/router/**` 静态注册」，孩子端登录页按 ADR-039 走静态路由。
- **理由**：
  ① 断言是用来**卡住违规**的，不是用来卡住「不同端的不同做法」的——
     口径错了会逼着人把代码改成错的，或者把断言改成没有牙齿的；
  ② 「更精确」与「更宽松」必须分清：本次每一条放宽都换成了**另一条更细的约束**
     （禁断点属性、禁动态色、要求引用统一组件），净效果是约束变多而不是变少；
  ③ 「剥注释」在本仓已是既定纪律，不该有断言类各写各的。
- **影响**：
  ✅ 19 条既有失败断言逐条定性：9 条改生产侧、8 条改断言口径、2 条属其它测试类；
  ✅ 全量 `mvn test` 324 条全绿；
  ✅ 新口径做过**故障注入闭环**（注入 3 处 ⇒ 红 3/3 精确命中 ⇒ 还原 ⇒ 绿）。
- **复审触发条件**：
  ① 《产品设计规范》改版导致某一端的适用性变化 ⇒ 同步调整对应端的作用域；
  ② 新增一端（如「教师端」）⇒ 必须同时新增该端的作用域与口径，不许沿用别的端。

## ADR-043 菜单 `is_leaf` 语义按「子菜单」判定；可达性断言照抄后端遍历算法

- **状态**：✅ 已采纳
- **背景**：
  §11.2 浏览器实测（2026-11-03）抓到两个 P0 级缺陷：管理端「考点维护」与「考点版本历史」
  两个 `:code` 页面打开是**404 插画**——但**接口 200、控制台干净、菜单树 JSON 里 children 齐全**，
  没有任何一条报错能指向原因。
  根因在底座 `SysPermissionController#getPermissionJsonArray`：
  ```java
  // SysPermissionController.java:735 与 :759
  if (!permission.isLeaf()) {
      getPermissionJsonArray(jsonArray, metaList, json);
  }
  ```
  **只有 `is_leaf = 0` 的节点才会被递归下去**。父菜单被标成 `is_leaf = 1` 时，
  它的子菜单**被静默丢弃**——不是 404，是「这一支从来没出现在菜单树里」。
  第一版种子把两个 `:code` 菜单挂在「坐标树」下，而「坐标树」同时被写成 `is_leaf = 1` ⇒ 整支消失。
  对照证据：家长端「关联管理」正常，因为它挂在 `st_menu_parent`（`is_leaf = 0`）**平级**下。
- **决策**：
  ① **`is_leaf` 的语义是「有没有子菜单」**，判据只算**子菜单**（`menu_type IN (0,1)`），
     **不含按钮**（`menu_type = 2`）——上游里「只有按钮」的菜单 `is_leaf = 0`，
     因为后端要递归下去把按钮挂到 `meta.permissionList`。
     ⇒ 不变量是**单向**的：「**有子菜单 ⇒ `is_leaf` 必须为 0**」；
     「无子菜单 ⇒ `is_leaf` 必须为 1」**不成立**（有按钮的菜单就是反例）。
  ② **`:code` 动态路由菜单挂在**目录**菜单**（`st_menu_manage`）下，不挂在叶子菜单下——
     与家长端「关联管理」已跑通的写法一致。
  ③ **种子脚本按实际子节点重算 `is_leaf` 自愈**（§5 `UPDATE ... CASE WHEN COUNT(*) = 0 THEN 1 ELSE 0 END`），
     且 `ON DUPLICATE KEY UPDATE` **必须回写** `parent_id` / `is_leaf`——
     只写 `INSERT` 的话，改挂载层级**重跑脚本也救不回来**。
  ④ **可达性断言照抄后端遍历算法**：从 `parent_id` 为空的根出发，
     进入某节点后**只有 `is_leaf = 0` 才继续下探**，复算出可达集合，
     断言全部 `st_menu%` 节点可达。这比只查 `is_leaf` 字段本身更强——
     它能抓住任何「祖先被标成叶子导致整支被剪掉」的形态。
  ⑤ **断言只覆盖 `st_menu%`**，不去动上游数据：全库实测有 1 处上游同类违规
     （`平级模式`，上游 snowflake id），不在本项目管辖范围。
- **理由**：
  ① 「接口 200 + 控制台干净 + 页面 404」这种组合，静态扫描与接口探测**都抓不到**——
     只有真渲染才发现少了一支。这类缺陷必须靠**照抄后端算法复算**来兜；
  ② 断言要卡的是**可判定的不变量**，不是「所有字段都该是某个值」——
     单向不变量（`有子菜单 ⇒ is_leaf=0`）比双向约束更贴合真实语义，也不会误伤上游；
  ③ 种子脚本带自愈，意味着以后再加子菜单忘了改 `is_leaf`，**重跑脚本就能修回来**，
     不必再靠人肉发现。
- **影响**：
  ✅ 两个 `:code` 页从 404 插画恢复为真实页面（截图 A03 / A04）；
  ✅ 菜单树 DB 核对：9 个子菜单 `is_leaf` 全部为 0，根菜单 `st_menu_manage` / `st_menu_parent` /
     `st_menu_study` 均为 `is_leaf=0`；
  ✅ 新增 3 条 DB 支撑断言（`StudyMenuRenderRuleTest`，8/8 全绿）；
  ✅ 22 号种子脚本连跑两遍 `exit=0`（幂等）。
- **复审触发条件**：
  ① 上游改掉 `getPermissionJsonArray` 的遍历规则（如改成「有子节点就递归」）⇒
     同步改可达性断言的算法复刻；
  ② 底座新增一种会让 `is_leaf` 承担别的语义的场景 ⇒ 重新确认不变量方向。

## ADR-044 管理端列表内核统一补 `dataIndex`；操作列单一来源；加载用序号守卫丢弃过期响应

- **状态**：✅ 已采纳
- **背景**：
  同一轮浏览器实测抓到另一个 P0 级缺陷：**管理端 5 个列表页（A04/A05/A06/A07/A08）
  所有数据列渲染为空**，只有操作列的「查看」链接有内容。表格在、表头在、分页在，就是没有数据。
  根因在 antd 的取值约定：
  - antd 表格按 **`record[dataIndex]`** 取值；
  - 底座 `useColumns` 只处理 `key → dataIndex` 的**显示名**，
    **不会**把 `key` 当成取值字段；
  - 薄配置页为了少写代码，只写 `{key, title, width}` ⇒ 每格都是 `record[undefined]` ⇒ **整列空白**。
  连带两个问题：
  - **双操作列**：`tableColumns` 手工注入 `{key:'action'}` + BasicTable 的 `actionColumn` 又 push 一列，
    而 `handleActionColumn` 只按 `flag === ACTION_COLUMN_FLAG` 去重，手工注入的那列不带 flag，拦不住；
  - **「展开行」按钮凭空多出**：考点 VO 带 `children`，antd 以为这行可展开，
    而「考点版本历史」是**平铺**的版本列表，本来就没有子节点可言。
  同轮还抓到第四个缺陷（竞态类）：**「母题维护」页表格有 4 条数据，下方却挂着一行
  「请指定要访问的孩子」**。根因是内核的 `onMounted(reload)` **先于**页面自己的 `onMounted`
  （取孩子下拉）执行 ⇒ 发出一次必然 4010 的请求；该请求的 `catch` **晚于**第二次成功请求落地，
  而 `errorText` 在成功路径上**没被清** ⇒ 数据与错误提示并存。
- **决策**：
  ① **`dataIndex` 由内核统一兜底**：薄配置页只描述「内容列」（`{key,title,width}`），
     内核的 `tableColumns` 统一补 `dataIndex: item.dataIndex || item.key`。
     薄配置页**允许**显式写 `dataIndex`（覆盖用），但不写也能渲染。
  ② **操作列只由 BasicTable 的 `actionColumn` 提供一处**：内核删除手工注入的 `{key:'action'}`；
     薄配置页**不得**自己声明操作列。
  ③ **只读页不留空操作列**：`:show-action-column` 由 `hasActionColumn = Boolean(props.detailBuilder)`
     驱动——表头写着「操作」而格子里什么都没有，比没有这一列更让人以为功能坏了。
  ④ **加载用序号守卫**：`reload()` 维护 `reloadSeq`，每次请求取号，
     **只有最新一次请求能写状态**（过期响应直接 return）；成功路径必须 `errorText.value = ''`。
     薄配置页侧同时约束：**依赖尚未就绪的入参时直接返回空数组，不发必然失败的请求**。
  ⑤ **平铺列表要去掉 `children`**：把 VO 里的 `children` 映射为 `undefined`，
     避免 antd 凭空多出「展开行」按钮。
- **理由**：
  ① 9 个管理端内容维护页结构同构，共用一个内核——**取值约定必须收敛到内核**，
     否则每个薄配置页都要自己记得写 `dataIndex`，漏一处就整列空白，而且**没有任何报错**；
  ② 「操作列」在语义上属于**内容浏览与维护**层（R-04：不做公开比较、不提供批量处置入口），
     由内核统一提供才能保证每页口径一致；
  ③ 竞态的通用解法是**序号守卫**而不是「小心写 catch」——
     内核先于页面 `onMounted` 执行是**结构性的**，靠调用顺序规避必然复发；
  ④ 「数据格空白」这类指标**必须单独数**：操作列走 slot、与 `dataIndex` 无关，
     只看「操作列有没有链接」验不出整列空白。
- **影响**：
  ✅ A04/A05/A06/A07/A08 数据格空白全部归零（A05 从 180/180 空 → 0）；
  ✅ A04 不再有「展开行」按钮，也不再有空操作列；
