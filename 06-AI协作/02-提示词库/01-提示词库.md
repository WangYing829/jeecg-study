# 提示词库

> 可复用的任务提示词模板。**照抄结构，替换尖括号变量**。
> 每个模板都带「输入上下文 / 提示词正文 / 期望产出 / 自检点」四段——**自检点不要删**，那是 AI 自查的锚。

## 使用规约

| 规约 | 说明 |
|---|---|
| 先给上下文 | AI 不知道仓库里有什么。**每次都先给文件路径**，不要让它猜 |
| 给参照物 | 「照抄 `<path>:<line>` 的写法」比「按 JeecgBoot 规范写」有效得多 |
| 写死边界 | 「不做什么」必须写进提示词，否则 AI 会顺手扩范围 |
| 红线前置 | 涉及练习、判分、家长端的任务，**红线条款要写进提示词正文**，不能只靠链接 |
| 一次一任务 | 一条提示词对应一张任务卡（见 `../01-任务台账/03-任务卡模板.md`） |

## P-01 需求 → 任务卡拆分

**输入上下文**：`01-需求迭代/02-需求文档/01-产品需求说明书.html` · `06-AI协作/01-任务台账/01-任务台账总表.md`

```text
在 jeecg-study 项目中，把下列需求拆成可执行任务卡。

需求编号：<F-XXX-NN …>
阶段：<V0 地基 / V1 …>

要求：
1. 每张任务卡只做一件事，不跨模块。
2. 每张卡必须写明：需求编号、落点（后端包路径 / 前端目录 / SQL 脚本）、
   验收判据（可判定，不许写「正常显示」）、红线检查（触及 R-01…R-04 哪几条）。
3. 落点必须符合 ADR-014 的包结构口径（域优先）。
4. **不做**：不改需求编号体系、不写实现代码、不动已生成的 HTML。
5. 输出用 `../01-任务台账/03-任务卡模板.md` 的格式。

同时列出：这些任务依赖哪几条已知缺口（台账 §5.1）。
```

**期望产出**：一组任务卡 + 缺口依赖说明。
**自检点**：每卡都有需求编号、落点、≥1 条可判定判据、红线检查栏已填。

## P-02 新增后端接口

**输入上下文**：`02-代码开发/03-接口文档/01-接口设计说明书.html` · `06-AI协作/04-知识库/01-JeecgBoot底座速查.md`

```text
在 jeecg-study 实现接口：<METHOD /api/v1/study/...>

契约（来自《接口设计说明书》）：<粘贴该接口的请求/响应/错误码>

要求：
1. Controller 骨架照抄参照实现：
   `<JeecgBoot>/jeecg-boot/jeecg-boot-module/jeecg-module-monitor/src/main/java/org/jeecg/modules/monitor/alarm/controller/MonitorAlarmModelController.java:24-47`
   —— @Tag / @RestController / @RequestMapping，@Operation，@RequiresPermissions，
   分页用 pageNo/pageSize + QueryGenerator.initQueryWrapper + service.page，返回 Result.OK。
2. **路径风格按项目接口设计说明书**（REST），不要用 JeecgBoot 原生的 /add /edit /delete。
3. 包路径按 ADR-014（域优先）：org.jeecg.modules.study.<域>.controller|service|entity|mapper
4. **单库 `jeecg-study`，不要加 `@DS`**（ADR-015 已取消双数据源）；全仓不应出现 `@DS(`。
   数据范围隔离靠 `child_id` 条件，见第 5 条。
5. 事务边界在 Service；错题池/排期/掌握度的写入必须在同一事务内。
6. Controller 不写业务逻辑、不直接用 Mapper；Engine 是纯计算，不碰 DB。
7. **数据范围**：Service 层强制按 `child_id` 拼条件（家长用 `ChildScopeHelper` 求交集，孩子用 JWT 的 `childId`）；越权返 **4010**（不用 404）。
8. **不做**：不改需求编号、不新增表结构（表结构变更另走 P-05）、不引入第三方依赖。
```

**期望产出**：Controller + Service + Mapper + Entity/DTO/VO 代码，附接口自测说明。
**自检点**：分页参数名是 `pageNo`/`pageSize`；返回 `Result.OK(...)`；没有用 `PageResult`；`judge`/`engine` 包无 AI 依赖。

## P-03 新增前端页面

**输入上下文**：`01-需求迭代/03-设计规范/01-产品设计规范.html` · `02-代码开发/04-前端页面/01-前端页面清单.html`

```text
在 jeecg-study 实现前端页面：<页面名 / 路由>

要求：
1. **先读**《产品设计规范》（V1.1，数值均带上游 JeecgBoot v3.9.2 基座 file:line），
   配色、布局、组件尺寸间距、字体字号一律沿用既有值，
   不引入新色值、不自定义间距。
2. 学习端页面：独立全屏布局 layouts/study，不加载管理端顶栏与侧栏。
   管理端页面：用 useListPage + BasicTable（上游封装，不手写 a-table、不另做分页）。
   管理端表单沿用基座默认 layout="horizontal"；窄表单与学习端才用 vertical。
3. HTTP 调用统一 defHttp；API 函数集中放 src/api/study/study.ts。
4. 移动视口（390px）不得横向溢出；表格首列只放短标签，长描述放第二列
   或用可折行 span 包裹。
5. 涉及练习的页面：**答案区初始态不渲染到 DOM**（不是 display:none）。
6. 涉及家长端的页面：不出现 rank/percentile 字段，不出现「排名/超过…同学」文案。
7. **不做**：不引入 UI 库、不做暗色主题、不改全局主题变量。
```

**期望产出**：页面组件 + API 调用层 + 移动端自检说明。
**自检点**：设计规范每个数值都有出处；桌面 + 移动双视口都无横向溢出；答案区不在 DOM。

## P-04 写测试用例 / 红线断言

**输入上下文**：`03-测试验证/02-测试用例/01-测试用例.html` · `03-测试验证/04-自动化测试/01-红线断言规格.md`

```text
为需求 <F-XXX-NN> 编写测试用例。

要求：
1. 编号用 TC-{测试项}-{序号}，与《测试用例》现有编号不冲突。
2. 每条用例含：前置、编号步骤、预期结果、级别、追溯（至少一个需求编号）。
3. 预期结果必须**可判定**——不许写「正常显示」「运行正常」。
4. 若涉及红线，按《红线断言规格》给出对应的断言编号（R01-x / R02-x / R03-x / R04-x）
   和**可自动化的实现方式**（单测 / 集成 / 静态扫描 / 浏览器断言）。
5. P0 用例标注为发布否决项。
6. **不做**：不执行用例、不写缺陷单。
```

**期望产出**：用例表 + 红线断言映射。
**自检点**：每条都有追溯；红线断言编号齐全且能对应到规格表。

## P-05 SQL 变更

**输入上下文**：`02-代码开发/02-数据库/03-脚本/01-脚本约定.md` · `02-代码开发/02-数据库/01-数据库设计说明书.html`

```text
为 jeecg-study 编写 SQL 脚本。

变更内容：<表 / 索引 / 种子数据>

要求：
1. 落点：`02-代码开发/02-数据库/03-脚本/`。按类型选文件：
   - 建表 / 改表结构 → 02-schema.sql
   - 初始数据 → 03-init.sql
   - 增量修复 → 04-fix.sql（追加，不改历史）
2. **脚本必须幂等**：可重复执行不报错、不重复插数据。
3. 表前缀 study_；主键与索引遵循《数据库设计说明书》的命名规则。
4. 变更走增量脚本，**不改历史脚本**；DDL 的真源在本目录，不在文档里。
5. 写明：影响的表、是否需要数据迁移、是否影响追溯矩阵。
6. **不做**：不写删除数据的脚本、不修改已发布的脚本段。
```

**期望产出**：脚本片段 + 影响说明。
**自检点**：连跑两次结果一致；无 DROP TABLE；有 `IF NOT EXISTS` / `ON DUPLICATE KEY` 等幂等保护。

## P-06 代码评审

**输入上下文**：待评审的变更文件列表 + `06-AI协作/04-知识库/03-AI常见坑.md`

```text
评审以下变更：<文件列表>

按优先级输出问题，每条给出：文件:行号 → 问题 → 依据（引用哪条规约/红线/ADR）→ 建议改法。

必查清单：
1. 红线：答案是否落 DOM？判定是否依赖 AI？judge_source 是否可能写入 model？
   家长端是否出现排名/百分位？是否引入第三方统计 SDK？
2. 分层：Controller 是否写了业务逻辑？Engine 是否碰了 DB 或网络？
   事务边界是否在 Service？是否误加了已作废的 `@DS("study")`？
   数据范围是否按 `child_id` 强制过滤？越权是否返 4010 而不是 404？
3. 前端：是否符合《产品设计规范》？首列是否 nowrap 长文本？移动端 390px 是否溢出？
4. 安全：密钥是否入库？是否新增了未登记的第三方依赖？
5. 追溯：本次变更涉及的接口/用例是否需要重跑追溯矩阵？

只报真问题，不要为了凑数报风格问题；每条都要能定位到行。
```

**期望产出**：按严重度排序的问题清单。
**自检点**：每条有行号、有依据出处、没有「建议加强测试」这类空话。

## P-07 排查问题

```text
现象：<可复现描述>
期望：<应该怎样>
实际：<实际怎样>
相关文件：<路径>

排查要求：
1. 先给出**最可能的 2 个原因**，各附一条验证方法（具体命令或读哪个文件哪一行）。
2. 不要猜测性改代码——先验证再改。
3. 若根因在本项目已知坑清单里，指明是哪一条（`../04-知识库/03-AI常见坑.md`）。
4. 若涉及 PowerShell 脚本：注意无 BOM 的 .ps1 按 GBK 解码会吞换行符。
5. 修复后给出回归验证方式。
```

**期望产出**：假设 + 验证方法 → 根因 → 修复 → 回归方式。

## P-08 产出文档（Markdown 源稿 → HTML）

```text
为 jeecg-study 产出一份《<文档名>》。

要求：
1. 产出 **Markdown 源稿**放在对应阶段目录，文件名 YYYYMMDDNN-<业务名>.md，
   序号项目内全局唯一。
2. 源稿开头必须有 <!--META {json} --> 块，sections 数组的 id/数量/顺序
   与正文二级标题严格一致。
3. 生成命令：
   python .\05-公共资源\2026103001-报告生成器.py <源稿.md> <输出.html>
   输出文件名用 NN-<业务名>.html 放进对应目录。
4. 生成后跑静态校验（2026103013），必须 ALL PASS。
5. 表格必须有表头；移动端表格卡片化依赖 thead 取列名。
6. **不做**：不手改生成的 HTML；不改需求编号体系。
```

**期望产出**：源稿 + 产物 + 校验通过。
**自检点**：`ALL PASS`；sections 与 `##` 数量一致；无 BOM；章节数 = 导航项数。
