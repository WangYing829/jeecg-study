# AI 常见坑

> 本项目里 **AI 编码最容易踩的坑**。每条都写明「现象 → 根因 → 正确做法」。
> 踩到新坑就往这里加，格式一致；**加之前先搜是否已有同类条目**。

---

## A 红线类（踩了就是发布否决）

### A-01 用 `display:none` 藏答案 —— 直接违反 R-01

- **现象**：练习页用 `v-show` / `display:none` 把答案区藏起来，等孩子答完再显示。
- **根因**：AI 默认「隐藏即可防剧透」，但**DOM 里已经有答案**——孩子按 F12、读 HTML、或者 AI 自己的校验脚本一查就穿帮。
- **正确做法**：**答案区初始态根本不渲染到 DOM**（`v-if` 控制，或答案从独立接口在作答后才取）。判定标准见 `03-测试验证/04-自动化测试/01-红线断言规格.md` R01-3、R01-5。
- **依据**：《系统设计说明书》ADR-009 / 红线 R-01。

### A-02 让 AI 直接判对错 —— 违反 R-02

- **现象**：Controller 里出现 `if (model.chat(prompt).contains("正确"))` 这类写法；或者 `judge_source` 允许写成 `model`。
- **根因**：AI 天然倾向「用模型做判断最省事」，而本项目**明令 AI 只做解释层**。
- **正确做法**：判定走**确定性规则**（可验算）；`judge_source` 在**类型层面**只允许 `rule` / `rule+model`，不允许 `model` 单独取值（ADR-008）。`rule` / `engine.judge` 包**不允许**引入 AI 客户端依赖，用 ArchUnit 断言把红线变成编译期事实。
- **依据**：《系统设计说明书》ADR-007/008、红线 R-02。

### A-03 让模型生成变式答案再拿去判分

- **现象**：`variant.answer = model.generate(...)`，然后判分也用模型。
- **根因**：变式生成被理解成「让模型出题」。
- **正确做法**：变式生成是**结构化模板变换（规则）**，答案恒可验算；模型只做自然语言润色（ADR-007）。

### A-04 家长端出现排名 / 百分位

- **现象**：响应里加了 `rank`、`percentile`、`vsPeers`；文案出现「超过 78% 的同学」。
- **根因**：AI 默认「家长端要有对比才有价值」。
- **正确做法**：家长端只看**客观趋势与状态**。数据库不建排名字段，响应不返回排名数值，文案全局不出现「排名 / 排行 / 超过…同学 / 百分位」（红线 R-04，断言 R04-1…3）。

## B 工程类

### B-01 动了需求编号但不同步追溯矩阵

- **现象**：新增需求 `F-WRD-08`，接口和用例都做了，但 `02-追溯矩阵.csv` 没重跑。
- **根因**：矩阵是脚本生成的，手改会被下次生成覆盖；而**不重跑就没人知道覆盖情况变了**。
- **正确做法**：改完 PRD / 接口 / 用例，**重跑 `2026103015-追溯矩阵生成.py`**，再看 `2026103016-红线断言检查.py` 是否还绿。

### B-02 手改已生成的 HTML

- **现象**：直接编辑 `01-产品需求说明书.html` 里的表格内容。
- **根因**：HTML 是生成产物，下次重新生成就被覆盖，白干。
- **正确做法**：改 **Markdown 源稿** → 重新生成 → 跑静态校验。

### B-03 「未覆盖 = 不需要实现」

- **现象**：追溯矩阵里某需求显示 `未覆盖`，AI 就跳过了。
- **根因**：把追溯状态当成「需求优先级」。
- **正确做法**：`未覆盖` 是**待判读信号**，不是豁免。豁免必须登记在 `06-AI协作/01-任务台账/01-任务台账总表.md` §5.2 并写明理由。当前已登记 5 条豁免（E-01…E-05）。

### B-04 漏建「被引用但未定义」的需求编号

- **现象**：PRD 正文引用了 `F-BASE-06`，但需求表里没有这一行。
- **根因**：AI 写 PRD 时容易在正文引用新编号却忘了在表里登记。
- **正确做法**：每个新编号必须**同时**出现在：需求表、接口表需求列、用例追溯列。当前有 3 条此类缺口（G-01…G-03），已登记待补。

### B-05 分层越界

- **现象**：Controller 里写业务逻辑、直接注入 Mapper；Engine 里访问数据库。
- **根因**：AI 为了「少写几个类」会把逻辑上提。
- **正确做法**：按《系统设计说明书》§4.2 的分层职责表——Controller 只做参数校验 + 鉴权 + DTO↔VO；Service 负责业务编排与**事务边界**；Engine 是纯计算，**不碰 DB、不碰网络**。

### B-06 事务边界放错层

- **现象**：在 Mapper 方法上加 `@Transactional`，或在 Controller 上加。
- **根因**：AI 随手加注解。
- **正确做法**：事务边界在 **Service**。错题池、排期、掌握度三者的写入**必须在同一事务内**（N-04）；排期写入失败则整笔回滚。

### B-07 多数据源 `@DS` 位置不对（**V1.1 已不适用，但保留作反面教材**）

- **现象**：`@DS("study")` 加在 Mapper 接口上，事务却加在 Service 上。
- **根因**：dynamic-datasource 的数据源切换与 Spring 事务绑定有先后关系，位置错了事务可能绑到旧数据源。
- **正确做法**：**本项目已改单库 `jeecg-study`（ADR-015），全仓不应出现任何 `@DS(`**。若将来要拆库，`@DS(...)` 只能加在 **Service 实现类的方法**上，不能加在 Mapper 上；并须先做最小验证。详见 `06-AI协作/04-知识库/01-JeecgBoot底座速查.md` §3.3。

> ⚠️ **AI 很容易凭「JeecgBoot 教程里的双数据源写法」自动加 `@DS`**——写码前先确认当前口径是**单库**。

### B-08 密钥入库

- **现象**：把数据库口令写进 `application-dev.yml` 并准备提交。
- **根因**：AI 不知道本项目「口令不入库」的约定。
- **正确做法**：本地口令写 `application-dev.yml`（该文件 gitignore），生产走环境变量。`.gitignore` 已就位。

## C 文档与交付类

### C-01 表格首列撑破桌面视口

- **现象**：桌面视口横向溢出，但**移动端一切正常**。
- **根因**：模板 `td:first-child { white-space: nowrap }` + 首列放长句。**移动端媒体查询会把首列改回 `white-space: normal`**，所以只测移动端永远发现不了。
- **正确做法**：首列只放短标签；长描述放第二列或用可折行 `span` 包裹。**探针必须同时跑桌面与移动视口。**

### C-02 `<style>` 顶层裸写 CSS 变量

- **现象**：某组颜色整体失效（背景变透明、边框变黑），但**不报错**。
- **根因**：`--blue:#2563eb;` 写在 `<style>` 顶层（不在任何选择器内），浏览器**直接忽略整条声明**。
- **正确做法**：整组变量必须包在 `:root { ... }` 里。静态校验脚本已加这条检查。

### C-03 代码块撑破页面

- **现象**：SQL / YAML 代码块把页面撑出横向滚动条。
- **根因**：Markdown 围栏代码块输出 `<pre><code>`，拿不到模板 `pre.cmd` 的 `overflow-x:auto`。
- **正确做法**：生成后正则把 `<pre>` 换成 `<pre class="cmd">`；`code` 加 `overflow-wrap:anywhere`，但 `pre.cmd code` 保持 `white-space:pre`。

### C-04 用无头 Edge 做浏览器验证

- **现象**：截图拍出来是 Edge 新标签页（MSN 壁纸）或隐私弹窗；`--dump-dom` 输出 0 字节却不报错。
- **根因**：本机 20+ 个 msedge 进程常驻，headless 导航被**交给已运行的实例**。
- **正确做法**：用**内置 Browser + iframe 校验台**（390px / 1280px）。DOM 真值必须加 `--user-data-dir=<临时目录>` 启独立实例。

### C-05 以为「滚动没生效」就判失败

- **现象**：内置 Browser 的 `scroll` action 报 `NO_SCROLL_EFFECT`。
- **根因**：smooth 动画的读数假象，**滚动实际生效**。
- **正确做法**：以 `inspect` 返回的 `scrollPosition` 为准，不要据此判定失败。

### C-06 无头下测 CSS 过渡 = 假读数

- **现象**：`class` 已加 `show`，但 computed `opacity` 恒为 0、`transform` 停在起点。
- **根因**：无头环境**不跑动画时钟**；`pointer-events` 不可过渡所以立即生效，于是出现「class 变了、样式没变」的分裂现象。
- **正确做法**：验证副本里注入 `*{transition:none !important}` 再读 computed style（**不要污染交付文件**）。快速判据：**`pointer-events` 变了而 `opacity` 没变 → 几乎一定是测量环境问题，不是样式写错。**

### C-07 目录存在但空 = 看不见

- **现象**：建了 `05-源码/` 下只有 README 的空目录，以为「骨架已就位」。
- **根因**：空目录在 git 里不存在，CI / 克隆后就没了。
- **正确做法**：每个占位目录里放一份 `README.md` 说明**这里将来放什么、对应哪个设计文档的哪一节**——这正是本仓库 `02-代码开发/05-源码/` 的做法。

## D 合流与工具链类（2026-10-31 V0–V4 合流新增）

### D-01 `@MockBean` 一个接口，把**唯一实现它的 Bean** 整体顶掉

- **现象**：某个测试类加了 `@MockBean private StudyErrorPoolService errorPoolService;` 之后，**整个 Spring 上下文起不来**（`No qualifying bean of type '...StudyErrorManageService'`），连没写 mock 的测试类也一起挂；210 条用例里 82 条失败。
- **根因**：`StudyErrorPoolServiceImpl` 同时实现 `StudyErrorPoolService` 与 `StudyErrorManageService`，是这两个契约**唯一**的 Bean。Spring 的 `@MockBean` 按**类型**替换，mock 接口时这个 Bean 被换成「只实现该接口」的替身 → 另一个契约无人实现 → 依赖它的 Controller 构造器注入断链。
- **正确做法**：一个类实现多个 Service 契约时，测试**必须 mock 具体实现类**（`@MockBean StudyErrorPoolServiceImpl`）——替身是具体类的子类，天然同时实现两个接口。治本的「拆成两个独立 Bean」在本项目走不通：委托方若依赖被 mock 的接口会拿到 mock 替身，若依赖具体类则会在 mock 替换时被摘掉。见 ADR-029。
- **通用判据**：看到「某个类 `implements` 了两个以上 service 接口」，就先查全仓有没有人 `@MockBean` 其中一个接口。

### D-02 扫描型断言用**绝对路径**判范围 → 仓库名带关键字时全仓误判

- **现象**：红线断言报上游 `chartdemo/index.vue`（「销售额排行」）、`dashboard/Analysis/*`（文件名含 analysis）违规——这些是 JeecgBoot 基座自带的 demo 页，**本项目一行没改**。
- **根因**：判据写成 `path.contains("study")`，而**仓库路径本身就叫 `20261030-jeecg-study`** → 上游几百个页面全被当成学习端扫。
- **正确做法**：范围判断一律用**相对项目根的路径**（`root.relativize(file)`），并显式列出本项目管辖的目录白名单；上游基座不纳入本产品红线范围（ADR-028）。
- **同类坑**：断言「扫到 N 处违规」时，若扫描集合本身是空的，会**空通过**（假绿）。必须配一条「集合非空」的前置断言。

### D-03 正则灾难性回溯：一条断言打挂整套件

- **现象**：红线套件偶发 `StackOverflowError`，栈里全是 `Pattern$GroupHead.match` / `Pattern$Loop.match` 递归。
- **根因**：`"(?:[^"\\]|\\.)*"` 这类「贪婪 + 交替」写法，在大文件（825KB 的 `canvas-editor.js`）上回溯量指数级增长。
- **正确做法**：字符串提取改**占有量词** `"(?:[^"\\]++|\\.)*+"`；模板文本提取改**懒惰量词** `">([^<>{}]*?[\u4e00-\u9fa5][^<>{}]*?)<"`（贪婪的前半段会吞掉目标字符，懒惰才等价）。见 ADR-028。

### D-04 依赖 `Paths.get("")` 的测试，换个启动目录就失真

- **现象**：源码扫描类断言（红线 / UI 规范）大批失败，或反过来**全部空通过**。
- **根因**：`moduleDir() = Paths.get("").toAbsolutePath()` = **当前工作目录**。私有运行器从仓库根启动 → `moduleDir()/target/classes`、`moduleDir()/src/main/java/...` 全都不存在 → 扫描集合为空。
- **正确做法**：运行器在拉起 JVM 前 `Push-Location` 到模块目录；再给扫描器加一个 `-Dstudy.classes.dir` 覆盖，让它能指向本次编译产物而不是陈旧的 `target/classes`。

### D-05 私有编译目录复用 → 陈旧 class 被 Spring 扫到

- **现象**：排除某个域编译后跑测试，Spring 报「找不到某个 Service 的 Bean」，而那个域的源码根本没参与本次编译。
- **根因**：私有输出目录**复用**，上次编译进去的 class 还在；Spring 组件扫描按 `classpath*:` 枚举**所有**副本，于是扫到了半成品。
- **正确做法**：每次编译用**独立的时间戳目录**，不复用（Windows 的 `rm --` 需要回收标记，临时目录删不掉，新建目录比清空目录可靠）。

### D-06 javac 的 `@argfile` 编码跟随 `file.encoding`

- **现象**：argfile 写 GBK、命令行加 `-J-Dfile.encoding=UTF-8` → `MalformedInputException`；或者中文路径全变乱码 → `错误: 找不到源文件`。
- **根因**：javac 用 `Charset.defaultCharset()` 读 `@argfile`，而它由 `file.encoding` 决定；`-J` 参数若写进 argfile 内部，javac 会用 UTF-8 重读 argfile（里面的路径还是 GBK 字节）。
- **正确做法**：两边**统一**：argfile 写成 **UTF-8 无 BOM**，`-J-Dfile.encoding=UTF-8` 放**命令行**（不放 argfile）；同时 `[Console]::OutputEncoding = [Text.Encoding]::UTF8`，否则 javac 的 UTF-8 字节又被 PowerShell 按 GBK 读成乱码。
- **配套**：PS 5.1 下 `$ErrorActionPreference='Stop'` 会把 native 命令的 stderr 升格成终止性错误，**javac 的真实报错反而看不到** → 调用 native 命令前临时降级为 `'Continue'`。

### D-07 PowerShell 函数参数声明成 `[string[]]`，FileInfo 被降级后 `.FullName` 变 null

- **现象**：传给 javac 的源文件列表全变成空行 → `错误: 无源文件`。
- **根因**：函数签名写 `[string[]]$Files`，FileInfo 被强制转成字符串，之后 `$f.FullName` 取到 **null**（字符串没有这个属性）。
- **正确做法**：这类参数声明成 `[object[]]`，或直接用 `$f` 本身。

### D-08 测试只删孩子、不删行为表 → 库里攒孤儿行

- **现象**：跑完一轮测试，`study_review_schedule` 里多出几十行，而 `study_child` 是 0 行；反复跑会越攒越多。
- **根因**：测试清理只按「昵称以 UT 开头」删 `study_child`，但 `study_review_schedule` / `study_error_pool` / `study_writing` / `study_eye_usage` / 练习记录分区表都挂 `child_id`，没跟着删。
- **正确做法**：清理要**先删行为表、再删孩子**（行为表的删除条件依赖孩子还在）；分区表要按 `information_schema` 查实际存在的分区名逐个清。**残留数据本身就是缺陷信号**——每轮跑完顺手核一遍关键表的行数。

### D-09 `.ps1` 含中文路径必须存成 **UTF-8 带 BOM**

- **现象**：`Set-Location` 报「路径不存在」，路径显示成 `02-浠ｇ爜寮€鍙慭…`。
- **根因**：PowerShell 5.1 读**无 BOM** 的 `.ps1` 会按系统 ANSI（中文 Windows = GBK）解码，文件里的 UTF-8 中文路径全乱。
- **正确做法**：`.ps1` 一律 UTF-8 带 BOM。`write` 工具写的是无 BOM，得手工补：
  ```powershell
  $txt=[IO.File]::ReadAllText($p,[Text.Encoding]::UTF8)
  [IO.File]::WriteAllText($p,$txt,(New-Object Text.UTF8Encoding($true)))
  ```
- **注意**：`.html` / `.css` / `.js` 用 `[IO.File]::ReadAllText(path, UTF8)` 显式读取时不受影响；只有被 **PowerShell 自己解析**的 `.ps1` 有这个坑。

### D-10 前端、后端、文档三方的契约要**一处为准**

- **现象**：家长反馈端点三处不一致——前端打 `/parent/feedback`、后端实现 `/writing/parent/feedback`、设计文档写 `/writing/feedback`；页面功能端到端不通，但**所有自动化用例都绿**（因为没人测这条链路）。
- **根因**：多 Worker 并行时，各自按自己读到的文档版本实现；文档本身又是历史版本。
- **正确做法**：合流时**逐条比对「前端调用路径 ↔ 后端映射路径 ↔ 接口文档总表」**三列，差一个就当场定死并写进 ADR；接口文档的「需求」列要跟着一起改，否则追溯矩阵会把这块判成「零引用缺口」。

### D-11 排序并列 = flaky 用例的常见根因，别去改测试迁就

- **现象**：`mvn test` 上一轮全绿、这一轮同一条用例红了，报 `expected: "UTU1" but was: "UTU2"`——两条记录的排序值**并列**。重跑又绿了。
- **根因**：`ORDER BY MIN(unit_order)` 这类**聚合排序**没有唯一兜底键。UTU1 与 UTU2 的 `MIN(unit_order)` 都是 1，谁排在前面由**执行计划**决定 → 数据没变、结果变了。
- **同类写法**（本项目一次查出 26 处）：
  - `GROUP BY` 后**完全不写** `ORDER BY` —— 家长端日序列趋势图的横轴顺序会漂；
  - `ORDER BY cnt DESC LIMIT n` 的 TOP-N —— **并列时截断哪几条不确定**；
  - `ORDER BY create_time DESC LIMIT 1` 的「最近一条」 —— 同一秒的多行不可判定；
  - `LIMIT 5` 不排序 —— 等于随机丢数据。
- **正确做法**：
  1. **排序键末位必须是唯一列**（落在该表唯一索引上，或主键 `id`）。`ORDER BY MIN(unit_order), unit_code`、`ORDER BY cnt DESC, knowledge_point_code`、`ORDER BY create_time DESC, id DESC`。
  2. **唯一性判定要查真实库**，别凭印象：```sql
     SELECT TABLE_NAME, INDEX_NAME, GROUP_CONCAT(COLUMN_NAME ORDER BY SEQ_IN_INDEX)
     FROM information_schema.STATISTICS WHERE TABLE_SCHEMA='库名' AND NON_UNIQUE=0
     GROUP BY TABLE_NAME, INDEX_NAME;
     ```
     注意**组合唯一索引**（如 `(family_id,user_id)`）和**分区表**（`study_practice_record_yyyyMM`）。
  3. 把规则落成**可执行断言**，否则下一批 SQL 又会漏。本项目是 `StudySqlOrderDeterminismTest`（SQL-A：`GROUP BY` 必须有序 / SQL-B：截断必须有序 / SQL-C：`LIMIT 1` 末位键必须唯一）。
- **判断口诀**：**用例偶发红，先怀疑排序并列**，而不是先怀疑测试写得不对。改测试让它「稳定地红」是掩盖，不是修复。

## E 前端 Vue 3 与浏览器取证类（2026-10-31 末轮 P2 取证新增）

### E-01 `provide/inject` 方向反了：布局是页面的**子**组件

- **现象**：页面里 `inject()` 拿不到布局 `provide()` 的值，`inject` 返回 `undefined`，页面表现为「数据为空」且**不报错**。
- **根因**：`layouts/study/index.vue` 是布局组件，而页面模板里写的是 `<StudyLayout>` —— 布局是页面的**子**组件。Vue 的 `provide/inject` 是「**父 provide → 子 inject**」，页面作为父级根本 inject 不到子级提供的值。
- **正确做法**：跨组件传**会话级**状态不要用 provide/inject，改用**模块级共享单例**（ADR-032）。provide/inject 只适合「祖先 → 任意后代」的场景。
- **通用判据**：写 `inject` 前先画组件树，确认 provider 在**祖先**位置，不在**子孙**位置。

### E-02 模板 ref 拿到的是**深层 reactive 代理**，嵌套 ref 会被自动解包

- **现象**：`const eye = layoutRef.value; eye.eyeIntervalMin.value` 恒为 `undefined`，但 `eye.eyeIntervalMin` 本身有值；`undefined?.value` 静默通过，页面表现为「取不到数据」而不是报错。
- **根因**：模板 ref 赋值的是**深层响应式代理**（`reactive`），Vue 会把代理对象里的嵌套 ref **自动解包**。`setup` 返回对象的**顶层** ref 也会解包，但**嵌套普通对象属性里的 ref 不会**——同一个 ref 在两种位置表现不同，极难凭直觉判断。
- **正确做法**：不要用「模板 ref + defineExpose」传状态对象。状态统一放**模块级单例**（ADR-032）；非要传就用 `shallowRef` / `toRaw` 并显式写明解包预期。
- **配套**：Vue 3 **只解包 setup 返回对象的顶层 ref** —— 嵌套普通对象属性拿到的是 `Ref` 实例本身。

### E-03 状态工厂里注册生命周期钩子 → 钩子绑到**第一个调用者**

- **现象**：用眼时长在首屏正常累计，**路由切页后静默停摆**，控制台无任何报错。
- **根因**：`useXxx()` 这类状态工厂内部写了 `onMounted(() => start())`。Vue 的 `onMounted` 绑定的是**「当前正在 setup 的组件实例」**——也就是**第一个调用这个工厂的组件**。换路由后调用者变了，钩子归属就错位。
- **正确做法**：**工厂只造状态，不注册钩子**；谁负责生命周期由**明确的宿主组件**决定（学习端布局持 `onMounted`/`onBeforeUnmount`）。
- **固化**：`StudyEyeSharedStateTest` 会扫描状态模块里有没有 `onMounted`/`onBeforeUnmount`，有就红。

### E-04 上游默认布局在窄屏把侧栏渲染成**常开抽屉 + 遮罩**

- **现象**：家长端页面在 390px / 768px 下被**整个盖住**，抽屉压住内容、遮罩压灰整页 → 页面直接不可用；而桌面 1440px 完全正常。
- **根因**：上游 `layouts/default/sider/index.vue:2-12` 在 `<992px` 时渲染 `<Drawer :open="!getCollapsed">`（**常开**）并带遮罩。而本项目家长端菜单独挂在 `layouts/default`（上游 `transformObjToRoute` 对 DB 菜单**一律挂 LAYOUT**，动态菜单**永远无法用自定义布局**）。
- **正确做法**：**不改上游**。在本项目目录里用**全屏固定层**盖掉管理端外壳（`position: fixed; inset: 0; z-index: 1100`），并**自带导航与登出**（盖掉管理端顶栏后必须补偿）。见 ADR-033。
- **通用判据**：上游框架的响应式断点行为要**实测**而不是读文档猜；`@media` 命中后的 DOM 结构可能与桌面完全不同。

### E-05 Vite dev server 会把**任意浏览器口径导航**改写成 `index.html`

- **现象**：在 dev server 上用浏览器直接访问 `/study-parent/report` 这类路径，拿到的是首页而不是目标页；用 iframe 同源测量也因此失真。
- **根因**：Vite 的 `historyApiFallback` 会把未知路径回落到 `index.html`。
- **正确做法**：取证要**同源**（iframe 内文档的 `scrollWidth` 只有同源才能读到），但**不能**走 dev server。自建一个**静态服务 + 反向代理**（把 `/jeecgboot` 前缀转给后端）做同源取证——本项目用 8765 端口的 Node 服务，同时托管 `probe.html` 与反代 API。
- **配套**：前端 axios `baseURL` 用**相对路径**（`VITE_GLOB_API_URL=/jeecgboot`）时同源无 CORS；认证头是 **`X-Access-Token`**，不是 `Authorization: Bearer`。

### E-06 字面量扫描类断言**必须先剥注释**，否则假绿

- **现象**：新加的断言**第一次跑就绿**，但把生产代码改成明显违规（如 `position: fixed` → `relative`）后断言**仍然是绿**。
- **根因**：断言用「源码里是否包含某字面量」判断，而**注释里也包含这个字面量**——注释写「不使用 `position: fixed`」也算命中。
- **正确做法**：判定前**先剥掉注释**（`//`、`/* */`、HTML 注释）再扫。这条规则与既有 `StudyUiSpecAssertionTest` 一致，**新写断言必须照做**。
- **反向教训**：注释里为了「解释清楚」而写出禁用字面量，反而会让断言失去约束力。

### E-07 字面量扫描会**误伤 CSS 属性名**

- **现象**：`tc08_21_noHardcodedLightColor` 报「出现硬编码亮色 `white`」，但代码里根本没有白色色值。
- **根因**：扫描 `white` 字面量，而 CSS 属性 **`white-space`** 里就含 `white`。
- **正确做法**：扫描**色值**要用带上下文的正则（如 `:\s*white\b`、`#fff`、`rgb(...)`），不要裸扫词；或先剥离 CSS 属性名。
- **同类**：`overflow-x: auto` 扫描会误伤**注释里**的同名文字（见 E-06）；间距刻度断言只允许 `0/4/8/10/12/16/24/32px`，`6px` 会红。

### E-08 浏览器取证台（`probe.html`）的三个硬约束

- **为什么需要它**：跨源 iframe 读不到 `scrollWidth`（同源策略），所以必须同源；同源又不能走 Vite dev server（E-05）→ 自建服务。
- **拼版用 CSS Grid 不用 flex**：flex-wrap 的换行判定按「单元宽度 + gap」算，**差 1px 就整列掉下来**（实测 1440×0.43 两列差 1px → 被迫单列）。Grid 的 `repeat(cols, max-content)` 稳定。
- **标题条要独占高度**：标题条若绝对定位压在 iframe 上，会**遮住页面自己的顶栏**（家长端切换条 / 学习端 48px 顶栏）→ 取证就缺证据。做法：`CAP_H = 18` 预留独立高度，iframe `top: CAP_H`。
- **裁剪区按 cell 紧算**：`#stage` 在流内是满宽的，用 stage 的块宽会把右侧空白也圈进截图 → 外部 `clip` 要按 `.cell` 的最大 `right/bottom` 算。
- **量完即拆 iframe**：同一页堆几十个 iframe 会把渲染进程拖垮；`measure` 模式每量完一页就 `row.remove()`。
- **截图尺寸上限**：Browser `scope:clip` 超出视口高度会被裁到视口（实测 1265×720），所以拼版必须 **≤ 视口高度**。

### E-09 `always_show=1` 让 Vue3 菜单节点**渲染成叶子** → 下级菜单一个都不显示

- **现象**：管理端侧边栏里「学习助手」「家长端」两个一级菜单**看得见**，但点开是空的——7 个 / 3 个下级菜单**一个都没渲染**。接口层看菜单树却有子节点。
- **根因**：`src/components/Menu/src/components/BasicSubMenuItem.vue:41-48` 的 `menuHasChildren()` 末项是 `&& checkChildrenHidden(menuTreeItem)`；而 `src/utils/common/compUtils.ts:389-399` 的 `checkChildrenHidden()` **第一句**就是 `if (alwaysShow) { return false; }` ⇒ **`alwaysShow` 为真时 `menuHasChildren` 恒为 false**，节点被当叶子渲染。
- **`always_show` 的真实语义**：不是「强制显示子菜单」，而是「**没有**子菜单时也别塌成一个入口」。它与「children 展开」在 Vue3 菜单渲染里**互斥**。
- **正确做法**：**有可见下级菜单的节点一律 `always_show=0`**。上游 12 个一级菜单（主页 / AI应用平台 / 低代码开发 / 数据可视化 / 系统管理 / 我的租户 / 系统监控 / 消息中心 / 统计报表 / 组件示例 / 导航示例 / 关于）的 `always_show` **全部是 0**——与上游对齐就不会错。
- **排查口径**：先查上游同构菜单的 `always_show` 分布（全 0 vs 自己有 1），**比读代码更快定位**。

### E-10 菜单图标「数据库里有」≠「渲染得出来」——三段链路任一段断掉都是空心圆点

- **现象**：所有菜单图标都是空心圆点（`<span class="iconify">`，样式 `border-radius:100%`）。
- **根因（实测三段）**：
  1. **环境变量**：`VITE_GLOB_ICONIFY_USE_TYPE=online` 时图标走 `api.iconify.design` **在线**拉取；内网不通 → `renderSVG()` 返回 null → 退化成占位符。DB 侧 92 个图标值**全有**，别先查 DB。
  2. **离线图标集只扫源码**：`vite-plugin-purge-icons` 按 `content` 配置**扫源码文本**（html/pug/vue/js/ts），**只存在于数据库、源码里从没出现过的图标名不会被收集** → 离线模式照样空圆点。
  3. **上游图标名失效**：上游 `about` 菜单写 `simple-icons:about-dot-me`，iconify 现名是 `aboutdotme`（simple-icons v10 起去掉连字符）→ **online / local 两种模式都取不到**。
- **正确做法**：① 各环境统一 `local`；② 建**数据库菜单图标白名单**（纯数据清单、不 import，数组元素本身就是 purge 的收集点）；③ 失效名**数据库与上游源码两边同时改**（只改一边都不行）；④ 断言「DB 每个菜单图标 ⊆ 可收集集合」。
- **运行时取证**：dev server 上真实产物在 **`/@id/@purge-icons/generated`**（不是 `/@id/__x00__@purge-icons/generated`，后者命中 SPA index.html 回退）；模块体是 `const collections = JSON.parse('...')`，按 `prefix` + 图标名分组。

### E-11 JeecgBoot 的 **admin 没有「兜底全量菜单」**

- **现象**：admin 登录后侧边栏看不到新加的业务菜单，但 kid / parent 角色能看到。
- **根因**：`SysPermissionServiceImpl.queryByUser(userId)` **纯按** `sys_user_role → sys_role_permission → sys_permission` 取菜单。**admin 角色没有特判**——不是「admin 自动可见一切」，而是「admin 看得见的 = 显式授给 admin 的」。
- **正确做法**：**在数据侧授权**（增量脚本 `INSERT … SELECT … WHERE NOT EXISTS`，主键用 `CONCAT(前缀, LEFT(MD5(...),16))` 保证幂等），**不要**在代码侧给 admin 开后门。
- **配套**：admin 想在家长端页面上看到**真实数据**，还得把它挂进某个**演示家庭**（`study_family_member` + `study_parent_child_rel`）；但这**不等于**放开跨孩子访问——隔离语义（越权 4010）必须保持不变。

### E-12 断言 SQL 里**写死月份表名** = 跨月当天必炸的时间炸弹

- **现象**：昨天全绿的回归，今天早上挂在一条 `NullPointerException: Cannot invoke "Map.get" because "row" is null`——但断言逻辑一行没改。
- **根因**：生产侧按**服务端时钟**拼分表名（`study_practice_record_` + `YearMonth.now()`），而断言里写死了 `study_practice_record_202610`。**跨月当天**记录落进 `..._202611`，写死的表查不到行 → `queryOne` 返回 null → NPE。
- **正确做法**：断言**不要写死月份**。两种写法：
  - 用库里**真实存在的分表清单**逐个查（支持类已有 `practiceRecordTables()`，用的是 `information_schema.TABLES` + `LIKE 'study_practice_record%'`）；
  - 或与生产**同一套**拼表名表达式（测试文件里本来就有 `recordTable()` 辅助方法，只是这条断言没用它）。
- **通用判据**：**凡是随时间变化的资源**（月份分表、日期区间、季节性配置），断言里**一律不许写死具体值**；要么从环境推导，要么从库里枚举。
- **同类雷区**：种子脚本按当月建表（`05-partition.sql` 用 `NOW()` 动态拼表名）本身是对的，但**每月要跑一次**——运维清单里必须有这一条，否则下个月线上插入直接报表不存在。

### E-13 清理目录前先分清**四类**，别把「同名」当「同源」

- **四类**：**源码**（不可删）/ **构建产物**（可重建）/ **依赖**（可重装）/ **运行时释放物**（自愈）。
- **运行时释放物的判据**：**同源副本在 classpath / 资源目录里**。jeecg-study 的 `jeecg-system-start/config/jeecg/code-template-online`（201 个文件）是从 `jeecg-system-biz/src/main/resources/jeecg/code-template-online` 释放出来的 → 删掉启动会自愈。
- **⚠ 同名陷阱**：`config` 这个名字**既**是运行时释放目录，**又**是源码包名（`jeecg-boot-base-core/src/main/resources/config`、`org.jeecg.config` 等）。写 `**/config/` 的忽略规则会**误伤真实源码** ⇒ **忽略规则必须写精确路径**。
- **判依赖能不能删**：先查**包管理器与锁文件**。本项目上游是 pnpm（README / `package.json` / docker 全是 pnpm），但本地多出一份 `package-lock.json`（`npm install` 副产物）⇒ **双锁文件是版本漂移风险**，要删的是它，不是 `pnpm-lock.yaml`。
- **删前先算净收益**：fat jar 常常是 target 里的大头（jeecg-study 的 `jeecg-system-start/target` 309.3 MB 里 **309.3 MB 是 fat jar**，classes 只有 2.6 MB）⇒ 只跑 `compile`/`install` 并加 `-Dspring-boot.repackage.skip=true`，空间**不会长回来**。

### E-14 Windows 上删「被 JVM 占用的文件」必须先停进程，且要认准 pid 属于哪个仓库

- **现象**：`mvn` 跑过的 `target/*.jar` 被 Java 进程打开着，删除直接失败（文件被映射）。
- **正确做法**：**先停进程 → 再删 → 再重编译**。
- **⚠ 认 pid 的坑**：本机同时跑着 **monitorV2 / jeecg-skiot / jeecg-study 三个 JeecgBoot 后端**，命令行长得几乎一样（都是 `java -jar .../jeecg-system-start-3.9.2.jar`），只差路径。**按端口定位**（jeecg-study = 8590），再按命令行里的**项目路径**二次确认，**不要按进程名批量杀**。
- **PowerShell 坑**：`rm` 是 `Remove-Item` 的别名，**不是**运行时的可恢复删除通道。Windows 上可恢复删除要用 `<activeDataDir>\bin\mavis-trash.cmd -r -f -- "<target1>" "<target2>"`。
- **Maven 参数坑**：PowerShell 5.1 会把 `-Dspring-boot.repackage.skip=true` **拆成两段**（`-Dspring-boot` + `.repackage.skip=true`）→ mvn 报 `Unknown lifecycle phase ".repackage.skip=true"`。**所有 `-D` 参数一律加单引号**。

### E-15 父仓库跟踪**嵌套仓库**里的文件：两个拦截点，症状都是「exit 0 但没生效」

- **场景**：项目里放了一份**自带 `.git`** 的第三方源码（jeecg-study 的 JeecgBoot v3.9.2 基座），要把其中「相对上游的改动」入库。
- **拦截点 ①（嵌套 `.git`）**：`git add -f -- <嵌套目录内的文件>` → **exit 0、索引没变**（静默跳过）；`git add -f -- <整个嵌套目录>` → `fatal: 'xxx/' does not have a commit checked out`。
  **解法**：绕开工作区扫描，直接写索引——
  ```
  git hash-object -w --no-filters -- <文件>            → blob hash
  git update-index --add --cacheinfo <mode>,<hash>,<路径>   → 进索引
  ```
  实测：`git status` 不误报、`git commit` 正常、`git clone` 出来文件完整。
- **拦截点 ②（`.gitignore`）**：上面那条命令换成**批量形式** `git update-index --index-info`
  会被 ignore 规则命中而**静默跳过**——同样是 exit 0、条目没落地。
  **必须用 `--cacheinfo` 单条形式**（可一次传多个 `--cacheinfo` 分批调用，规避 Windows 命令行 32KB 上限）。
- **⚠ 通用判据**：**「命令 exit 0」不等于「事情做成了」**。凡是「批量写入索引 / 批量写文件 / 批量改配置」，
  一律要**回读校验**（`git ls-files --cached`、重新读文件），否则静默失败会被当成成功一路带到线上。
- **配套坑**：git 默认 `core.quotepath=true`，会把**中文路径转义成八进制**（`"\346\240\273..."`）——
  直接写进清单文件就是坏路径。所有 git 调用加 `-c core.quotepath=false`。
- **配套坑**：清单类产物**自己会被下一轮收录**（`export` 生成的清单，下一轮 `export` 又把它当新增收进去）⇒ 自我引用。要显式排除。
- **配套坑**：PowerShell 管道给原生程序会加 **BOM**，`git update-index --index-info` 会报 `malformed index info ﻿﻿100644 ...`。
  用 Python 的 `subprocess(input=...)` 或 `git -C` 绝对路径，**别走 PS 管道**。

### E-16 凭据扫描闸门：先判「**会不会被推上去**」，再判「像不像凭据」

- **现象**：把「仓库里有没有敏感词」当判据，会同时出两类错：
  **假阳**（上游自带的公开默认值 `root` / `postgres` / `123456`、yml 里的 `??` 掩码、文档里的 `src/App.vue:41-99`、
  脚本里的 `$env:MYSQL_PWD` 全被当成口令）；**假阴**（`${VAR:-真实口令}` 这种「占位符里藏口令」的形式）。
- **正确判据分三层**：
  1. **范围**：只扫**会入库**的文件——本项目是「仓库普通文件 + 基座目录按 overlay 清单」，**不是**扫工作区。
     （工作区里有一整棵上游源码，扫它必然刷屏。）
  2. **是不是凭据**：字母+数字混合，或长度 ≥12 且字符类 ≥3。`??` / `$env` / `getToken()` / `root}` 一律不算。
  3. **是不是明文**：`${VAR}` / `${VAR:默认值}` / `$(...)` / `{{...}}` / 含中文的占位文案 / 上游公开默认值白名单 ⇒ 安全；
     **但 `${VAR:-默认值}` 的「默认值」要再判一次**——`${MYSQL_ROOT_PASSWORD:-真实口令}` 仍然是泄漏。
- **⚠ 白名单要有出处**：白名单里每一条都该写清「这是上游 v3.9.2 自带的公开默认值」，而不是「这是我允许的」。
  判断归属的办法是**逐行与上游比对**：把上游的同名文件拉出来，diff 出「当前有、上游没有」的行——那才是本项目引入的。
- **闸门必须自带有效性自检**：塞几条合成口令（必须命中）+ 几条安全写法（必须放过），
  规则写坏时会「扫描集合非空但规则全失效 ⇒ 假绿」。
- **⚠ 自检里的路径参数要真实**：规则里有「只对 `.md` 生效」这类路径相关分支时，自检也得传 `.md` 路径，
  否则自检样本走不到那条分支，会误判成「规则失效」。
- **配套**：明文一旦进**公开**仓库历史，**改代码不闭环，轮换口令才闭环**——所以扫描必须发生在**推送之前**。

### E-17 Windows 上「clone 成功但 checkout 失败」= 路径超长，不是网络问题

- **现象**：`git clone` 退出码非 0，报文里有一大段 `error: unable to create file ...: Filename too long`，
  末尾一句 `warning: Clone succeeded, but checkout failed.`——**clone 其实成功了，只是工作区没检出全**。
  这类仓库会让人误以为是网络/代理问题，反复重试毫无意义。
- **根因**：Windows MAX_PATH **260 字符**。JeecgBoot 上游的代码模板目录
  （`jeecg-boot/jeecg-module-system/jeecg-system-biz/src/main/resources/jeecg/code-template-online/...`
  下的 `${bussiPackage}/${entityPackage}/...`）路径长达 **250+ 字符**，
  目标目录前缀每多 10 个字符就多 10 字符地往上顶。
- **正解**：
  1. clone 加 `-c core.longpaths=true`（走 `\\?\` 前缀，不受 260 限制）；
  2. **目标目录越短越好**——实测同一份上游：目标 45 字符 → 最长路径 253（通过）；
     目标 73 字符 → 281（失败）。
  3. 系统侧还要 `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem` 的 `LongPathsEnabled=1`。
- **判据**：目标路径长度 + 上游最长相对路径 ≤ 260 才安全；不确定就**换短路径**试，别改代码。
- **配套（换行符漂移）**：Windows 上 git 默认 `core.autocrlf=true`，clone 出来的文件是 **CRLF**；
  而用编辑器/脚本新建的文件通常是 **LF**。做「字节级补丁」（overlay）时这会让
  「还原结果与本地一致」**只在内容层面成立、字节层面不成立**。
  ⇒ 用根目录 `.gitattributes` 写 `* -text`：**入库什么，检出就是什么**，跨平台字节一致。

### E-18 git 的 credential helper 链顺序 = system → global → **local**，本地配置排在最后

- **症状**：push 报 `remote: Invalid username or token`，但**同一个 token 调 API 是好的**（HTTP 200、scopes 正常）。
  容易误判成「token 权限不够」或「仓库没权限」，实际是**根本没轮到这个凭据**。
- **根因**：helper 列表按 **system → global → local** 拼接，**逐个询问，谁先返回凭据就用谁**。
  所以**本地** `.git/config` 里写的 helper 排在**全局**之后——全局那条内联函数
  （`!f() { echo username=...; echo password=...; }; f`）永远抢先，**本地的 `manager` 形同虚设**。
- **正解**：在**本地** `.git/config` 写一条**空值** helper，把前面的列表**重置**掉：
  ```ini
  [credential]
      helper =          # 空值 = 重置列表（不是「什么都不做」）
      helper = manager
  ```
  之后 GCM 才会被问到，Windows 凭据管理器里的条目也就生效了。
- **⚠ 写不进空值**：`git config --local --add credential.helper ""` 会报
  `wrong number of arguments, should be 2`——**PowerShell 5.1 会吞掉空字符串参数**，
  数组 splatting（`& git @a`）也一样。**只能直接编辑 `.git/config` 文件**。
- **配套**：全局那条写死的 token 失效后，**`git ls-remote` 仍可能 exit=0**——
  空仓库允许匿名读，**读成功不代表写能用**。判断凭据有效性要**直接打 API**（`/user`），
  别用 `ls-remote` 的退出码代替。
- **⚠ 别把 token 写进远端 URL**：`https://user:token@github.com/...` 会让 token 出现在
  `git remote -v`、进程命令行和日志里。正确做法是让 helper 链走 GCM。

### E-19 vite 的 `import.meta.glob` 在 **dev server 启动时**展开并缓存 —— 新增 `.vue` 必须重启

- **症状**：新增了一批 `.vue` 页面，路由也配好了，点进去却是 JeecgBoot 的
  **「查看组件引用是否正确」**空态。代码看着没问题，路径也对。
- **根因**：`src/utils/dynamicPages.ts` 用 `import.meta.glob` 枚举视图组件，
  这个 glob **在 dev server 启动时静态展开并缓存**。之后新增的 `.vue`
  **不会**进入缓存 ⇒ `dynamicImport` 找不到组件 ⇒ 路由组件解析失败。
- **正解**：**新增 `.vue` 页面后必须重启 dev server**。这是 vite 的机制，不是本项目的约定。
- **⚠ 别用 `Start-Process` 起 vite**：`Start-Process` + `RedirectStandardOutput` 会**卡死**
  （0 CPU、无监听、无日志）；且传**含中文的绝对路径**会被 ANSI 编码打乱。
  正确做法是 **Python `subprocess.Popen(cwd=...)`**（走 `CreateProcessW`），
  脚本路径用**相对路径**（`node_modules\vite\bin\vite.js`）。
- **排查姿势**：看到「组件引用不正确」空态，先 `curl` 一下
  `http://127.0.0.1:8589/src/utils/dynamicPages.ts`，
  **grep 新页面路径在不在**——不在就是 glob 陈旧，重启即可，别去改路由。

### E-20 `is_leaf = 1` 会让后端**静默剪掉整棵子树** —— 不是 404，是「从来没出现过」

- **症状**：菜单树 JSON 里 children 齐全，接口全 200，控制台一条错都没有，
  但某个子菜单**点不到 / 打开是 404 插画**。极难定位。
- **根因**：底座 `SysPermissionController#getPermissionJsonArray`（`:735` 与 `:759`）
  **只有 `!permission.isLeaf()` 才递归进子节点**。父菜单 `is_leaf = 1` ⇒
  它的子菜单**被静默丢弃**，没有任何报错。
- **正解**：
  ① **有子菜单 ⇒ `is_leaf` 必须为 0**；反向**不成立**——上游里「只有按钮」的菜单
     `is_leaf = 0`（后端要递归下去把按钮挂到 `meta.permissionList`），
     所以**只能按子菜单（`menu_type IN (0,1)`）算，不能按「无任何子节点」算**；
  ② 动态路由（`:code`）菜单挂在**目录**菜单下，不挂在叶子菜单下；
  ③ 种子脚本 `ON DUPLICATE KEY UPDATE` **必须回写** `parent_id` / `is_leaf`
     （只写 `INSERT` 的话，改挂载层级**重跑脚本也救不回来**）；
  ④ 脚本带**自愈 UPDATE**：`SET is_leaf = (SELECT CASE WHEN COUNT(*) = 0 THEN 1 ELSE 0 END ...)`。
- **断言口径**：照抄后端算法复算**可达集**（从根出发，`is_leaf=1` 就不下探），
  断言所有 `st_menu%` 可达——比只查字段本身强（ADR-043）。

### E-21 antd 表格按 `record[dataIndex]` 取值 —— 底座 `useColumns` **不会**把 `key` 映射成 `dataIndex`

- **症状**：表格在、表头在、分页在，**所有数据列全空**，只有操作列的「查看」链接有内容。
- **根因**：antd 按 `record[dataIndex]` 取值；底座 `useColumns` 只处理 `key → dataIndex` 的
  **显示名**，**不会**把 `key` 当取值字段。薄配置页只写 `{key,title,width}` ⇒
  每格都是 `record[undefined]` ⇒ **整列空白，且没有任何报错**。
- **正解**：**取值约定收敛到内核**——薄配置页只描述「内容列」，
  内核统一补 `dataIndex: item.dataIndex || item.key`（ADR-044）。
- **连带两个坑**：
  - **双操作列**：手工注入的 `{key:'action'}` **拦不住**——
    `handleActionColumn` 只按 `flag === ACTION_COLUMN_FLAG` 去重。
    操作列**只能由 BasicTable 的 `actionColumn` 提供一处**；
  - **凭空多出「展开行」按钮**：VO 里带 `children`，antd 以为这行可展开。
    平铺列表要把 `children` 映射为 `undefined`。
- **判据**：验「整列空白」**不能只看操作列有没有链接**（操作列走 slot，与 `dataIndex` 无关），
  必须单独数**数据格**的空单元格。

### E-22 antd 表格有一行**隐藏测量行** —— 统计「空白单元格」必须先扣掉它

- **症状**：数出来「空白单元格 = 列数」，一眼看像整列空白，其实是好的。
- **根因**：antd 表格有一行隐藏的测量行（`ant-table-measure-row`），
  它按**列数**贡献等量空单元格（用于列宽测量）。
- **正解**：判据是**真实数据行的空白格是否非零**，
  不是「表格里有没有空单元格」。A04 的 3 个空格是真数据为 NULL（已用接口原始响应交叉核对）。
- **配套（判据写错 vs 产物写错）**：报告 FAIL 先质疑**判据本身**——
  对照底座实现、样例、上一期成品复核，确认判据无误再改产物；反过来也一样。

### E-23 「兜底」挂在**写入口**上，等于没挂在读路径上

- **症状**：以为「当月分表不存在」的隐患已经处理过了——
  数学域的写入口里有 `createTableIfAbsent`，看着挺稳。
- **根因**：兜底挂在**写入口**，而**读路径也会炸**：
  练习域「取一道孩子没做过的题」SQL 里带 `NOT EXISTS (SELECT 1 FROM ${tableName} ...)`，
  子查询所在的表不存在 ⇒ **取题直接失败** ⇒ 孩子连题都拿不到。
  「记不上分」是看得见的症状，「连题都取不到」是看不见的那个。
- **正解**：兜底挂在**「拿表名」那一刻**（收进公共守卫 `currentTableName()`），
  任何一处调用都自动被保护，**漏不掉**（ADR-045）。
- **判据**：问「这条 SQL 路径上，缺表会怎样」——
  **读路径与写路径要分开看**，只看写入口就下结论，必然漏判。
- **连带**：建表失败**不要抛异常**，只记 WARN；让后续真实读写抛「表不存在」的原始错误，
  那才是运维该看到的根因，在兜底处抛「建表失败」反而掩盖它。

### E-24 生产 `@MapperScan` 只扫 `*.mapper` 包 —— 测试扫描更宽，**会把这个缺陷掩盖掉**

- **症状**：新 Mapper 放在 `common/record/` 下，**测试全绿**，
  但生产启动就报找不到 Bean / 应用起不来。
- **根因**：基座生产 `@MapperScan(value={"org.jeecg.**.mapper*"})`
  **只扫包名以 `mapper` 开头的目录**；而测试用的
  `@MapperScan(basePackages="org.jeecg.modules.study", annotationClass=Mapper.class)`
  范围**大得多** ⇒ **测试永远发现不了这个问题**。
- **正解**：Mapper 一律放在 `…/xxx/mapper/` 下；
  并补一条静态断言「Mapper 接口的包末段必须以 `mapper` 开头」（ADR-045）。
- **判据**：**扫描范围差异 = 会被测试掩盖的缺陷面**。

### E-25 MySQL 8.0 的 `--skip-grant-tables` **隐含关闭网络** —— 恢复口令要走 IPC

- **症状**：停服务后用 `mysqld --skip-grant-tables --console` 起临时实例，
  日志直接 `ERROR 10131: TCP/IP, --shared-memory, or --named-pipe should be configured`，
  并且 `port: 0`。
- **根因**：MySQL 8.0 的 `--skip-grant-tables` **会连带关掉网络**；
  显式加 `--skip-networking=OFF` **不生效**（实测仍 `port: 0`）。
  Windows 上必须留一条 IPC 通道（命名管道或共享内存）。
- **正解**（本机实测可行）：
  ① 用 `--init-file` 把改口令的 SQL 交给服务器**启动时**执行
     （`FLUSH PRIVILEGES;` 必须在 `ALTER USER` **之前**，否则 1045）；
  ② IPC 用**共享内存**：`--shared-memory=1 --shared-memory-base-name=MYSQL`，
     客户端 `mysql --protocol=MEMORY --shared-memory-base-name=MYSQL -u root --skip-password`；
  ③ 改完口令后 `mysqladmin ... shutdown` **优雅关闭**，再 `Start-Service MySQL80` 恢复服务。
- **两个连带坑**：
  - **`init-file` 路径别放 `C:\Windows\Temp`**：那是**受保护路径**，
    bash / write 工具都写不了也删不掉 —— 里面若含明文口令就**留在盘上删不掉**。
    放 `%TEMP%` 或工作区外可写目录；
  - **`FLUSH PRIVILEGES` 会把「免密」这个后门关掉**：init-file 里先 `FLUSH PRIVILEGES`
    之后，账号表已加载、认证被强制 ⇒ 连不上的就别再连，
    改口令要**在同一次 init-file 执行里**做完 `FLUSH PRIVILEGES` + `ALTER USER`。
- **PowerShell 坑**：**here-string 经管道传给原生命令时带 UTF-8 BOM**，
  `ALTER USER` 会报 `ERROR 1064 ... near '﻿ALTER'`（BOM 粘在语句开头）。
  正解：SQL 用 `-e` 直接传参，或先写**无 BOM** 的临时文件再喂给客户端。

### E-26 口令「查不到变更来源」时**不要自己改回去** —— 改口令是破坏性操作

- **症状**：某台机器上 MySQL root 突然登不上，binlog 里有一条
  `ALTER USER 'root'@'localhost' IDENTIFIED WITH 'caching_sha2_password' AS '$A$005$...'`
  （**只有哈希、不可逆**），查不到是谁改的 ⇒ 顺手「恢复」成旧口令。
- **真相（2026-11-04 实测）**：口令是**用户自己主动改的**，而且**有意为之**。
  「恢复」动作**反向覆盖了用户的新口令** ⇒ 用户的新口令在库里失效，
  还得再改一次才能恢复。**破坏性操作猜错方向 = 制造第二份损失**。
- **正解**：口令类变更查不到来源时，**先问**（用户 / 会话 / 工单），**不要自己改回去**。
  判据：**改口令会覆盖对方的意图 ⇒ 不可逆 ⇒ 必须先确认**。
  与「代码被覆盖」同源，但**代价更高**（凭据错了连服务都起不来）。
- **配套（问不到怎么办）**：要临时恢复访问，就**用最小改动**恢复
  （`ALTER USER ... BY`，而不是重建账号），并**明确告知用户「我把它恢复成了 X」** ——
  否则用户会以为自己的新口令还在用。
- **连带教训（同一个坑的另一面）**：口令的**注入点 ≠ 真源**。
  计划任务 / 服务 / 独立身份在跑时，**拿不到人工会话的环境变量** ⇒
  口令来源必须有一个**不依赖会话的兜底**（本项目用 DPAPI 加密凭据文件，ADR-046）。
  「之前跑通过」可能只是**恰好**有环境变量 ⇒ **运气不是设计**。
- **再往前一步**：环境变量在进程环境块里是**明文**，同用户任何进程都能读出来
  ⇒ 它可以做**注入点**，但不适合当**真源**。真源要满足三条：
  **只有一份**、**机器上没有明文副本**、**能被多个身份取用**。

### E-27 「形态规则全绿」**不等于**「没有明文口令」—— 必须有一条**按真值**兜底的规则

- **症状**：凭据扫描闸门 R1…R6 **全绿**，但真口令**确实**明文写进了
  `CHANGELOG.md` 和任务台账 ⇒ 最后是被**另一条独立扫描**抓到的，不是闸门抓到的。
- **根因**：R1…R6 全是**形态**规则 ——
  - 要么要「敏感**键名** + 值的结构」（`password: X` / 表格列 / 引号字面量）；
  - 要么要「短词 + 艾特 + 恰好四位数字」这一种固定形态；
  - 通用值判定 `looks_like_secret()` 也是**形态**（字母+数字混合）。
  真实口令含 `!@#` 等特殊字符、在散文里写成一句「新口令是 X」时，
  **既没有键名，也不符合任何形态** ⇒ **前 6 条全部放过**。
- **通用判据**：**形态的种类是无界的，真值只有一个。**
  凭据的泄漏形态可以是散文 / 注释 / 表格 / JSON / SVG / 提交信息 / 文件名……
  ⇒ 凡是「按形态判定」的闸门，都必然存在**它抓不到的形态**。
  正确做法是**再加一条按真值兜底的规则**：
  凭据真源在机器上（DPAPI / Vault / KMS），闸门运行期解密，**逐字比对**。
- **三条配套约束**：
  ① **不落明文**：真源只在内存里解密一次；命中回显**一律掩码** ——
     **闸门自己的输出 / CI 日志也是泄漏面**（连形态规则抓到真口令时也不许明文回显）；
  ② **不依赖机器**：CI / 其它机器没有真源 ⇒ 该规则**跳过并明确提示**，
     **不能因此让闸门永远红**；但输出里必须写清「这条规则本轮没生效」；
  ③ **未分类文件也要覆盖**：形态规则通常只扫配置/脚本/源码，
     而 `.html` / `.json` / `.css` / `.svg` 里同样可能藏凭据 ⇒ 兜底规则要**扫全部文本**。
- **自检要覆盖规则本身**：新增规则要有**专项自检**（用**合成值**，绝不用真口令）
  + **反例夹具**（造一份含真口令的假文件 ⇒ 闸门必须报红 ⇒ 删掉后必须复绿）。
  没有反例夹具，就无法证明这条规则**真的在工作**。
- **附带教训**：本轮 R7 上线后的**第一次**跑闸门就报红了 —— 命中的正是
  **我自己写进 R7 说明文字里的真口令**（写文档时把真口令当例子写进去了）。
  ⇒ **写任何涉及凭据的文档，都不要把真值当例子写**；
  例子用「含特殊字符的那一组口令」这种描述代替。

### E-28 端点比对：`normalize("")` 把「无方法级路径」变成尾斜杠 —— 凭空造出 7 条幽灵缺失

- **症状（2026-11-04 实测）**：接口文档 106 个端点，后端 105 个 ⇒ 差 11 个。
  但把两侧端点集合**逐条打印**再人工比对，真实缺口是 **13 个**，
  另有 **7 个是假阳性**：`POST /context`、`GET /textbook-versions`、
  `POST|GET|PUT /family`、`GET|POST /children` —— 这些**代码里明明有**。
- **根因**：方法级映射**可以没有路径**（`@PostMapping` + 类级
  `@RequestMapping("/api/v1/study/family")`）。扫描时把「空」当成「根」处理：
  ```python
  path = normalize(method_group)      # normalize("") → "/"   ← 错在这里
  full = root + path                  # → "/api/v1/study/family/"
  ```
  文档侧是 `/api/v1/study/family`（无尾斜杠）⇒ **两边永远对不上**。
  尾斜杠归一只处理了 `len(p) > 1`，**恰好漏掉长度为 1 的 `"/"`**。
- **正解**：`normalize` 遇空串**原样返回 `""`**，让拼接层决定「空路径 = 沿用类级根」。
  ```python
  if path is None or path == "": return ""
  ```
  拼接层再分支：`if root and path: full = root + path` / `else: full = root or path`。
- **通用判据**：**归一化函数必须先定义「空」代表什么**。
  「空路径」≠「根路径」—— 前者是「沿用上级」，后者是「就是 `/`」。
  凡是做**两套来源比对**的断言（文档↔代码、DB↔代码、前端↔后端），
  都要单独验证这一条：**空输入会不会被悄悄补成 `/`？**
- **附带（为什么这次差点蒙混过去）**：假阳性是**多报**、不是少报，
  所以「断言报红」看起来更「安全」。但它会让人去**实现已经存在的端点**，
  或把断言改成「豁免」来放行 —— **假阳性比假阴性更危险**，
  因为它会诱导人**关掉闸门**。
  ⇒ 断言报出的清单必须**逐条人工核对**一次，确认真实缺口数，
  再决定「补实现」还是「改口径」。
- **配套自检**：端点比对类断言要能打印**两侧集合的差集**，
  且**跑一次「已知全部实现」的基准场景**确认差集为空 ——
  否则没法区分「真缺」与「扫描口径错」。

### E-29 追溯矩阵只查「文档表格」不查「代码路由」⇒ 文档承诺的接口一个没实现，矩阵却显示零缺口

- **症状**：2026-11-04 全量盘点发现，《接口设计说明书》共 **106** 个端点，
  代码里实存 **105** 个 —— 但**差的不是 1 个，是 13 个**。

  于是**追溯矩阵判成「已覆盖」** —— 而它查的是**文档表格**，不是**代码路由**。
  结果：**文档承诺的接口一个都没实现，追溯矩阵却零缺口。**
- **根因**：「追溯」的语义是「需求 ↔ 接口 ↔ 用例」三者的**文档级引用关系**；
  它**从来没承诺**「接口一定存在」。缺的那一环是
  **接口文档 → 代码路由**（文档说了什么 ⇢ 代码真的有什么）。
- **正解（补上闭环的那一环）**：
  ① 矩阵生成器新增 `scan_backend_endpoints()`，
     扫控制器真实路由；**接口总表的端点必须在代码里存在才计入覆盖**，
     未实现的单列清单并让**退出码 = 2**；
  ② 另立一条**可执行断言**（`StudyApiDocEndpointTest`）做
     **接口文档 → 后端**方向的双向闭合校验。
  与既有的 `StudyInterfacePageTest`（**前端 → 后端**）方向相反，**两个方向都要有** ——
  只有前端侧校验时，「文档写了但没实现」的端点会从两个方向都漏过去。
- **合法豁免只有一种**：接口文档该行**说明列显式写明「未实现 / 暂不实现」并给出原因**。
  不接受「已合并到 XXX」这类含糊说法 —— 那会让断言失去意义
  （**这正是本轮 13 个漏网端点的成因**）。
- **通用判据**：**「追溯」不等于「存在」。**
  任何「文档说做了 ⇒ 就算做了」的判定，都是把**声明**当**事实**。
  判断一个产出是否真的落地，要有一条**指向可执行产物**的独立校验，
  而不是指向**同一份文档**的交叉引用。

### E-30 PowerShell 把 SQL 喂给 `mysql` 用管道 ⇒ 中文变 `??????` + BOM 被当 SQL 内容

- **症状（2026-11-04 实测）**：`migrate.ps1` 实跑报
  `ERROR 1064 ... syntax error near '﻿'`；把出错的 SQL 单独看又像是对的。
- **根因（两层叠加）**：
  ① **管道重编码**：`$sql | & $mysql` 会让 PowerShell 5.1 按
     **ANSI（GBK）**重编码输出 ⇒ UTF-8 里的中文注释变成 `??????`，
     在 SQL 里就成了非法 token；
  ② **BOM 进了内容**：生成的脚本文件带 UTF-8 BOM，
     经管道传给客户端后 BOM 成为**内容的一部分**，
     于是报错位置落在**语句开头的 `﻿`** 上。
- **正解**：**不要用管道喂 SQL**。改成「去 BOM → 写临时文件 → `cmd` 重定向导入」：
  ```powershell
  $tmp = [IO.Path]::GetTempFileName()
  $body = [IO.File]::ReadAllText($sql, [Text.Encoding]::UTF8)
  [IO.File]::WriteAllText($tmp, $body, (New-Object Text.UTF8Encoding($false)))  # 无 BOM
  cmd /c "mysql --database=jeecg-study < `"$tmp`""
  ```
  三处细节：① **显式 UTF-8 读取**（别让 PS 猜编码）；
  ② **写回时 `UTF8Encoding($false)`**（不要 BOM）；
  ③ **用 `cmd` 重定向**（`<` 是 `cmd` 的重定向，PS 不支持）。
- **同类坑（顺带记）**：`mysql -e "`库名`"` 用反引号包库名 ⇒
  PS 转义成 `` \` `` ⇒ 报 `Unknown command '\j'`。
  正解：用 `--database=jeecg-study` 或 `-D 'jeecg-study'`，**不要反引号**。
- **通用判据**：**任何把「带编码的文件内容」喂给原生命令的管道，都要先问一句「编码谁说了算」。**
  Windows 下 PS 的管道是**文本管道**，会按 `$OutputEncoding` 重编码 ——
  **只有「字节」才安全**：改走文件 + 重定向。
  这条与 E-25（init-file 要放可写目录，别放受保护路径）同源：
  **凡是要落盘的中间产物，路径和编码都得自己说了算。**

### E-31 「注释里的 HTML 标签」让注释散文被当成用户可见文案 —— 前端文案扫描的真陷阱

- **症状（2026-11-04 实测）**：R-04 文案断言（`r04_3_noRankingCopy`）报红，
  命中的却是一段 **JSDoc 注释**：
  ```java
  <p>只读页面：只展示<b>当前孩子自己</b>的考点掌握情况（R-04 / 自检清单 #30）。
   * 不出现排名、百分位、也不与任何其他人比较。</p>
  ```
  报错文本明确显示命中内容是「**注释里的散文**」，
  而页面上根本没有这句文案 —— 用户永远看不到它。
- **根因**：前端文案扫描的正则是
  `>([^<>{}]*?[\u4e00-\u9fa5][^<>{}]*?)<`，
  即**取 `>` 与 `<` 之间的内容**当模板文本。
  而 JSDoc 里习惯写 `<p>` / `<li>` / `<b>` / `</p>` ——
  **注释里的 `>` 与 `<` 同样成对**，于是整段注释散文被当作「模板里的可见文字」扫进来。
  ⇒ **注释里的 HTML 标签 = 一个伪装成注释的文案出口。**
- **正解（二选一）**：
  ① 注释里**不写 HTML 标签**，用纯文本段落（这样 `>` … `<` 不会在注释里出现）；
  ② 或者**彻底不用违禁措辞**，注释也一并改写。
- **配套判据（很关键）**：**同一套扫描规则在前后端口径不同** ——
  Java 侧只扫**双引号字符串字面量**（`JAVA_STRING`），**注释不参与**；
  前端侧扫「模板文本 + 引号字符串」，**注释会参与**。
  ⇒ **「后端注释随便写、前端注释要小心」不是约定，是实现差异**，
  照搬后端的注释习惯到前端就会踩雷。
- **通用判据**：**任何「按正则抽文案」的断言，都要先问「这条正则会不会越过注释边界」。**
  判别方法：拿一段**只出现在注释里**的文本去试 —— 若被命中，说明正则越界了。
  **断言的误报方向很重要**：
  - 误报**少**（该抓的没抓）⇒ 闸门失守，危险；
  - 误报**多**（没违规也报红）⇒ 诱导人去**改断言或加豁免**来放行，
    **更危险** —— 因为它会让人主动把闸门拆了。
  ⇒ 所以断言报出的清单**必须逐条人工核对**，
  确认是「真违规」还是「扫描口径越界」，再决定改代码还是改口径。
- **顺手修掉的同类项**：本次同一轮里，另一个前端文件在
  `<li>…不给名次与分数（R-04）。</li>` 这类注释里踩了同一个坑 ——
  说明这不是偶发，而是**「在注释里写给人看的解释」这一习惯的系统性副作用**。
  ⇒ 在有文案扫描断言的目录里写注释，**默认假设注释也会被扫**。

### E-32 mysql 选项文件里的 `#` 会**静默截断口令** ⇒ 1045 Access denied

- **症状（2026-11-04 实测）**：CI 建库脚本用 `--defaults-extra-file` 传口令，
  连接报 `ERROR 1045 (28000): Access denied for user 'root'@'localhost' (using password: YES)`。
  但同一个口令用 `MYSQL_PWD` 环境变量、以及命令行直连**都能连上**，
  且脚本里明明写的是 `using password: YES`（说明口令**传进去了**，只是**值不对**）。
- **根因**：mysql 的**选项文件（my.cnf 家族）把 `#` 和 `;` 当注释起始符**。
  口令里含 `#` 时，`password=abc#def` 这一行**从 `#` 处被截断**，
  客户端实际拿到的是 `abc` ⇒ 认证失败。
  **它不报「格式错误」，只是把口令改小了** —— 所以现场现象是「口令明明是对的却连不上」。
- **判据**：**「口令对」不等于「传过去的是同一个口令」。**
  连接失败先做**逐字节对比**（长度 + 哈希），而不是先怀疑服务端。
  本次实测：PowerShell 侧 `DB_PASSWORD` 长度 14、sha 前缀 `8fab1a53…`，
  bash 侧拿到的**完全一致** ⇒ 说明问题不在「传参」，而在**解析**。
- **正解**：选项文件里的值**用双引号包起来**，并转义 `\` 与 `"`：
  ```bash
  cnf_pw="$(printf '%s' "$DB_PASSWORD" | sed -e 's/\\/\\\\/g' -e 's/"/\\"/g')"
  printf '[client]\nhost=%s\nport=%s\nuser=%s\npassword="%s"\n' "$HOST" "$PORT" "$DBUSER" "$cnf_pw" > "$CNF"
  ```
- **通用判据**：**任何「键=值」格式的配置文件，都要问「值里可能出现分隔符/注释符吗」。**
  同类高危位：`.env`（`#` 注释）、`ini`（`;`/`#`）、`.gitignore`（`#`）、
  YAML（`#`）、properties（`#`/`!`）。
  ⇒ **口令类值一律加引号**，别赌「我的口令里没这些字符」——
  真源口令是 DPAPI 生成的，**字符集不受人控制**。

### E-33 Git bash 的 `bash.exe script.sh` **不带 `/usr/bin`**，内建工具全是 MISSING

- **症状（2026-11-04 实测）**：用 `D:\DevTools\Git\usr\bin\bash.exe <脚本>` 跑本机实测，
  脚本里 `command -v sed / mktemp / sha256sum / awk / tr` **全部 MISSING**，
  脚本里再调 `bash` 又落到 `C:\Windows\System32\bash`（WSL 启动器）⇒ 弹出 WSL 安装提示。
- **根因**：**非登录 shell 不注入 MSYS 的 `/usr/bin` 到 PATH**，
  继承的是 Windows 的 PATH（里面没有 `/usr/bin`）；
  而 `C:\Windows\System32\bash.exe`（WSL 启动器）**排在 Windows PATH 前面**，
  于是脚本里的 `bash` 解析到了 WSL 而不是 Git bash。
- **正解**：**一律用 `bash.exe -lc '<脚本>'`**（登录 shell 会把 `/usr/bin` 挂到 PATH 最前）：
  ```powershell
  & 'D:\DevTools\Git\usr\bin\bash.exe' -lc 'source /c/Users/<用户>/AppData/Local/Temp/x.sh'
  ```
  验证：`bash -lc 'command -v sed'` → `/usr/bin/sed` ✓
- **通用判据**：**在 Windows 上调 POSIX 工具链时，「能不能跑」取决于 shell 是不是登录 shell。**
  `bash -n`（语法检查）不依赖 PATH，**所以「`bash -n` 通过」不等于「脚本能跑」** ——
  这是个很危险的错觉：语法过了、工具全缺，跑起来才炸。
  ⇒ **能用 `-lc` 就用 `-lc`**，别用 `bash.exe script.sh`。

### E-34 GitHub Actions 的 service container 拿不到 **step 里才生成**的变量

- **症状**：想把「CI 自己生成的随机口令」同时喂给 MySQL service container 和 job，
  但 service container 的 `env:` 在 **job 启动前**就要定下来，
  写在后面的 step 里 `export` 的变量它**根本看不到**。
- **正解**：**拆成两个 job**，用 job output 传递：
  ```yaml
  jobs:
    prepare:                       # ① 先生成
      outputs:
        db_password: ${{ steps.gen.outputs.db_password }}
      steps:
        - id: gen
          run: |
            pw="$(openssl rand -hex 24)"
            echo "::add-mask::$pw"        # 掩码，别让口令进日志
            echo "db_password=$pw" >> "$GITHUB_OUTPUT"
    ci:                           # ② 再消费
      needs: prepare
      env:
        DB_PASSWORD: ${{ needs.prepare.outputs.db_password }}
      services:
        mysql:
          env:
            MYSQL_ROOT_PASSWORD: ${{ needs.prepare.outputs.db_password }}
  ```
  `jobs.<job>.services.<svc>.env` **支持 `needs` 上下文**（也支持 `github`/`secrets`/`vars`），
  所以这条链是通的。
- **配套**：口令用**纯 hex**（`openssl rand -hex`）生成 ——
  天然避开 E-32 的 `#`/`;` 注释符问题，也天然避开各种 shell 转义；
  再加 `::add-mask::` 保证它不进日志。
- **通用判据**：**「谁先被求值」决定了这个值能不能用。**
  service container 的 env 属于**最早期**求值的一档，
  step 里的 `export` 属于**最晚期** —— 跨越这个边界必须走 **job output**。

### E-35 PowerShell 5.1 默认 ANSI(GBK) 读写 UTF-8 文件 ⇒ 中文全成乱码

- **症状**（2026-11-04 实测）：用 PowerShell 改一批 `application-*.yml`，
  提交前看着没异常，但**文件里的中文注释全变成了乱码**（`【`→`锛?`、`后端`→`鍚庣`）。
- **根因**：PowerShell 5.1 的 `Get-Content` / `Set-Content` **默认编码是系统 ANSI**
  （中文 Windows = GBK/CP936），**不是 UTF-8**。
  于是「读 UTF-8 文件」被按 GBK 反读一遍（中文 → 乱码），
  「写回」又按 UTF-8 存 ⇒ **双重编码**，原文永久丢失。
  典型症状是 `?` 与 **U+FFFD 替换符**混在乱码里 —— 那是被判为非法字节的**不可逆**位置。
- **为什么当时没炸**：乱码只落在**注释**里 ⇒ YAML 语法不变 ⇒ 应用照常起。
  真正炸的是另一件事（见 E-36），两者叠在一起才致命。
- **正解**：
  ```powershell
  # 读
  $s = [System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)
  # 写（无 BOM）
  [System.IO.File]::WriteAllText($p, $s, (New-Object System.Text.UTF8Encoding($false)))
  ```
  **不要**用裸的 `Get-Content`/`Set-Content`/`Out-File` 处理含中文的 UTF-8 文件。
- **恢复手法（关键）**：**不要试图把乱码转回去**（有不可逆位）。
  正确做法是**从干净基座重建**：
  - 有 HEAD 版本的 ⇒ 取 HEAD 的 blob（正确 UTF-8）；
  - 没有的（上游新增文件）⇒ 取上游仓库的原件。
  然后把**新增的补丁块原样搬回去** ——
  关键洞察：**本次编辑「新增」的行是直接写入的 Unicode，没被污染**，
  只有「原有内容」被反读了 ⇒ 两者可以拼回来，**语义差异恰好只剩预期改动**。
- **配套闸门**：`05-公共资源/2026110404-编码体检.py` 的 **C1 GBK 反读检测**。
  判据：把文件按 UTF-8→GBK→UTF-8 走一圈，**往返后中文数量仍占原文 35% 以上** ⇒ 报红。
  阈值是**实测标定**的：受损文件 0.479–0.504，正常文件最高 0.231，**中间 2 倍空档，零误报**。

- **症状**：给基座的 `application-*.yml` 加 `update-begin/update-end` 痕迹行后，

### E-37 PowerShell 里 `rm` 是 `Remove-Item` 的别名，回收站要走 `mavis-trash.cmd`

- **症状**：`rm -- "<绝对路径>"` 报 `Windows recoverable-delete plan requires the targets-only trash marker.`

  & 'C:\Users\<用户>\.minimax\bin\mavis-trash.cmd' -- '<绝对路径1>' '<绝对路径2>'
  # => mavis-trash: moved to trash: '...'
  ```
  **一条命令一次给全所有目标**；不要与 `cd` 组合；不要把路径写成内联表达式。
- **附带**：本地安全策略还会把命令文本里形如 `in <单字母>:` 的片段误判成**盘符路径**（如 `in s:` / `in t:`）
  ⇒ 写临时 Python 脚本时**避免单字母变量名出现在冒号前**，或直接用文件落盘再跑。

### E-38 `vite build` 随机撞 EMFILE —— 看**失败点是否每次都换文件**

- **症状**（2026-11-04 实测，连撞 3 次）：
  ```
  ERROR  ✗ Build failed in 1m 58s
  [vite-plugin-pwa:build] [less] EMFILE: too many open files,
    open '.../src/design/var/breakpoint.less'
  ```
- **判据（关键）**：**失败点每次都换文件**
  —— 第 1 次是 `src/components/.../LinkTableListModal.vue`，
  第 2 次是 `src/design/var/breakpoint.less`，第 3 次又换一个。
  **文件不同 ⇒ 不是那个文件的问题**，是**机器级句柄耗尽**。
  如果是代码/依赖问题，同一个文件会稳定复现。
  ⇒ **别去改那个文件，先怀疑环境。**
- **根因**：rollup 的 `build.rollupOptions.maxParallelFileOps` 默认 **1000**，
  配合 less / PWA 后处理阶段的海量文件读取，本机句柄被打满。
- **正解**：限并发。
  ```ts
  build: {
    rollupOptions: {
      maxParallelFileOps: 16,   // 实测进程句柄峰值从 6636 降到约 250
    },
  }
  ```
  放在**基座 `vite.config.ts`** 里而不是构建脚本里 ⇒ **本地与 CI 跑同一条路径**。
- **验证口径**：不看「有没有报错」，看**两件事同时成立**：
  ① stdout 有 `✓ built in <时长>`；② stderr 里 `ERROR` 行为空。
  再加一条：产物 `dist/**/*.js` 里能搜到**新增页面各自的组件名**（光有产物不算数）。
- **顺带**：并发降到 16 后单次构建 **2m22s**（9761 模块 + PWA precache 330 条），
  比撞 EMFILE 的那次（1m58s 失败）只是慢一点，**换来的是可重复**。
- **通用判据**：**随机失败 + 失败点漂移 ⇒ 先查环境，不要先改代码。**
  这与「断言随机红、且报出的文件不是我改过的」是同一类信号（见本文件 git 同步类条目）。

### E-39 GitHub Actions 的 `services:` 容器初始化是**黑盒** —— 失败只给两行报错，容器日志拿不到

- **症状**（2026-11-04，CI 首跑 run 41790579310）：
  ```
  job 后端测试 + 闸门 + 前端构建        failure
      step Initialize containers        failure   ← 13 秒就挂，后面 10 个 step 全 skipped
  annotation: Failed to initialize container mysql:8.0
  annotation: One or more containers failed to start.
  ```
  **仅此而已** —— 没有容器 stdout、没有 exit code、没有失败原因。
- **为什么查不到**：
  - `GET /actions/jobs/<id>/logs` 需 **admin 权限**（本仓库是公开仓，匿名 403）；
  - 作业页 HTML 里其实**有**每步的 `data-log-url`，但该端点**需登录**（匿名 404）；
  - GitHub runner 在这一步会自己执行 `docker logs` 打进 job log —— **但那份 log 恰好要登录才看得到**；
  - 本机**没有 Docker** ⇒ 无法本地复现。
  ⇒ 四条路全堵死 ⇒ **这不是「多花点时间就能查到」，是「这个接口设计上就不可观测」**。
- **判据（通用）**：**凡是一个错误信息只说「失败了」而不说「为什么」的工具接口 = 黑盒。**
  GitHub 的 service container 初始化把**容器 env 解析、healthcheck 语义、端口占用、镜像拉取**
  全藏在一个 step 里，失败时一概压缩成两行。**可观测性优先于便利性。**
- **正解：把平台托管的资源换成自己显式拉起。**
  ```bash
  docker run -d --name jeecg-study-mysql \
    -e MYSQL_ROOT_PASSWORD="$MYSQL_ROOT_PASSWORD" \
    -e MYSQL_ROOT_HOST='%' \
    -p 3306:3306 mysql:8.0
  # 自己写就绪探测（真口令 + 真查询，见 E-40），失败时把现场打进 job log：
  docker logs --tail 80 jeecg-study-mysql
  ```
  收益有三层：① 失败原因**直接进 job log**，不用登录也能看；② 就绪判据由自己定义；
  ③ 容器启动与后续步骤解耦，各失败各归各。
  再补两条兜底：**显式 `docker pull`（重试 3 次）**把「拉镜像失败」和「容器起不来」分成两条错误；
  **启动前先腾端口**（停宿主 mysql 服务 + `/dev/tcp` 探端口）——端口被占是 `docker -p` 失败的头号原因。
- **顺带核实过的几个「疑似」，都不是**：GitHub 官方文档确认
  `jobs.<job_id>.services.<service_id>.env.<env_id>` **支持 `needs` 上下文** ⇒ 口令传得进去；
  runner 镜像自带 MySQL 但**服务默认 disabled** ⇒ 3306 不被宿主占用；
  `ubuntu-latest` 已迁到 Ubuntu 26.04，**自带 mysql 客户端** ⇒ 不必 apt 装。
- **通用判据**：**CI 里凡是「平台托管的资源」，一旦失败拿不到日志，就该改成自己显式拉起。**
  宁可多写 20 行 bash，也不要留一个「报错但不知道为什么」的黑盒步骤。

### E-40 `mysqladmin ping` 对 Access denied 也返回 0 ⇒ **不能**用它判就绪

- **事实**：MySQL 官方文档对 `mysqladmin ping` 写得很明确 ——
  「即使报 Access denied 也返回 0」，因为「服务在跑但拒绝连接」与「服务没跑」是两回事。
- **后果**：用 `mysqladmin ping` 当**就绪判据**会**假阳性** ——
  「服务起来了但口令不对」会被判成就绪，然后脚本在下一条 `CREATE DATABASE` 上炸成 `ERROR 1045`，
  **真正的错误（口令不符）被藏在了后面**。
- **正解**：判就绪要跑**真查询**，且用**真口令**：
  ```bash
  mysql --defaults-extra-file="$CNF" -N -B -e "SELECT 1" >/dev/null 2>&1
  ```
- **顺带红利**：走 **TCP**（`host=127.0.0.1`）探测还能天然等过 MySQL 的**初始化阶段** ——
  初始化期的临时服务器是 `--skip-networking` 的，TCP 根本不通 ⇒ 探测会自然地一直等到真正就绪，
  **不需要自己猜「要等多久」**。
- **通用判据**：**探活命令的语义要和「我真正要确认的东西」对齐。**
  ping 类命令通常只证明「进程在」，不证明「能用」；判「能用」就得发一条真请求。

### E-41 GitHub Actions 会**跳过被掩码的值**作为 job output ⇒ 掩码值必须走 `$GITHUB_ENV`

- **症状**（2026-11-04，CI 连续两次红，根因同一个）：
  ```
  [warning] Skip output 'db_password' since it may contain secret.
  [warning] Can't add secret mask for empty string in ##[add-mask] command.
  ```
  下游 job 拿到的 `MYSQL_ROOT_PASSWORD` 是**空串** ⇒ MySQL 容器启动即退出。
- **机制**：step 里 `echo "::add-mask::$pw"` 把值注册成掩码值，
  紧接着 `echo "x=$pw" >> "$GITHUB_OUTPUT"` 想把它作为 step output 传出去 ——
  **runner 发现这个值「可能是密」，于是直接跳过它**（只留一行 warning）。
  ⇒ **job output 静默变空串**，下游拿到的是「没设」而不是「没传」。
- **为什么难发现**：报错**不在传值的地方**。本例里它表现为
  「MySQL 容器起不来」，排查方向会一路偏到镜像/端口/entrypoint 上，
  而真正的错因在**上一个 job 的输出通道**里。
- **正解**：
  - **掩码值走 `$GITHUB_ENV`**，不要走 job output ——
    `echo "DB_PASSWORD=$pw" >> "$GITHUB_ENV"` 是掩码值的标准传递方式，不受该跳过规则影响；
  - 或者**干脆不拆 job**：在同一个 step 里生成并使用（本例 MySQL 容器就是这么起的），
    后续 step 用 env 文件接手；
  - 再加一步**显式断言**（`[ -z "$DB_PASSWORD" ] && exit 1`），
    让「没传到位」当场变成一句明确的话，而不是下游的 1045。
- **判据**：**静默变空 ≠ 没传**。凡是「值从一个执行单元传到另一个执行单元」，
  都要有一处**显式断言**，别指望下游的报错能反推根因。

### E-42 闸门脚本里写死 Windows 绝对路径 ⇒ CI 上**全灭**

- **症状**：`ROOT = r"D:\DevProject\2-JavaPrj\20261030-jeecg-study"`。
  本机跑 7 道闸门全绿，推到 Linux runner 上却会**每道都找不到目录**。
- **为什么容易漏**：本机路径是**对的**，本地任何验证都发现不了；

- **正解**：按脚本位置推导仓库根（本仓已有 9 个脚本是这个写法）：
  ```python
  ROOT = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
  ```

- **顺带查的其它跨平台点**（本仓现状）：
  - `git ls-files` / `git clone` ⇒ Linux 有 git ✅；
  - DPAPI 解密（凭据扫描 R7）⇒ 真源文件不存在时**优雅跳过**（脚本里已写明「CI / 其它机器属正常」）✅；
  - MySQL 客户端 ⇒ runner 镜像**自带** ✅。
- **通用判据**：**写「跑在别人机器上的脚本」时，路径必须可推导，不能可复制。**
  凡是在脚本里看到盘符开头（`C:\` / `D:\`），一律改成 `__file__` 推导或环境变量。




### E-43 GitHub Actions 的 annotation 每 step 只有 10 条 error + 10 条 warning

- **症状**：CI 红了，把 Maven 日志末尾 40 行逐行 `::error::` 出去 ⇒ 匿名能看到了，
  但**看到的全是无用信息**（`MojoExecutor.execute` / `SurefireHelper.throwException` 的栈帧），

- **判据**：诊断脚本要**在本地用构造样本实跑一次**，确认它输出的每一条都是你要看的，

### E-44 JVM 时区 ≠ JDBC 的 `serverTimezone` ⇒ datetime 列整体漂移 8 小时

- **症状**（2026-11-04，CI 上 3 个用例红，本地全绿）：
  - 锁定期期望 8~10 分钟，实测 **489 分钟**（= +480 分钟 = +8 小时）；
  - 「今天」算成了明天，撞唯一索引 `uk_schedule_error_date`。
- **机制**：`application-test.yml` 里 `serverTimezone=Asia/Shanghai` ⇒ **DB 会话恒为 +08:00**。
  写入时 Java 的 `Timestamp` 按**连接时区**落库；读出时 DATETIME 按 **JVM 时区**解释。
  ⇒ 两边时区不同时，datetime 列**双向漂移**。
  本地 Windows 是 +08:00 ⇒ 恰好与 DB 一致 ⇒ **永远绿**；GitHub runner 默认 **UTC** ⇒ 漂 8 小时。
- **正解**：**三方对齐到同一个偏移**（JVM 时区 / DB 会话时区 / JDBC `serverTimezone`）：
  - CI：job 级 `env.TZ=Asia/Shanghai`（把 JVM 钉住）；
  - 建库脚本：`SET GLOBAL time_zone = '+08:00'`
    （**不要**用 `-e TZ=Asia/Shanghai` —— slim 镜像常常没有 tzdata，静默不生效）；
  - 加断言把契约钉死（`StudyTimeZoneContractTest`：比对 `ZoneId.systemDefault()` 与
    yml 里 `serverTimezone` 的**当前偏移**，而不是比对 zone id ——
    Windows 的 zone id 是「中国标准时间」，和 `Asia/Shanghai` 同偏移不同名）。
- **判据**：`LocalDate.now()`（JVM）与 `CURDATE()`（DB 会话）**必须同一天**。
  只要这两个分属不同时区，跨过 16:00（UTC+8 与 UTC 的分界）就会开始错。

### E-45 路径大小写：Windows 绿、Linux 红；再叠加「读不到文件静默返回空串」= 假绿

- **症状**：用 `…/studyrecordtablemapper.java` 去找 `StudyRecordTableMapper.java`：
  - Windows 不区分大小写 ⇒ 找得到 ⇒ 本地一切正常；
  - Linux 区分 ⇒ 找不到 ⇒ 依赖该文件内容的断言拿到**空集合**，
    失败信息是「列集合解析不出来 / 不一致」，**完全指不到「路径大小写」这个真因**。
- **放大器**：当时的 `RedLineScanner.read()` 读不到文件会**静默返回 `""`**，
  于是「文件找不到」被伪装成「文件是空的」⇒ 断言要么假绿、要么报一个指向下游的错误。
- **正解**：
  - 读文件**读不到就抛异常**（`Files.isRegularFile` 先判 + 明确的信息里点名「Linux 区分大小写」）；
  - 「用于字符串比对的小写相对路径」与「用于 `resolve` 的真实路径」**分成两个常量**；
  - 加一道**静态闸门**扫出所有「真的拿去做 `resolve`」的路径常量，逐个做**大小写敏感**存在性校验
    （`05-公共资源/2026110406-路径大小写检查.py`）。
- **⚠ 写这类闸门时自己也会踩同一个坑**：Windows 的 `os.path.isfile` **也不区分大小写**，
  拿它当「精确匹配」检查 ⇒ 永远返回 True ⇒ 闸门形同虚设。
  正解是**逐段拿 `os.listdir` 的真实目录项做精确比对**。
- **判据**：凡是「本地绿、CI 红」，先查这三样：**时区 / 路径大小写 / 换行符**。

### E-46 `bash -e -o pipefail` 下，失败管道会直接退出 ⇒ 诊断分支根本走不到

- **症状**：CI 里 `mvn ... | tee log` 失败后，什么诊断信息都没有 —— 连我们自己写的
  「失败时打印关键行」那段都没执行。
- **机制**：GitHub 默认用 `bash -e -o pipefail` 跑 `run:` 块。
  `errexit` 对**管道中的任一环**生效 ⇒ `mvn` 一失败，整个 run 块立刻退出，
  后面的诊断代码**永远执行不到**。
- **正解**：用 `|| status=$?` 把失败**兜住**，把退出码存进变量，
  诊断完再 `exit "$status"`：
  ```bash
  status=0
  mvn ... 2>&1 | tee "$RUNNER_TEMP/mvn.log" || status=$?
  if [ "$status" != "0" ]; then
      # 诊断
      exit "$status"
  fi
  ```
  （`||` 让 errexit 对该命令不生效。）
- **判据**：凡是「失败时应该打印点东西」的管道，后面都得跟 `|| status=$?`。
