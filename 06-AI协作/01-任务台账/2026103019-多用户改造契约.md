## 0 变更背景与用户确认

| 项 | 变更前 | 变更后 |
|---|---|---|
| 系统性质 | 单用户（一个孩子 + 一个家长） | **多家庭、多孩子、多家长** |
| 登录 | 无（本地单机使用） | 家长标准账号 + 孩子独立 PIN |
| 家长↔孩子 | 1:1 | **多对多** |
| 数据范围 | 无隔离概念 | **按 child_id 强制隔离** |
| 数据库 | 平台表 `jeecg-boot` + 业务表 `jeecg-study` 双库 | **单库 `jeecg-study`**（平台表 + 业务表同库） |
| 代码基座 | 无（仅文档） | **JeecgBoot v3.9.2 独立基座**（已拉取） |

**用户已确认的三项选择**：

1. **单库**：平台表与业务表全部进 `jeecg-study`，不再用双数据源。
2. **孩子独立 PIN 登录 + 家长标准账号**。
3. **文档全部同步**（PRD / 数据库 / 接口 / 前端 / 测试）。

## 1 身份模型

### 1.1 三类身份

| 身份 | 载体 | 凭据 | 登录端点 | 权限码前缀 |
|---|---|---|---|---|
| 家长 | JeecgBoot `sys_user` + 角色 `study_parent` | 用户名 + 密码 | `POST /sys/login`（底座原生） | `study:parent:*` |
| 孩子 | JeecgBoot `sys_user` + 角色 `study_kid` + `study_child` 档案 | **PIN**（4–6 位数字） | `POST /api/v1/study/kid/login` | `study:kid:*` |
| 管理员 | JeecgBoot `sys_user` + 底座 `admin` 角色 | 用户名 + 密码 | `POST /sys/login` | `study:*`（全部） |

> **关键设计：孩子也是 `sys_user`。** 这样 Shiro/JWT、Redis 会话、`@RequiresPermissions`、菜单权限**全部复用底座现成能力**，不新增第二套认证栈。孩子只是**登录方式**不同（PIN 代替密码），登录成功后签发的 token 与家长完全同构。

### 1.2 孩子 PIN 登录流程

```
孩子端打开
  ↓
① POST /api/v1/study/kid/lookup   { familyCode }
  → 校验家庭码 → 返回该家庭孩子的候选列表（仅 id / nickname / avatar）
  → 失败 4009「家庭码不正确」
  ↓
② POST /api/v1/study/kid/login    { childId, pin }
  → 校验 child 状态 + PIN（失败累计 5 次锁 10 分钟）
  → 复用底座 JwtUtil.sign(username, password, CLIENT_TYPE_APP) + Redis 存 token
  → 返回 token + 孩子信息 + 绑定的家长昵称列表（仅昵称，不含账号）
```

**为什么要有「家庭码」这一步**：孩子端不能公开列出所有孩子（信息泄露），也不能暴露底座登录页。家庭码由家长在家长端生成/重置，**明文只在生成时返回一次**，库里只存哈希。

### 1.3 家长标准账号

家长直接用 JeecgBoot 原生登录（`POST /sys/login`），**不新增接口**。登录后：

- 家长进入**家长端**（`layouts/parent`，独立布局，与学习端一样不吃管理端顶栏）
- 家长端首页展示「我关联的孩子」卡片列表
- 家长可切换查看哪个孩子的数据（切换的是**视角**，不是身份）

### 2.2 既有 13 张业务表：哪些加 `child_id`

| 表 | 加 `child_id` | 理由 |
|---|---|---|
| `study_context` | ✅ | 上下文按孩子隔离（不同孩子教材版本/年级可不同） |
| `study_textbook_version` | ❌ | 全局字典 |
| `study_knowledge_point` | ❌ | 全局考点树，内容供给成本高，家庭内共享 |
| `study_error_pool` | ✅ | 错题是孩子的 |
| `study_review_schedule` | ✅ | 排期是孩子的 |
| `study_question` | ❌ | 全局题库 |
| `study_mother_question` | ❌ | 全局母题 |
| `study_question_variant` | ✅ | 变式由某孩子的错题生成 |
| `study_word` | ❌ | 全局词库 |
| `study_grammar_point` | ❌ | 全局语法点 |
| `study_writing` | ✅ | 作文是孩子的作品 |
| `study_practice_record_202610` | ✅ | 作答记录是孩子的 |
| `study_eye_usage` | ✅ | 用眼统计是孩子的 |

> **原则：内容/知识库全局共享（7 张），学习行为/数据按孩子隔离（6 张）。**
> **7 张业务表加 `child_id`**：`study_context` `study_error_pool` `study_review_schedule` `study_question_variant` `study_writing` `study_practice_record_202610` `study_eye_usage`（含分表）。
> 新增索引 `idx_child`（`child_id`, `del_flag`）。

## 3 数据范围（Data Scope）

### 3.1 规则

| 身份 | 可读范围 | 判定来源 |
|---|---|---|
| 管理员 | 全部 | — |
| 家长 | **仅 `study_parent_child_rel` 中与自己关联的 child_id** | 每次请求实时查关系表 |
| 孩子 | **仅自己的 child_id** | JWT 携带 `childId` |

### 3.2 实现约定

- 孩子 token 载荷携带 `childId`（JWT 附加 claim）。
- 家长请求：Service 层用 `ChildScopeHelper.childIdsOf(currentUserId)` 拿到 child_id 集合，**强制**拼进 where 条件。
- **Controller 不接受前端传来的 `childId` 作为唯一依据**——家长侧必须与关系表求交集，防止越权。
- 违反隔离 → 返回 **4010 越权**（不是 404，避免探测）。

### 3.3 家长之间的隔离

- 家长 A **看不到**家长 B 的反馈、评价、申诉记录。
- 家长 A 只能看到**孩子**的客观趋势（与单用户时一致）。
- **R-04 强化**：多家长场景下**明确禁止家庭内比较**——不出现「谁的孩子更…」「家长评分对比」等任何形式。

## 5 认证与权限

| 项 | 约定 |
|---|---|
| 家长登录 | 底座原生 `POST /sys/login`，**不新增** |
| 孩子登录 | `POST /api/v1/study/kid/login`，内部复用 `JwtUtil.sign(username, password, clientType)` + Redis 存 token，**与底座同构** |
| 孩子 token 附加 claim | **不附加 `childId`**（见下方 D-28 说明）；token 与家长完全同构，只带 `username` / `clientType` |
| 家长 token 附加 claim | `role=study_parent` |
| 免认证路径 | `/api/v1/study/kid/lookup`、`/api/v1/study/kid/login`；底座 `shiro.excludeUrls` 同步登记 |
| 权限码 | `study:<资源>:<动作>`，家长 `study:parent:*`，孩子 `study:kid:*` |
| PIN 强度 | 4–6 位数字；**不要求复杂**（低龄孩子），靠失败锁定（5 次 / 10 分钟）兜底 |
| PIN 存储 | **PBKDF2-HMAC-SHA256**（每行独立盐 `pin_salt`，10 万次迭代），**不存明文**；不用底座 `PasswordUtil.encrypt`（那是 PBEWithMD5AndDES **可逆**对称加密，底座还配了 `decrypt`，4–6 位数字的 PIN 等于明文放旁边） |
| 家庭码 | 6 位大写字母数字（字母表去掉易混的 `0/O/1/I`）；**HMAC-SHA256(服务端 pepper, code)** 存 `study_family.family_code`，pepper 由配置注入（`jeecg.study.family-code-pepper`），**不入库、不进版本库** |
| 会话 | Redis，TTL 与底座一致；孩子端用 `CLIENT_TYPE_APP` 更长的过期时间 |

### 5.1 实现口径的两处偏离（ADR-029）

> 本节记录**契约正文与实现实际做法**的偏离，以实现为准，并在此同步，避免后来人按正文写代码。

**D-27 · 凭据存储策略** —— 契约正文原写「`PasswordUtil.encrypt(...)` 同款哈希」。
实现改为：

| 凭据 | 算法 | 检索方式 | 为什么不一样 |
|---|---|---|---|
| 孩子 PIN | PBKDF2-HMAC-SHA256，每行独立盐，10 万次迭代 | 按 `child_id` 取行后校验 | 熵只有 10^4–10^6，必须用慢 KDF + 每行盐 |
| 家庭码 | HMAC-SHA256(服务端 pepper) | 按 `family_code` 唯一索引直接定位 | HMAC 是**确定性**的，才能 O(1) 检索；pepper 不在库里，拿到库也反推不出码 |

**为什么不用底座 `PasswordUtil`**：它是 `PBEWithMD5AndDES` **可逆**对称加密，
底座同时提供了 `decrypt`。孩子 PIN 只有 4–6 位数字，存可逆密文等于把凭据放在明文旁边。

**D-28 · 孩子身份的 `childId` 来源** —— 契约正文原写「孩子 token 附加 claim `childId`」。
实现改为：**服务端按 `study_child.user_id` 实时反查**当前登录用户的 `childId`，不放进 JWT claim。

- 效果等价（token 与家长同构，底座 Shiro/JWT 链路不变）；
- 但更贴合契约 §3.2「Controller 不接受前端传来的 `childId` 作为唯一依据」——
  claim 是**客户端可读**的内容，反查则完全在服务端闭环；
- 停用孩子后立即失效，不需要等 token 过期。

**`study_family.family_code_salt` 列的现状**：当前 HMAC 方案是确定性的、不需要每行盐，
该列存随机盐，作为**pepper 轮换迁移的预留位**，不参与当前校验链路。
