### 3.13.6 凭据闸门补 R7：形态规则抓不到真实口令

**发现的问题**：把口令收敛到真源后复跑凭据扫描闸门，**R1…R6 全绿**，
但本轮**确实**发生过一次真口令明文入库（写进了 `CHANGELOG.md` 与本台账 §3.13），
最后是被**独立的全仓扫描**抓到的，不是闸门抓到的。

**根因**：R1…R6 全是**形态**规则：

| 规则 | 判定依据 | 为什么漏 |
|---|---|---|
| R1 / R2 / R3 / R5 | 「敏感**键名** + 值的结构」 | 散文里一句「新口令是 X」**没有键名** |
| R6 | 「字母 @ **4 位数字**」形态 | 真实口令含 `!@#`，`@` 后面不是数字 |
| 通用值判定 | `looks_like_secret()` = 字母+数字混合 | 那是**形态**判定，不是**真值**判定 |

⇒ 形态规则**天然抓不到**「带特殊字符的真实口令 + 随手写进散文」这种组合。

**R7 规则**：不看形态，只看**真值**。

1. 闸门运行期用 **DPAPI `LocalMachine`** 解开凭据真源（`CryptUnprotectData`，直接调
   `crypt32.dll`，**不依赖 pywin32**）⇒ 明文**只在内存里**，不落盘；
2. 对全部待入库文本**逐字比对** ⇒ 凭据落在任何文件、任何写法里都报红；
3. **未分类文件走兜底通道**：`.html` / `.json` / `.css` / `.svg` 等原不参与形态扫描的文件，
   现在**至少过 R7**（本轮实测另有 **20 个**文件走这条通道）；

### 3.15.9 上线学习端错题线时挖出的**两个真阻塞**（页面写了也跑不通，已修）

| # | 阻塞 | 现象 | 根因 | 处置 |
|---|---|---|---|---|
| B-1 | **孩子端错题列表 / 错因统计被权限码挡住** | `GET /error-pool`、`GET /error-pool/statistics` 后端是 `@RequiresPermissions("study:parent:error:query")`，而 `study_kid` 角色只授了 `study:kid:error:query` ⇒ 孩子端一调就 403 | 权限码只写了家长口径 | ① 权限码补 `study:kid:error:query`；② `childCode` 改**可选** —— 孩子不传时由服务端按会话取自己（契约 §3.2），前端不再需要先查 childCode 再回传 |

- §6.1 `POST /error-pool`：原文写「`multipart/form-data` + `image` 文件」，

### 3.15.11 前端构建的 EMFILE —— 失败点漂移 ⇒ 环境问题，不是代码问题

| 项 | 内容 |
|---|---|
| 现象 | `vite build` 连续 3 次在 less / PWA 后处理阶段撞 `EMFILE: too many open files`，**失败点每次都换文件**（`LinkTableListModal.vue` → `breakpoint.less` → …） |
| 判据 | **失败点漂移 ⇒ 不是那个文件的问题** ⇒ 机器级句柄耗尽；若是代码/依赖问题，同一文件会稳定复现 |
| 根因 | rollup `build.rollupOptions.maxParallelFileOps` 默认 **1000**，本机句柄被打满（进程句柄峰值 6636） |
| 处置 | 在**基座 `vite.config.ts`** 里加 `maxParallelFileOps: 16`（留 update 痕迹）—— 放在基座而非构建脚本 ⇒ **本地与 CI 跑同一条路径** |
| 实测 | `✓ built in 2m 19s`，9761 模块转换 + PWA precache 330 条全过，stderr **ERROR 行为空**，进程句柄降到约 250 |
| 产物核对 | `dist/**/*.js` 里 **22/22** 命中新增页面与组件的 `name`（21 个新页 + `StudyChildSwitcher`）—— 光有产物不算数，要按组件名逐个对账 |

> **教训**：**随机失败 + 失败点漂移 ⇒ 先查环境，不要先改代码。**
> 这与「断言随机红、报出的文件不是我改过的」是同一类信号。
> 另记一条验收口径：**「构建没报错」不等于「构建成功」** ——
> 要同时看 `✓ built in` 与 stderr 的 ERROR 行，并按组件名核对产物。

### 3.15.12 CI 首跑红了 —— GitHub 的 `services:` 容器初始化是**黑盒**

| 项 | 内容 |
|---|---|
| 现象 | 首跑 run `41790579310`（sha `6028001`）：`prepare` job 成功，主 job 挂在**第 2 步 `Initialize containers`**（耗时 13 秒），后面 10 个 step 全 skipped |
| 报错 | 只有两行：`Failed to initialize container mysql:8.0` / `One or more containers failed to start.` |

| 本地验证 | `ci.yml` YAML 可解析（2 jobs / 12 steps）；抽出的 **8 段 shell 全部 `bash -n` 通过**（heredoc 缩进已核对）；**7 道闸门全绿** |

### 3.15.13 CI 第二次也红 —— 真正的根因是**掩码值不能走 job output**

| 项 | 内容 |
|---|---|
| 现象 | 第二次 run `41792232941`（sha `8cf1d53`）仍红，但红在**我们自己的 step** ⇒ 失败现场第一次进了 job log |
| 关键证据 | 我们自己埋的 `::error::` 变成了**公开可读的 annotation**（不用登录、不用 admin）：`Can't add secret mask for empty string` + `MySQL 120 秒内未就绪` ⇒ **`MYSQL_ROOT_PASSWORD` 是空串** |
| 真正的根因 | prepare job 的 annotation：`Skip output 'db_password' since it may contain secret.` —— **runner 会跳过被掩码的值作为 job output**，`::add-mask::` 注册的值紧接着写进 `$GITHUB_OUTPUT`，在提升为 job output 时被**静默丢弃** |
| 连带解释 | **第一次首跑也是它**：`services:` 的容器 13 秒就挂（entrypoint 报 `MYSQL_ROOT_PASSWORD is required` 直接退出），GitHub 只给两行笼统报错 ⇒ 当初判成「黑盒不可定位」，其实是**一个可定位的传值问题** |
| 处置① | **删掉 `prepare` job** —— 它存在的唯一理由是 `services:` 的 env 求值时机；不用 `services:` 了，这个理由就不存在 ⇒ **跨 job 传密这件事本身就不该做** |
| 处置② | 口令经 **`$GITHUB_ENV`** 传给后续 step（掩码值的标准通道，不受「跳过 output」规则影响） |
| 处置③ | 加一步**显式断言** `DB_PASSWORD` 非空 ⇒「静默变空 ≠ 没传」，当场说清楚，而不是下游 1045 |
| 处置④ | 探活循环每轮先查容器是否还活着，**退出即带退出码与日志立刻退出**，不再白等满 120 秒 |
| **第二颗雷** | 两个闸门脚本写死 Windows 盘符路径（`ROOT = r"D:\DevProject\..."`）⇒ **本机全绿、Linux runner 上必然找不到目录**。首跑死在更早的步骤、闸门根本没跑到，所以一直埋着。已按仓内既有写法（9 个脚本）改为按 `__file__` 推导 |
| 本地验证 | `ci.yml` YAML 可解析（1 job / 13 steps）；8 段 shell 全部 `bash -n` 通过；**7 道闸门全绿**（含刚改过路径推导的两个脚本） |

> **教训**：
> ① **静默变空 ≠ 没传** —— 值跨执行单元传递时，必须有一处**显式断言**；
> 下游的报错（1045、找不到目录）会**把人带偏**到完全无关的方向。
> ② **「本机能跑」不等于「CI 能跑」** —— 脚本里看到盘符开头，一律改成 `__file__` 推导。
> ③ 埋 `::error::` annotation 是**在黑盒平台里给自己开一扇窗**：
> 本次正是靠它，匿名读到了两次失败的真实原因。
> 详见知识库 **E-41** / **E-42**。

### 3.15.14 CI 第 4–11 次 —— 绿了：三个「本地绿、CI 红」的根因

| 项 | 内容 |
|---|---|
| 现象 | 第 4–6 次 run 陆续把失败点推进到「Java 测试」，但**读不出真正原因**；第 9 次 run Java 测试已通过，又在闸门处红了一轮：第 5 次的诊断分支被 `bash -e` 直接退出（失败管道让 errexit 生效）走不到；第 6 次进了诊断分支，却把仅有的 10 条 annotation 额度花在「日志末尾 40 行」上，其中 9 条是 `MojoExecutor` 的无用栈帧 |

#### 顺手把「发布候选产物」变成可验证对象

E-51 暴露的根本问题是：**以前所有取证都是打在 vite dev server 上的** —— 对着**源码**取证，
永远看不到**产物**残缺。于是给取证脚本加了两个能力：

| 改动 | 作用 |
|---|---|
| `--front` 参数 | 前端地址可切换 ⇒ 可以对着**发布候选产物**取证。验证方式：`vite preview --mode development --port 4173` 托管 `builds/latest/frontend/dist`（`preview.proxy` 默认继承 `server.proxy`，所以后端代理照常生效），再 `2026103024-浏览器取证.py --front http://127.0.0.1:4173` |

#### E-52 发布产物的 WebSocket 指向**构建期默认地址** ⇒ 每页一条连接被拒

- **怎么发现的**：**第一次对着发布候选取证**（`vite preview` 托管 `builds/latest/frontend/dist`）⇒

  **对着 dev server 取证永远看不到** —— dev 走 `.env.development`（`http://localhost:8590/jeecg-boot`），产物走 `.env.production`。
- **根因**：`dist/_app.config.js` 的 `VITE_GLOB_DOMAIN_URL` 构建期写死 `http://127.0.0.1:8080/jeecg-boot`；
  前端通知 WebSocket 地址由它派生（`notify/index.vue`：`glob.domainUrl` 把 `http://` 换成 `ws://` 再拼 `/websocket/<userId>`）
  ⇒ 部署到 8590 时它去连 **8080**。
- **为什么上游不算 bug**：基座 `build/script/buildConf.ts` 注释原文
  「**生成外部配置文件，用于生产发布后配置，无需重新打包**」⇒ `_app.config.js` 本就是**运行期覆盖文件**，
  **部署时改**是设计内动作 —— **漏的是我们自己的发布流程**（《部署方案》§5.3 原来没有这一步）。
- **处置（已落成可执行判据）**：
  ① `build-and-sync.ps1` 新增 `-RuntimeDomainUrl`：改写**源 dist** → 同步到 `latest` → **断言生效**（没生效就 `throw`，禁止发布）；

  ③ `manifest.json` 增记 `runtimeDomainUrl` / `frontendFiles`；
  ④ 《部署方案》§5.3 新增「步骤 4：前端运行期配置」；§7.1 新增**第 11 条冒烟**（运行期配置正确）；
  ⑤ 本版产物三份（源 dist / `latest` / 版本目录）已统一改写为 `http://127.0.0.1:8590/jeecg-boot`。
- **验收**：改写后**重跑发布候选取证**（同一份产物，34 页 × 3 视口 = 102 张）：

追溯矩阵：每行一条需求，接口与用例双向可查。

[`02-追溯矩阵.csv`](./02-追溯矩阵.csv) 每行一条需求，列含义：

| 列 | 含义 |
|---|---|

用法：

1. **接任务前**——查自己那条需求的接口数与用例数，为 0 就是没人接。
2. **写完接口后**——重跑 `2026103015-追溯矩阵生成.py`，接口数应从 0 变正。
3. **进编码前**——跑 `2026103016-红线断言检查.py`，有缺口先判读。

> **口径**：状态为 `已覆盖` 的条件是「有接口**或**有用例」引用。要双向闭合（接口 + 用例都有），自己看两列计数。
