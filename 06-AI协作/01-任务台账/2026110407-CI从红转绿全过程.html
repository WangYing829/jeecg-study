CI 从红转绿全过程 · 三个「本地绿、CI 红」的根因

GitHub Actions 一共跑了 11 次：前 9 次非绿（8 次失败 + 1 次被新 push 取消），每次失败点前进一步，直到第 10 次才首次全绿。定位出三个互不相干的根因：JVM 时区与 JDBC serverTimezone 差 8 小时、全小写路径 resolve CamelCase 文件、闸门脚本路径清单用 Windows 反斜杠。三者同属「平台假设」——Windows 上成立、Linux 上不成立，且全被本地绿掩盖。

01

结论

一句话

结论

结论：CI 已经从红转绿——run #10（sha 936e1f1）conclusion = success，Java 测试 / 8 道闸门 / 前端构建全过；run #11（sha b405b68，仅文档）同样为绿。

但真正值得留下的不是「绿了」，而是绿之前那 9 次非绿是怎么一层层剥开的：它们暴露出三个互不相干的根因，而三个根因其实是同一类——平台假设。

编号口径：本文的 run 编号一律采用 GitHub 官方 run_number（可用 GET /repos/{owner}/{repo}/actions/runs 逐条核验）。实际一共 11 次 run —— 8 次失败（#1–#7、#9）、1 次被取消（#8）、2 次成功（#10、#11）。

根因 写法 Windows Linux 症状
① 时区 JVM 默认时区 ≠ JDBC serverTimezone +08:00（恰好一致） UTC datetime 列双向漂移 8 小时
② 大小写 全小写路径 resolve CamelCase 文件 不区分大小写，能找到 区分，找不到 断言假绿 / 假红
③ 分隔符 r"a\b\c.html" 反斜杠也是分隔符 反斜杠是普通字符 14 个交付物全 MISS

三个根因有一个共同特征，也是它们全部被本地绿掩盖的原因：本地跑的是 Windows。而失败信息全部指向下游（锁定期 489 分钟、列集合不一致、交付物缺失），没有一条指得到真因。

一句话教训：「本地绿、CI 红」先怀疑平台差异（时区 / 大小写 / 分隔符 / 换行符 / 绝对路径），不是先怀疑业务代码。

⚠ 别把 #8 记成一次失败。它的 conclusion 是 cancelled 而不是 failure —— 统计「连红几次」时它是分母里的噪声。CI 里 concurrency: { group: ci-${{ github.ref }}, cancel-in-progress: true } 意味着同一分支的新 push 会取消尚未跑完的旧 run ⇒ 连续修复时，编号天然会「跳号」。

推进节奏值得记一笔：前 6 次 run 全部只推进了「失败点位置」，没推进「失败原因」；真正的转折点是第 7 次——把诊断从「把日志贴出来」改成「把结论递出来」之后，一次拿到了 6 个失败用例的完整清单，两个根因同时暴露。

03

根因一 时区

8 小时

根因一 时区

application-test.yml 把 JDBC 的 serverTimezone 写死成 Asia/Shanghai ⇒ DB 会话恒为 +08:00。而 GitHub 的 ubuntu runner 默认 UTC：

写入：Java 的 Timestamp 按【连接时区】(+08:00) 落库
读出：DATETIME 按【JVM 时区】(UTC) 解释 ⇒ 读回来比写进去晚 8 小时

实测挂掉的三个用例：

用例 期望 实测
StudyKidAuthServiceTest.login_fiveFailures_locksTenMinutes 锁定期 8~10 分钟 489 分钟（= +480 分钟 = +8 小时）
StudyErrorPoolServiceTest.wrongAnswer_resetsScheduleToSameDay 排程日期 = 今天 算成明天，撞 uk_schedule_error_date 唯一键
StudyErrorPoolServiceTest.completeReview_sameDay_onlyAdvancesOnce 计数 1 计数 3

本地完整复现（这是定位到它的关键一步）：用 CI 同构库 jeecg-study-ci-test + 正确的 JDBC URL（此前被 Start-Process 传含 & 的参数截断过，一直是假象）+ JAVA_TOOL_OPTIONS=-Duser.timezone=UTC ⇒ 同样三个用例红；把 JVM 时区改回 Asia/Shanghai ⇒ 355/355 全绿。双向验证成立。

修法是三方对齐到 +08:00，不动业务代码：

  • ci.yml job 级 env.TZ=Asia/Shanghai（把 JVM 钉住）；
  • 2026110403-ci-init-db.sh 加 SET GLOBAL time_zone = '+08:00' —— 不用 -e TZ=Asia/Shanghai，因为 slim 镜像常常没有 tzdata，会静默不生效；
  • 新增 StudyTimeZoneContractTest：断言 JVM 默认时区与 yml 里 serverTimezone 同一时刻的偏移一致（比偏移而不是比 zone id：Windows 的 zone id 是「中国标准时间」，同偏移不同名）。
04

根因二 大小写

假绿

根因二 大小写

StudyRecordTableGuardTest 用全小写路径去找 CamelCase 文件：

// 旧：常量同时用于「比对」与「resolve」
"common/record/mapper/studyrecordtablemapper.java"   // 真实文件是 StudyRecordTableMapper.java
  • Windows 不区分大小写 ⇒ 找得到 ⇒ 本地绿；
  • Linux 区分 ⇒ 找不到。而当时的 RedLineScanner.read() 读不到文件会静默返回空串 ⇒ 列集合解析成空 ⇒ 三条「三处同步」断言连锁失败，失败信息是「列集合不一致」，完全指不到「路径大小写」。

修法三层：

  1. 拆常量：「用于字符串比对的小写相对路径」与「用于 resolve 的真实路径」分成两个；
  2. 读不到就炸：RedLineScanner.read() 读不到文件当场抛异常（信息里点名「Linux 区分大小写」），不再静默返回空串 —— 静默返回空值是假绿的温床；
  3. 加静态闸门：扫出所有「真的拿去做 resolve」的路径常量，逐个做大小写敏感存在性校验。
05

根因三 分隔符

全 MISS

根因三 分隔符

run #9：Java 测试已通过，红在「Python 闸门」。闸门报 9 条 [MISS]，可那些 HTML 明明在 git 里（git ls-files 查得到）。

真因在 2026103013-交付物校验.py 的文件清单：

r"01-需求迭代\02-需求文档\01-产品需求说明书.html"   # 反斜杠

Linux 上反斜杠是普通字符、不是分隔符 ⇒ 14 个交付物全部找不到 ⇒ 闸门直接红。本地 Windows 上反斜杠也是分隔符 ⇒ 一条都不报。

修法：清单改用正斜杠（Windows 同样接受）。

三个根因是同一类：平台假设。绝对路径、文件名大小写、路径分隔符 —— 全都是「Windows 上成立、Linux 上不成立」，且全都被本地绿掩盖。

06

诊断能力升级

三次

诊断能力升级

在黑盒平台上定位问题，本身就是一段需要设计的工程。三次升级：

版本 做法 结果
v1 services: + job output 传密 ❌ 平台只给两行报错，容器日志匿名拿不到
v2 显式 docker run + 就绪探测用真口令真查询 + 失败即带 docker logs ✅ 容器现场第一次进日志
v3 ::error:: annotation 逐行贴日志 ⚠️ 方向对，但额度被浪费（9 帧 Maven 栈）
v4 读 surefire 报告：error 放结论、warning 放明细 ✅ 第一次拿到完整失败清单

v4 的关键在于知道了 GitHub Actions 的 annotation 有硬上限：实测每个 step 最多 10 条 error + 10 条 warning，超出的静默丢弃（网页页脚会写 10 errors, 2 warnings, and 1 notice）。

所以「把日志末尾 40 行逐行贴成 ::error::」看着周全，实际把额度全花在栈帧上，真正要看的「哪个用例失败、报什么错」被挤掉。改成：

  • error 额度只放结论：Maven 失败摘要 + 失败用例名（≤4 条）；
  • warning 额度放细节：直接读 target/surefire-reports/*.txt 的失败摘要、异常类型、断言差异（≤5 条）。

另外两个必须记住的机制：

  • 掩码值不能走 job output：runner 会跳过被掩码的值（Skip output 'x' since it may contain secret.）⇒ 下游拿到空串且不报错。掩码值走 $GITHUB_ENV；更省事的是干脆不跨 job 传密。
  • bash -e -o pipefail 下失败管道直接退出：mvn | tee log 一失败，整个 run 块立刻退出，诊断代码永远执行不到。管道要用 || status=$? 兜住，诊断完再 exit "$status"。

新增守卫

排查的产出不只是「修好了」，还有三道让同类问题不再复发的守卫：

守卫 形式 守什么
StudyTimeZoneContractTest JUnit（2 条） JVM 默认时区必须与 JDBC serverTimezone 同一时刻偏移一致
2026110406-路径写法检查.py 闸门（第 8 道） ① Java 里用于 resolve 的常量大小写敏感地存在；② 路径字面量不用反斜杠当分隔符
RedLineScanner.read() 行为变更 断言口径 读不到文件当场炸，不再静默返回空串 ⇒ 消灭「假绿」的温床

每道守卫都做了反证（把修复改回去，必须报错）：

  • 常量改回全小写 ⇒ 闸门 exit 2，并指出真实文件名 StudyRecordTableMapper.java；
  • 清单改回反斜杠 ⇒ 闸门 exit 2，并指出文件与行号；
  • JVM 时区用 UTC 跑 ⇒ StudyTimeZoneContractTest 1 条失败。

写闸门时自己踩了一次坑：Windows 的 os.path.isfile 也不区分大小写，拿它当「精确匹配」检查会永远返回 True ⇒ 闸门形同虚设。正解是逐段拿 os.listdir 的真实目录项做精确比对。

09

复盘教训

可复用

复盘教训

  1. 「本地绿、CI 红」先怀疑平台差异 —— 时区 / 大小写 / 分隔符 / 换行符 / 绝对路径。本轮三个根因全是这一类。
  2. 本地复现必须「同构」 —— 同样的库脚本、同样的 URL、同样的 JVM 参数。只换时区就能复现，才算真的定位到。
  3. 静默返回空值是假绿的温床 —— 读文件、取配置读不到时必须炸。本轮 3 条「三处同步」断言之所以失败信息指向下游，就是因为 read() 返回了空串。
  4. 额度要花在结论上 —— annotation 每 step 只有 10+10 条，超出静默丢弃。「把日志全贴出来」不等于「把原因交出来」。
  5. 在黑盒平台给自己开一扇窗 —— 平台托管资源起不来时什么都看不到 ⇒ 改成自己 docker run，再配 ::error:: annotation，匿名就能读。
  6. 平台差异要落成可执行断言 —— 本轮新增的 2 条 JUnit + 1 道闸门，都是把「这次踩到的坑」变成「下次自动拦住」。
  7. 「被取消」不是「失败」 —— concurrency + cancel-in-progress 会让连续修复时的 run 编号跳号。统计口径必须按 conclusion 分（failure / cancelled / success），别按「我推了几次」数 —— 本轮就差点把「连红 10 次」写成事实，而真相是 8 次失败 + 1 次取消 + 2 次成功。

方法与口径

方法与口径

结论 核对方式
run 编号口径 一律用 GitHub API 的 run_number（GET /repos/{owner}/{repo}/actions/runs）；本仓共 11 条，conclusion 逐条核对，不用「本地记忆里的第几次」

时区根因 本机用 CI 同构库 + -Duser.timezone=UTC 复现，再改回 Asia/Shanghai 验证反向
路径大小写 静态扫描 + 「大小写敏感存在性」逐段精确比对（不能用 os.path.isfile，Windows 同样不区分大小写）
路径分隔符 按语义判定：把反斜杠换成正斜杠后若真能指向仓库里的文件，它就是想指那个文件
测试结论 以 target/surefire-reports/*.txt 为准，不读 mvn 控制台尾部（Spring 启动日志会淹没尾部输出）
闸门结论 逐个执行并读 exit code；2026103021 需先注入口令环境变量，否则 1045
仓库状态 git status --short（空）+ git log --oneline origin/main..HEAD（0 条）
