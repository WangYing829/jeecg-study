从 PRD 来

设计目标与原则

1.1 设计目标

本设计说明书承接《产品需求说明书 V1.1》的全部 P0 需求与红线，目标是让「六模块共享一份学情」这一唯一结构性差异在代码层面真正成立。

三个可验证的设计目标：

编号 目标 验证方式
G-01 任意两个模块的错题能在同一个池子里被同一套排期调度 跨模块错题汇聚集成测试（对应验收 A-02）
G-02 六个模块的内容全部挂到同一棵坐标树 库表外键与数据完整性检查
G-03 判对错结果 100% 可溯源到确定性逻辑，AI 输出不参与结论落库 判对错接口返回体审计 + 代码走查

1.2 五条设计原则

  1. 底座先行，不为省事绕过底座。任何模块写数据必须走底座服务，不允许模块自建错题表。绕过底座在代码评审时直接打回——这是保证 G-01 的唯一手段。
  2. 确定性优先，AI 后置。先问「这个结论能不能用规则算出来」，能就不许调模型。
  3. 写入即终态。错因、排期、掌握度三者在同一事务内落库，要么全成要么全滚。
  4. 按需抽象，不为假想需求抽象。不预留租户字段、不做通用权限体系、不做埋点看板；但已明确的隔离维度必须落地——多用户场景下 child_id 数据范围隔离是硬约束（N-05 / ADR-018），不能用「以后再说」搪塞。
  5. 可解释优先于可配置。配置项越少越稳；需要配置的地方一定是考纲版本、教材版本这类外部变量。

2.2 请求主链路（以「答一题」为例）

POST /api/v1/study/practice/answer
  │
  ├─ PracticeController.answer()            参数校验 + 鉴权
  │
  ├─ PracticeService.submit()               开启事务
  │    ├─ rule.JudgeEngine.judge()          确定性判定 ← R-02 落点
  │    │     ├─ 题型匹配器（题干/选项/填空）
  │    │     ├─ 数值容差判定（数学计算，带容差区间）
  │    │     └─ 字符串规范化比对（英语语法/单词）
  │    ├─ judgeResult = {correct, source:"rule", basis}
  │    │
  │    ├─ if (!correct)                      错题入池
  │    │    ├─ ErrorPoolService.record()    强制错因（缺错因直接抛 4001）
  │    │    ├─ ReviewScheduler.schedule()   排期：当天
  │    │    └─ MasteryService.update()       掌握度下降
  │    │
  │    ├─ ai.ExplainService.explain()       ← 只在判定之后调用，可失败
  │    │     └─ 超时/失败 → 返回降级文案，不影响事务
  │    │
  │    └─ ErrorCauseService.tagStep()       母题步骤打标（F-MTH-04）
  │
  └─ 返回 { correct, source, basis, explain?, nextReviewAt }

关键设计点：

  • AI 调用在事务内但被隔离：即使 AI 超时，事务内已写入的判定与错题记录照常提交。AI 失败只影响 explain 字段（返回 null + 降级提示），不抛异常。
  • source 字段强制：返回体必带 source，取值 rule / rule+model / model。前端据此决定是否显示「AI 仅供参考」角标，且model 不得作为唯一判定来源。
  • basis 字段必带：判定依据（命中了哪条规则、答案比对详情），供申诉与家长复核。

2.3 扩展点设计

系统需要在不重构的前提下接入后续模块（物理、化学、英语阅读等）。预留四个扩展点：

扩展点 接口 新增模块需实现
内容接入 StudyContentProvider 内容实体 → 坐标树挂载、统一 ID 分配、错题入池回调
判定规则 JudgeStrategy 按题型注册一个 JudgeStrategy 实现
遗忘模型 ForgettingModel 单词/词条的衰减更新公式（默认 SM-2 变体）
解释层 AiExplainer 针对内容类型的讲解生成器

V1.1（ADR-016）：本项目只有一个 jeecg-module-study 模块，这些扩展点接口直接定义在该模块的 service / engine 包内，不另建 jeecg-module-study-api。

JeecgBoot 拓展方式

怎么接进底座

JeecgBoot 拓展方式

3.1 决策：独立业务模块，不并入 system 模块

方案 优点 缺点 结论
A. 独立 Maven 模块 jeecg-module-study 业务代码边界清晰；可整体摘除；与上游 jeecg-module-demo、monitorV2 的 jeecg-module-monitor 做法一致 需要在 jeecg-system-start 中注册依赖 ✅ 采用
B. 并入 jeecg-module-system 少一处依赖注册 系统管理模块膨胀；学习业务与平台管理耦合 ❌
C. 独立仓库独立部署 隔离彻底 失去 JeecgBoot 的用户/菜单/权限/代码生成器复用 ❌

方案 A 与 20260722-monitorV2 的既有做法一致，工程形态已被验证。 V1.1 调整：原计划拆 jeecg-module-study + jeecg-module-study-api 两个模块， 现改为单模块 + 域优先分包——上游 jeecg-module-system 之所以拆 api/biz 是因为它被跨模块引用， 而本模块无此需求，多一个模块只增加构建复杂度（ADR-016）。

4.1 包结构（域优先 —— V1.1 变更）

分包口径已定（ADR-014 关闭）：采用业务域 → 技术层。 依据：① JeecgBoot 官方 CLAUDE.md 明确约定 org.jeecg.modules.<module>.{controller,entity,mapper,service,vo}； ② monitorV2 的 jeecg-module-monitor 实际就是这么分的；③ 同一业务域代码物理聚合，AI 更不容易漏建目录。

每个业务域包内部统一是 controller/ entity/ mapper/ service/ service/impl/ vo/ dto/（域优先，层在域内）。 family/scope/ 是唯一的例外——它是横切的数据范围组件，被所有业务域引用。

4.2 分层职责与红线

层 允许做 禁止做
Controller 参数校验、鉴权、DTO↔VO 转换 写业务逻辑、直接用 Mapper
Service 业务编排、事务边界、调用 engine 绕过底座服务直接写错题表
Engine 纯计算（判定、变式生成、衰减、掌握度） 访问数据库、访问网络
Rule 确定性判定规则 调用 AI
AI 适配层 生成讲解、追问、批改建议 返回「对/错」「得分」结论
Mapper 单表持久化 多表业务编排
Scope（数据范围） 解析当前身份可见的 child_id 集合 放业务逻辑

红线落地检查点：Engine 与 Rule 包不允许引入 AI 客户端依赖（ArchUnit 单元测试断言）。这条断言把 R-02 从口头约定变成编译期事实。

多用户落地检查点：Scope 包是唯一允许解析 child_id 的地方；Service 层取 child 集合时必须经由 ChildScopeHelper，不得直接信任前端传入的 childId（越权 → 4010）。

认证与多用户

多孩子多家长

认证与多用户

V1.1 新增章节。 系统从「单用户（一个孩子 + 一个家长）」改为「多家庭 / 多孩子 / 多家长」。 完整契约见 06-AI协作/01-任务台账/2026103019-多用户改造契约.md。

5.1 身份模型：三类身份，两种登录方式

身份 载体 凭据 登录端点 权限码
家长 sys_user + 角色 study_parent 用户名 + 密码 POST /sys/login（底座原生，不新增） study:parent:*
孩子 sys_user + 角色 study_kid + study_child 档案 PIN（4–6 位数字） POST /api/v1/study/kid/login study:kid:*
管理员 sys_user + 底座 admin 角色 用户名 + 密码 POST /sys/login 全部

关键设计：孩子也是 sys_user。 这样 Shiro 2.0.5 + JWT 4.5.0、Redis 会话、@RequiresPermissions、菜单权限全部复用底座现成能力， 不新增第二套认证栈。孩子只是登录方式不同（PIN 代替密码）， 登录成功后签发的 token 与家长完全同构（底座 JwtUtil.sign(username, password, clientType) + Redis 存 token）。 这也是「不引入第二套权限体系」的关键——多用户不等于要重写认证。

5.2 孩子端两步登录

孩子端打开
  ↓
① POST /api/v1/study/kid/lookup  { familyCode }        ← 免认证
  → 校验家庭码 → 返回该家庭孩子候选列表（仅 id / nickname / avatar）
  → 失败 → 4009「家庭码不正确」
  ↓
② POST /api/v1/study/kid/login   { childId, pin }       ← 免认证
  → 校验孩子状态 + PIN 哈希（连续失败 5 次锁 10 分钟）
  → 复用底座 JwtUtil.sign + Redis 发 token
  → 返回 token + 孩子信息 + 绑定的家长昵称列表（仅昵称，不含账号）

为什么要有「家庭码」这一步：孩子端不能公开列出所有孩子（信息泄露），也不能暴露底座登录页。 家庭码由家长在家长端生成/重置，明文只在生成时返回一次，库里只存哈希。 孩子端因此是独立的登录页，不出现「用户名/密码」。

5.3 数据范围（越权防线）

身份 可读范围 判定来源
管理员 全部 —
家长 仅 study_parent_child_rel 中与自己关联的 child_id 每次请求实时查关系表
孩子 仅自己的 child_id JWT 附加 claim childId
场景 返回
家长 A 请求孩子 B 的数据 4010 越权（不是 404，避免资源探测）
家长 A 传孩子 B 的 childCode 4010
孩子 A 请求孩子 B 的数据 4010
家长 A 不在目标家庭 4010

实现约定：家长侧 child_id 集合 = ChildScopeHelper.childIdsOf(userId) 实时查关系表的结果， 与前端传入的 childId 求交集后才能进 where 条件。不得直接信任前端参数。

5.4 家长之间的隔离

  • 家长只看到孩子的客观趋势（与单用户时一致）。
  • R-04 强化：多家长场景下明确禁止家庭内比较——不出现「谁的孩子更…」「家长评分对比」等任何形式。 新增红线断言 R04-5（家长响应不含他人标识）与 R04-6（全站无家庭内比较措辞）。

底座设计

5.1 全局上下文（F-BASE-01）

实现：StudyContextHolder（ThreadLocal）+ study_context 表。

场景 行为
进入任一模块 自动从 study_context 取当前上下文，模块不得再弹选择框
修改上下文 写新记录 + 将旧记录置 effective=false（保留历史，不删除）
历史记录与旧上下文 错题、练习记录携带当时的 context_id，切换后仍可追溯

补全点：历史记录不回填到新上下文。这是刻意的——孩子换年级后，旧的错题仍属于旧年级，不应被拉进新队列造成干扰。

5.2 坐标树（F-BASE-02 / F-REG-01…05）

结构：四层固定 地区考纲 → 学科 → 单元/章节 → 考点。

关键设计：树节点版本化而非单表树

study_knowledge_point(
  id              varchar(32)  主键（KPT-{学科码}-{序号}）
  parent_id       varchar(32)  父节点
  level           tinyint      1=考纲 2=学科 3=单元 4=考点
  name            varchar(128)
  question_type   varchar(64)   考点：题型
  score_weight   decimal(5,2)  考点：分值权重
  error_types     varchar(256)  考点：常见错误类型（逗号分隔）
  mother_q_id    varchar(32)   考点：对应母题 ID
  version         varchar(16)  节点版本
  effective_from  date         生效日期
  invalid_at      date         失效日期（NULL = 现行）
  status          tinyint      1=现行 0=失效
)

版本化策略：考纲调整时不更新旧节点，而是插入新版本节点并把旧节点 invalid_at 置为调整日。历史错题指向的旧节点仍然可查。

树的加载：单次加载当前 status=1 的全树进 Redis（key study:kp:tree:{contextId}），内存内做父子索引。改动后主动失效该 key。节点量级预计 < 5,000，全量缓存无压力。

5.3 统一 ID 体系（F-BASE-03）

分配器：IdGenerator，按前缀 + 序列生成，序列来自 Redis 自增（INCR study:seq:{PREFIX}），保证全局唯一且可读。

实体 前缀 格式

5.4 统一错题池（F-BASE-04 / F-WRG-04）

唯一入口：ErrorPoolService.record(ErrorRecord)。这是全系统唯一被允许写错题表的入口。

public interface ErrorPoolService {
    /**
     * 记录一次错误。errCause 为空直接抛 BusinessException(4001)。
     * 本方法必须在调用方的事务内执行。
     */
    String record(ErrorRecord record);
}

ErrorRecord 必填项：sourceModule（来源模块）、contentId（关联内容 ID）、knowledgePointId（知识点）、errorCause（错因）、rawAnswer（孩子原始作答）、correctAnswer。

各模块接入方式：

模块 触发点 内容 ID
背单词 单词练习答错 WRD-xxx
数学母题 变式题答错 QST-xxx（变式题也是题目）
英语语法 句子纠错 GRP-xxx + 句子哈希
语文写作 批改发现病句/表达问题 WRT-xxx + 句段定位

错因五维（F-WRG-01）：CONCEPT（概念不清）/ READING（审题偏差）/ CALC（计算失误）/ METHOD（方法不会）/ TIME（时间不够）。

设计注记：错误码用 ERROR_CAUSE 固定五维，但同时记录每个错因标签的使用频次（study_error_cause_stat）。V1 结束后按频次评估是否扩展或允许自定义——这是对竞品证据「错因维度必须由真实错题反推，不能预设」的工程化妥协。

5.5 练习作答的统一契约

所有模块的练习走同一套「作答 → 判定 → 记录」骨架，差异只在 JudgeStrategy 与内容渲染。

public interface JudgeStrategy {
    /** 该策略适用的题型/内容类型 */
    String contentType();
    /**
     * 确定性判定。禁止调用 AI。
     * @return 判定结果，必须带 source="rule" 与 basis 依据描述
     */
    JudgeResult judge(AnswerContext ctx);
}

已规划策略：

策略 适用 判定方式
SingleChoiceJudge 选择题 选项 ID 精确比对
FillBlankJudge 填空 规范化后比对（去空格/全半角/大小写）
NumericJudge 数值计算 带容差区间比对（容差可按考点配置）
ExpressionJudge 数学表达式 符号规范化 + 等价式判定
WordJudge 单词释义 同义词典匹配 + 容错字符
SentenceJudge 英文句子 语法点规则匹配 + 关键词命中
ManualJudge 写作段落 不由系统判定对错，只产出「待批改」记录，交给对照式批改

红线实现（R-02）：JudgeResult.source 字段的枚举只有 rule 与 rule+model。不存在 model 单独取值——类型层面杜绝「AI 直接判对错」。

排期

复习调度引擎

6.1 排期状态机

                    ┌──────────────┐
   答错 ──────────▶ │  PENDING(当日) │ ── 做对1次 ──▶ +1天 ──┐
                    └──────────────┘                          │
                    ┌──────────────┐                          ▼
   做错(复习中) ───▶ │ PENDING(重排) │ ◀── 做对2次 ──▶ +3天 ──▶ ...
                    └──────────────┘                          ▼
                    ┌──────────────┐
   连续3次做对 ─────▶ │  ARCHIVED     │  ← 移出队列
                    └──────────────┘
当前间隔 做对后 移出条件
当天 +1 天 —
+1 天 +3 天 —
+3 天 +7 天 连续三次做对

移出阈值取 3（不是 2），否则第 3 次做对即移出、+7 天档不可达。+14 天档仅在策略层保留（连对 3 次即毕业）。

「做对」的严格定义：母题的「过关」额外要求口述关键关系通过，口述未过时该母题保持 PENDING，不计入做对次数（F-MTH-03）。

6.2 队列生成算法

今日队列 = { 错题池中 next_review_at <= today 的条目 }
         ∪ { 单词 SRS 到期条目 }
         ∪ { 语法错句（复用错题池条目） }
         ∪ { 写作病句（复用错题池条目） }
排序键 = 薄弱度(考点掌握度) × 遗忘风险(距上次复习天数 / 预期半衰期)

关键设计：单词、语法、写作的复习条目复用错题池的记录，而非各自建表。否则「一条间隔重复队列管全部模块」就落空了。

实现要点 说明
队列物化 每日首次访问时物化到 study_review_schedule（含 sort_score），当天不变
排序稳定性 同分按 next_review_at 升序，再按 id 升序，保证顺序可预期
跨线升级 课内背错的词 upgrade=1，在课外线的到期队列中优先级加权（F-WRD-05）
容量上限 单日队列上限 50 条，超出按 sort_score 截断，其余顺延——避免孩子被任务压垮

6.3 掌握度模型

public enum MasteryState { UNKNOWN, LEARNING, FAMILIAR, MASTERED }
状态 进入条件 退出
UNKNOWN 新内容 首次答对 → LEARNING
LEARNING 连续做对 1–2 次 连续做对 3 次 → FAMILIAR
FAMILIAR 连续做对 3 次 连续做对 5 次 → MASTERED；答错 → LEARNING
MASTERED 连续做对 5 次 答错 → LEARNING（直接跌两级）

掌握度是考点级而非内容级：同一考点的所有内容共享一个掌握度，由该考点下所有作答结果聚合。这是「知识点」成为唯一坐标的意义所在。

│                  correct, basis, detail}       │

                    │ 拿着已确定的结论去要解释
                    ▼
┌────────────────────────────────────────────────┐

│  → 讲解 / 追问 / 变式提示 / 差异清单              │
│  ── 落库的是这一层的产出 ──                        │
└────────────────────────────────────────────────┘

7.2 AI 接入规范

规范 内容
位置 org.jeecg.modules.study.ai 与 engine.explain，不引入到 rule/engine.judge 包
输入 只能是「已判定的结论」+「内容」+「孩子原始作答」，不允许把内容交给模型让它判断
输出约束 结构化 JSON，schema 固定；解析失败即视为无输出
超时 3 秒；超时返回降级文案（静态讲解），不抛异常
失败语义 降级而非报错：AI 挂了只影响讲解文案的丰富度，不影响练习流程
幻觉防护 讲解中引用的知识点必须来自坐标树白名单；生成后做一次引用校验，不匹配则丢弃生成结果
申诉 每条 AI 讲解附「我不同意」入口，记录到 study_feedback，家长端可见

7.3 解释层的四种用法

场景 输入 输出
讲题 题目 + 判定结果 + 孩子作答 分步讲解（题干→思路→步骤→答案）
追问 题目 + 错因 苏格拉底式追问（不给答案）
变式提示 母题 + 孩子错在哪一步 指向关键关系的一句话提示
写作对照 作文 + 同题材佳作拆解 差异清单（最多 3 条）

「暴露错误思路」机制（借鉴豆包爱学「深度解题」）：讲题时可先复述一条孩子可能走的错误路径，再说明错在哪。这条路径由规则从错因推导，不由模型自由发挥。

8.3 模块③ 背单词（F-WRD）

双算法分线，但共用一套队列。

线 数据来源 算法 UI
课内 教材单元词表 1:1 映射 完成度优先：进度条、连续天数、养成激励 闯关、奖励、连续天数
课外 考纲高频词 + 真题熟词生义 抗遗忘优先：遗忘衰减、四档反馈、间隔重复 队列、效率视图

四档反馈（F-WRD-04）：认识 / 模糊 / 忘记 / 熟知。每档对应不同的记忆强度更新：

认识： S += 0.35, λ 不变
模糊： S += 0.10, λ *= 1.20
忘记： S = 0,     λ *= 1.60
熟知： S += 0.50, λ *= 0.80
下次复习间隔 = 基础间隔(S) × λ

遗忘模型接口化（ForgettingModel），可替换为 SSP-MMC 类模型而不动业务代码。

熟词过滤（F-WRD-03）：首次进入课外线做词汇量测试，命中的词直接标记为 known，不进队列。过滤量在报告中可见。

四个坑的设计对策：

坑 对策（落到设计）

8.4 模块④ 数学母题（F-MTH）

母题五段结构：母题实体 用五个独立字段组承载，每段可单独编辑与单独渲染：

段 存储 渲染用途
题型名 title 关卡名、检索
已知条件类型 condition_types（JSON 数组） 变式生成器的输入
关键关系 key_relation 口述过关的对象、提示语
解题步骤链 steps（JSON 数组，每步含公式与说明） 讲解、步骤打标
易错点清单 pitfalls（JSON 数组） 错因预判、追问

三层变式生成器（F-MTH-02）：

层 生成方式 检验力
L1 换数字 保持结构，替换数值参数 低（防记答案）
L2 换情境 保持结构，替换表层情境（人物/物品/场景） 中（防记套路）
L3 逆向提问 由结果反推条件 高（检验真懂）

实现约束（补全）：变式生成是结构化模板变换，不是模型自由生成。生成器读取母题的条件类型与关系式，做参数替换后由规则引擎校验答案（数值/符号等价）。模型只负责把变式转写成自然语言表述（可失败，失败则用模板文案）。这保证 R-02 不被绕过——变式的答案仍然必须算得出来。

过关判据（F-MTH-03）：

过关 = 全部 N 道变式（首版 N=3）判定为对
     AND 口述关键关系通过（孩子口述或用语音转文字后由规则匹配关键关系关键词）

口述未过的处理：给一道苏格拉底式追问（针对 key_relation 的一个提示问题），不给答案。追问后仍不过关，母题保持 PENDING。

闯关顺序（F-MTH-05）：按考纲优先级排序——score_weight 降序 + 掌握度升序 + 薄弱度降序。不是随机推荐，也不是按录入顺序。

8.5 模块⑤ 英语语法（F-GRM）

设计点 说明
句子变形器 输入中文意思，输出 5 种英文表达。优先从语料库检索，无命中时由模型生成并经校验
错误定位 确定性规则优先：句法模式匹配 + 形态规则（时态一致、主谓一致、冠词、介词搭配）。规则无法定位时才交给模型
最小讲解 每个语法点自带 rule（一句话规则）、example（同类例句）、counterExample（反例）三件套，存库而非现生成
考纲锚定 语法点挂考点树，exam_type 字段标注单选/完形/语法填空/书面表达
错句收藏馆 复用统一错题池，只做视图筛选
语境库复用 与背单词共用 study_sentence_context 表，一份语料两处用

「错误即入口」的链路：

写句子 → 提交 → 规则定位错误 → 点击错误 → 弹出三件套 → 立刻改一次 → 改对则标记该错误点已掌握

8.6 模块⑥ 语文写作（F-WRT）

设计点 说明
六层拆解 WRT-HOOK（题目钩子）/ WRT-OPEN（开篇三句）/ WRT-MATERIAL（选材角度）/ WRT-STRUCT（结构图）/ WRT-HAND（三个手法例句）/ WRT-END（结尾回扣）。每层末尾附「换到你的题目上会怎么写」的提示题
对照式批改 输出「你这篇 vs 同题材佳作的差异清单」，最多 3 条。条数上限在服务层强制
三步训练流 审题 → 列提纲 → 写初稿。提纲未通过不允许提交初稿（服务端校验，非前端禁用）
情境库 同主题给不同处境/年龄/细节的情境，不给金句
温和分寸 只在语法/逻辑/结构层给建议，不做主观评价，不评价情感表达
错因入池 病句/表达问题按错因标签入统一错题池

防代写的服务端校验：

if (submission.step != "DRAFT" && !outline.passed) {
    throw new BusinessException(4002, "请先完成并通过提纲步骤");
}

8.7 家长端（F-PAR）

只读实现：家长端所有接口走独立的 ParentReadController，复用同一套 Service 但只暴露读方法。写操作仅限「一句话反馈」与「提醒偏好」两个白名单接口。

硬约束 实现
无辅导建议 报表接口的 DTO 中不含任何建议/讲解字段
无排名 DTO 字段不含 rank/percentile/compare；文案层无相关词
无答案查询 不提供按 ID 取答案的接口；JudgeResult 不对外暴露
一句话反馈 parent_feedback 表，content 长度上限 100 字，只关联练习/作文记录
身份区分 家长端与孩子端通过角色区分；家长操作写 parent_operation_log

10.1 统一响应与错误码

{
  "success": true,
  "code": 0,
  "message": "ok",
  "result": { }
}
错误码 含义 典型场景
4001 缺少错因 提交练习未选错因
4002 前置步骤未完成 写作未过提纲提交初稿
4003 违反练习顺序 未作答就请求解析
4004 上下文未配置 首次使用未配置地区/教材
5001 判定策略缺失 该题型未注册 JudgeStrategy

10.2 判对错响应契约

{
  "success": true,
  "result": {
    "contentId": "QST-SELF-2026-0088",
    "correct": false,
    "source": "rule",
    "basis": "数值容差判定：期望 12.5，实际 12，允许偏差 ±0.05",
    "detail": { "expected": "12.5", "actual": "12", "tolerance": 0.05 },
    "explain": { "type": "STEP_BY_STEP", "text": "..." },
    "explainStatus": "OK",
    "nextReviewAt": "2026-10-30",
    "errorId": "ERR-00000123"
  }
}

契约要点：

字段 约束
source 必带；rule 或 rule+model；无 model 单独取值
basis 必带；人可读的判定依据；家长端可见（脱敏后）
explain 可为 null；explainStatus 取 OK / TIMEOUT / UNAVAILABLE / SKIPPED
nextReviewAt 仅在 correct=false 时返回
errorId 仅在 correct=false 时返回；与 errorPool 表记录一一对应

10.3 练习页作答顺序契约（R-01）

练习页的「解析/答案」区块由前端 PracticeAnswerGate 组件控制：

状态机：UNANSWERED → ANSWERED → (可选) REVEALED
- UNANSWERED：解析组件不渲染到 DOM（不是 CSS 隐藏）
- ANSWERED：判定结果返回后才挂载解析组件
- REVEALED：孩子主动点「看解析」后才展开

「不渲染到 DOM」而非 display:none：这样「未作答即无法看到答案」在 DOM 层面即成立，评审可直接用 DOM 查询验证（对应验收 A-08）。
