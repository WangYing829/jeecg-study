## 2 铁律

| # | 规则 | 理由 |
|---|---|---|
| 1 | **脚本必须幂等**：重复执行不报错、不重复插数据 | 开发期反复执行是常态；非幂等脚本会把库搞脏 |
| 2 | **变更走增量脚本，不改历史脚本** | 历史脚本已在新环境执行过，改了会导致环境间 schema 不一致 |
| 3 | **表前缀 `study_`** | 与 `jeecg-boot` 库的底座表区分，见 `00-项目说明.md` §6.2 |
| 4 | **不写 `DROP TABLE`** | 除 `06-cleanup.sql` 的种子数据清理外，一律不删表 |
| 5 | **不含真实个人信息** | 家庭私有部署也不存真实孩子信息；种子数据全部虚构 |
| 6 | **不含口令** | 连接参数在 `application-dev.yml`（gitignore），脚本里不写 |
| 7 | **字符集 utf8mb4 / utf8mb4_unicode_ci** | 与建库语句一致 |

## 3 幂等写法速查

```sql
-- 建表
CREATE TABLE IF NOT EXISTS `study_xxx` ( ... );

-- 插入种子数据
INSERT INTO `study_textbook_version` (`id`, `name`) VALUES ('TV-RENJIAO', '人教版')
  ON DUPLICATE KEY UPDATE `name` = VALUES(`name`);

-- 加列
ALTER TABLE `study_xxx` ADD COLUMN IF NOT EXISTS `yyy` varchar(32) DEFAULT NULL;
```

> MySQL 8.0.29+ 才支持 `ADD COLUMN IF NOT EXISTS`。目标环境低于该版本时，用「先查 `information_schema.columns` 再决定」的存储过程写法。

## 4 执行顺序

```
02-schema.sql   （建库 + 建表）      ← 首次执行
03-init.sql     （种子数据）        ← 首次执行
04-fix.sql      （增量修复）        ← 按需追加执行
05-partition.sql（分表）            ← 每月 1 日由定时任务执行
06-cleanup.sql  （清理种子数据）    ← 仅测试环境用，保留结构
12-writing-scenario.sql            （增量：写作情境库建表 + 种子）← 首次部署必须执行
13-writing-scenario-cleanup.sql    （清理写作情境库种子）        ← 仅测试环境用
14-grammar-context-game.sql        （增量：语境库 + 玩法题库建表与种子）← 首次部署必须执行
15-grammar-context-game-cleanup.sql（清理语境库与玩法题库种子）  ← 仅测试环境用
16-seed-writing-scenario-menu.sql  （增量：写作情境页面菜单）        ← 前端页面就位后执行
17-seed-grammar-game-menu.sql      （增量：语法玩法页面菜单）        ← 前端页面就位后执行
18-seed-grammar-point.sql          （增量：语法点种子）              ← 与 14 号同批部署
19-seed-admin-study-menu.sql       （增量：admin 授权 study 菜单与按钮 + admin 进演示家庭）← 首次部署必须执行
20-fix-menu-icon-name.sql          （增量：修正失效的菜单图标名）    ← 首次部署必须执行
21-fix-study-menu-always-show.sql  （增量：修正一级菜单聚合路由标记）← 首次部署必须执行
```

> `12-writing-scenario.sql` 建的是 `study_writing_scenario`（内容表），
> **不在 `02-schema.sql` 里**，首次部署时必须单独执行一次（幂等，重复执行安全）。
>
> `14-grammar-context-game.sql` 建 4 张表（3 张内容表 + 1 张行为表 `study_grammar_game_record`），
> 同样**不在 `02-schema.sql` 里**，且**必须排在 `09-seed-content.sql` 之后**——
> 语境库的主例句直接取 `study_word.context_sentence`，两者是同一批例句。
>
> `16-` 与 `17-` 是**页面菜单**脚本，只往 `sys_permission` / `sys_role_permission` 插两行，
> 不建表、不改表结构，因此不依赖上表；排在 `07-seed-role-menu.sql` 之后即可。
>
> `19-` / `20-` / `21-` 是**管理端可见性**脚本，只改 `sys_permission` / `sys_role_permission` /
> `study_family_member` / `study_parent_child_rel` 的数据行，同样排在 `07-` 与 `08-` 之后即可；
> 三支都幂等，重复执行安全。

## 5 与追溯的关系

- **改了表结构** → 更新《数据库设计说明书》源稿 → 重跑提取器 → 重跑 `2026103015-追溯矩阵生成.py`。
- **新增业务表** → 先在《数据库设计说明书》补 DDL → 再跑提取器。**不要只在这里加表**，否则文档与脚本会分叉。
- **新增接口读新表** → 接口总表的「需求」列要挂上对应需求编号，否则追溯矩阵显示 `未覆盖`。

## 6 迁移记录

执行过的脚本要留痕。《部署方案》§迁移与初始化定义了 `study_schema_migration` 表——**每执行一次脚本，写一条记录**（脚本名、校验和、执行时间、执行人）。表结构见《数据库设计说明书》§迁移与初始化。

> **脚本内容 SHA-256 要入库登记**，防止事后改脚本。manifest 里记 `dump_sha256` / `schema_migration_registry.checksum` 这类字段。

## 7 常见问题

| 现象 | 原因 | 处置 |
|---|---|---|
| 重复执行报「Duplicate entry」 | 脚本非幂等 | 补 `ON DUPLICATE KEY UPDATE` 或 `IF NOT EXISTS` |
| 不同环境表结构不一致 | 有人改了历史脚本 | 用 `04-fix.sql` 补增量，**不要回改历史** |
| `study_practice_record_202610` 不存在 | 分表脚本没跑 | 执行 `05-partition.sql` |
| 找不到 `IF NOT EXISTS` 支持 | MySQL 版本低 | 用 `information_schema` 判断式写法 |
